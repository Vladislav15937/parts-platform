# Боевой сервер пилота

Паспорт машины, на которой поднят первый живой клиент, и как в неё зайти.
Заведён по `docs/cloud-bringup.md`; здесь — не «как поднять вообще», а «что
именно поднято и где у него что». Секретов в этом файле нет и быть не должно:
только имена и пути, значения живут в `.env` на самой машине (см. §Секреты).

Снято живьём **2026-08-13**, сразу после подключения клиента `yardt`.

## Как зайти в консоль

### 1. Обычный путь — SSH с рабочей машины

```bash
ssh deploy@200.165.228.163
```

- **Пользователь `deploy`, не root.** Вход по root закрыт намеренно
  (`/etc/ssh/sshd_config.d/00-hardening.conf`, `PermitRootLogin no`):
  `ssh root@…` не пустит вовсе. Всё, что требует прав, — через `sudo`.
- **Вход по ключу, пароль по SSH выключен.** Публичный ключ рабочей машины
  положен `deploy` при заведении (`ssh-copy-id`). Если ключей несколько,
  указать нужный: `ssh -i ~/.ssh/<приватный_ключ> deploy@200.165.228.163`.
- **Первый вход спросит отпечаток хоста** — это норма для новой машины,
  сверить и ответить `yes`. Дальше он запомнен в `~/.ssh/known_hosts`.
- **Репозиторий клиента живёт в** `~/parts-platform` (у `deploy`). Все
  команды ниже — из него.
- **Docker — без `sudo`:** `deploy` в группе `docker`. `sudo` нужен только
  для системного (ufw, пакеты).

### 2. Запасной путь — веб-консоль Timeweb (когда SSH не пускает)

Если сломали SSH (неудачное правило `ufw`, потеря ключа, опечатка в
`sshd_config`) — машина всё ещё доступна через панель, минуя сеть:

1. `https://timeweb.cloud/my/servers/8799637` → вкладка **«Консоль»**
   (VNC прямо в браузере).
2. Логин **паролем** (не ключом): пользователь `deploy` или `root`, пароль —
   **из менеджера паролей**, в этот файл он не выписан. Пароль root задавался
   при создании сервера в панели Timeweb.
3. Починить причину (вернуть правило `ufw allow 22`, поправить
   `sshd_config`, `sudo systemctl restart ssh`) — и вернуться к SSH.

Веб-консоль — единственный вход, который не зависит от `ufw`, `ssh` и сети.
Пароль root от неё поэтому хранить обязательно: потеряв и ключ, и пароль,
машину не открыть ничем, кроме переустановки.

### 3. Firewall

Наружу открыты ровно три порта (`sudo ufw status`):

| Порт | Зачем |
|---|---|
| 22 | SSH |
| 80 | HTTP → Caddy (редирект на 443 и ACME-проверка Let's Encrypt) |
| 443 | HTTPS → Caddy |

Порт приложения (8080), Postgres (5432), MinIO (9000), Kafka, Prometheus,
Alertmanager **наружу не смотрят** — они `expose` внутри сети compose, снаружи
их нет. Pushgateway висит на петле `127.0.0.1:9091`. Это не косметика:
открытый порт приложения свёл бы на нет и ограничение управляющего контура
по адресам, и защиту хранилища.

## Что запущено

Стек поднимается одним `docker compose -f docker-compose.prod.yml`. На
2026-08-13 работает семь контейнеров:

| Контейнер | Роль | Наружу |
|---|---|---|
| `caddy` | терминатор TLS, единственная точка входа | 80, 443 |
| `app-blue` / `app-green` | приложение + PWA (собрана внутрь jar); в покое работает одна сборка, на время выкладки обе | — (8080 внутри) |
| `postgres` | база; схема на арендатора | — (5432 внутри) |
| `minio` | хранилище фотографий (S3) | — (9000, через `s3.*`) |
| `prometheus` | сбор метрик | — (9090 внутри) |
| `alertmanager` | тревоги в Telegram | — (9093 внутри) |
| `pushgateway` | приём отметок от бэкапа | 127.0.0.1:9091 |

**Kafka не запущена, и это норма для пилота.** Она за профилем
(`--profile kafka`); без неё событийный контур идёт через outbox
in-memory-транспортом. Одноразовый контейнер `mc` (создаёт бакет фотографий
при старте) отрабатывает и выходит — в списке работающих его нет.

Приложение отвечает: `curl https://parts.plus-parts.ru/` → **200**.

## Секреты

**Значения — только в `.env` на машине (права `600`), в репозиторий не
попадают.** Что за секрет и зачем — реестр в `docs/deployment.md`, «Секреты
ячейки». Шаблон с пустыми значениями — `ops/env.pilot.example`.

| Что | Где | При утечке |
|---|---|---|
| `DB_PASSWORD` (владелец схем) | `.env` | сменить `ALTER ROLE`, пересоздать сборку под трафиком (`$C up -d $A`) |
| `APP_RUNTIME_PASSWORD` (рабочая роль) | `.env` | то же |
| `APP_CRYPTO_KEY` | `.env` | **необратимо**: ключи кабинетов не расшифровать. Копия — ОТДЕЛЬНО от бэкапа базы |
| `APP_PROVISIONING_TOKEN` | `.env` | сменить; **после подключения очистить** (пустое = выключено) |
| `S3_SECRET_KEY` | `.env` | сменить в MinIO и `.env` |
| токен бота тревог | `ops/secrets/telegram-token` (права `644`) | перевыпустить у @BotFather |

**644 у токена тревог — не ошибка:** контейнер Alertmanager бежит под `nobody`
(uid 65534) и файл, доступный только владельцу, не прочитает — тревога
сработает, но в Telegram не уйдёт. Защита тут в том, что токен не в переменной
окружения (её видно в `docker inspect`), а не в правах файла.

**Открытый долг на 2026-08-13:** `APP_PROVISIONING_TOKEN` ещё задан
(клиент только что заведён). Подключение закончено — пора очистить и
пересоздать сборку под трафиком (см. §Провижининг). Забытый включённым, он
даёт любому, кто дошёл до управляющего контура, заводить схемы, пока
не кончится диск.

## Повседневные команды

Всё — из `~/parts-platform` под `deploy`. Для краткости:
`C="docker compose -f docker-compose.prod.yml"`.

**Статус и здоровье**
```bash
A=$(ops/switch-build.sh --current)       # сборка под трафиком: app-blue или app-green
$C ps                                   # что поднято
$C logs $A --tail 100                   # хвост лога приложения
$C logs $A -f                           # следить в реальном времени
$C logs caddy --tail 50                 # сертификаты, входящие
curl -s -o /dev/null -w '%{http_code}\n' https://parts.plus-parts.ru/
```

**Журналы защищены?** (рабочая роль не владеет журналами)
```bash
$C logs $A | grep -m1 -E 'Журналы (защищены|правятся)'
```
Должно быть «Журналы защищены». «правятся прямым SQL» = ячейка работает одной
ролью, защита снята.

**Рестарт и выкладка новой версии**
```bash
$C restart $A                           # просто перезапуск, той же версией
```

**Новая версия ставится не перезапуском, а второй сборкой рядом — и на копии
базы** (задачи 0079 и 0112). Одной командой, она же стоит за кнопкой
(`docs/deploy-button.md`):

```bash
git pull                                # свежие compose и ops/ — не код
git rev-parse HEAD                      # полный SHA новой версии
ops/deploy.sh --tag <этот SHA>          # заморозка записи, копия базы, новая сборка
                                        # на копии рядом, трафик, самопроверки, и только
                                        # потом открыть запись и погасить старую
```

Запись на время выкладки заморожена — замерено 32 секунды на репетиции; чтение
работает, продавец видит «Идёт обновление, подождите», офлайн-очередь приёмки
повторяет сама. Упало до точки невозврата — трафик, база и запись прежние,
копия удалена. Оборвалась сама команда (упал ssh) — `ops/deploy.sh --abort`.

**Первая такая выкладка на этой машине пройдёт со сборкой, которая про
заморозку не знает.** Её код старше задачи 0112: на время заморозки запись
отвечает «Внутренняя ошибка», а не «идёт обновление». Данные при этом целы —
заморожена база, — но продавцу о минуте простоя лучше сказать заранее.

**Машина ничего не собирает** (задача 0074): образ собран один раз в CI
и лежит в реестре, `git pull` здесь за `docker-compose.prod.yml` и каталогом
`ops/`, а не за исходниками. Тег — **полный** SHA, сорок символов: короткого
в реестре нет, `pull` отвечает `manifest unknown` и ничего не трогает —
работающее приложение при этом остаётся прежним. Пустой тег валит команду
словами «укажите APP_IMAGE_TAG — SHA коммита, собранного CI».

**Откат после выкладки — `ops/deploy.sh --tag <прежний SHA> --migrate-with
none`**, а не обратное переключение: откатывается только приложение, база
остаётся новее и чинится вперёд. У прежней сборки прежняя база — замороженный
слепок на момент выкладки, — и `ops/switch-build.sh` на неё трафик
не переводит. Теги, профили и имя базы каждой сборки в `.env` ведёт сама
выкладка.

Порядок выкладки — expand/contract: сначала совместимая миграция, потом накат
схем арендаторов, потом код (см. `docs/deployment.md`, «Переключение трафика:
синяя и зелёная сборки»).

**Миграции схем арендаторов** (после нового changeset'а)
```bash
ops/migrate-tenants.sh                  # идёт по реестру, падает, если кто отстал
```

**Бэкап и проверка**
```bash
ops/backup.sh                           # дамп по арендатору + зеркало фото + офсайт
ops/verify-backup.sh                    # восстановление в отдельную базу со сверкой
```
Ставится по крону (`ops/install-cron.sh`): бэкап ежедневно, проверка
по понедельникам. Отметки уходят в pushgateway → Prometheus; пропажа отметки
сама поднимает тревогу.

**Провижининг нового арендатора** (изнутри контейнера — управляющий контур
снаружи закрыт, отвечает 404)
```bash
$C exec $A wget -qO- --header='Content-Type: application/json' \
  --post-data '{"token":"<APP_PROVISIONING_TOKEN>","companyCode":"…",
                "companyName":"…","ownerLogin":"…","ownerPassword":"…",
                "ownerName":"…"}' \
  http://localhost:8080/api/provisioning/tenants
```

**Выключить провижининг после подключения**
```bash
# в .env: APP_PROVISIONING_TOKEN=   (пусто)
$C up -d $A                             # пересоздать сборку под трафиком: она читает .env
```

**Проверка прайса Дрома** (число объявлений и снимков в файле)
```bash
URL='https://parts.plus-parts.ru/feeds/drom/<код>/<токен>.xml'
curl -s "$URL" | grep -o '<offer>' | wc -l     # объявлений
curl -s "$URL" | grep -o '<photo>' | wc -l     # снимков
```

**Psql владельцем** (для сверок; рабочая роль журналы менять не может)
```bash
$C exec -T postgres psql -U "$DB_USER" -d "$(ops/switch-build.sh --current-db)" -c 'SELECT ...'
```
База — сборки под трафиком: с первой выкладки копией это уже не `parts`
(задача 0112), а `parts` — замороженный слепок, в котором сегодняшней работы нет.

## Что помнить об этой машине

- **Одна ячейка на сервер.** Второй клиент масштаба «YARD» — на другой сервер:
  порты 80/443 одни, и десять разборок одного города общаются между собой.
- **Диск кончится раньше памяти.** Сейчас занято 6 ГБ из 96, но склад пилота
  ещё мал; снимки одного клиента масштаба «YARD» — ~24 ГБ, плюс зеркало
  бэкапа рядом. Следить за `df -h /`.
- **Офсайт-копия обязана жить вне этой машины.** Потеря диска уносит клиента
  вместе с локальным бэкапом. `OFFSITE_REMOTE` в `.env`, тревога
  `ОфсайтНеУезжал` — если её нет, копия наружу не уходит.
- **Смена имени проекта compose = пустая база на месте живой** (тома
  привязаны к имени). Не переименовывать работающую ячейку.
- **`APP_IMAGE_TAG` в `.env` появился позже самой машины.** Ячейка поднята
  13 августа 2026, когда прод собирал образ сам; переменную завела задача 0074
  (13 сентября). Если в `.env` на сервере её ещё нет, первая же выкладка
  остановится на ней — до запуска чего бы то ни было, сообщением «укажите
  APP_IMAGE_TAG». Вписать туда SHA выкладываемой версии; «оставить как
  сейчас» вариантом не является — работающий образ собран на этой машине,
  в реестре его нет и имени у него нет.
- **Сертификаты продлевает Caddy сам.** `ACME_EMAIL` в `.env` — туда придёт
  письмо, если продление сломалось; без верного адреса о проблеме узнать
  неоткуда, а в тот же день у приёмщиков пропадёт камера.
