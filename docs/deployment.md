# Развёртывание ячейки

Ячейка — комплект Postgres + S3 на группу арендаторов: 500 выдержаны пробой,
планировать наполнение стоит на 200–300 (см. «Сколько держит ячейка»). Отдельный
кластер на клиента не делаем: при пятистах клиентах это 12–22 млн ₽/мес против
150–450 ₽ на арендатора в ячейке.

## Что нужно до первого запуска

> Голый арендованный сервер до этого шага — Docker, firewall, домены,
> rclone для офсайта — поднимает `docs/cloud-bringup.md`. Здесь начинается
> с того, что машина к запуску ячейки уже готова.

Два домена, оба A-записью на эту машину: приложение и хранилище фотографий.
Записи должны существовать **до** запуска — Caddy получает сертификаты сам,
а Let's Encrypt проверяет владение доменом запросом на него же.

Хранилище отдельным именем не для красоты: телефон грузит снимок туда напрямую
по подписанной ссылке, мимо приложения, и хост входит в подпись.

## Как поднять

```bash
cp .env.example .env                   # 1. заполнить секреты и APP_IMAGE_TAG
ops/config-guard.sh                    # 2. настройки ячейки на месте — файл, а не каталог
docker compose -f docker-compose.prod.yml pull             # 3. забрать образы
docker compose -f docker-compose.prod.yml up -d            #    и поднять ячейку
ops/create-roles.sh                    # 4. завести рабочую роль
docker compose -f docker-compose.prod.yml restart "$(ops/switch-build.sh --current)"   # 5. перечитать роли
ops/install-cron.sh                    # 6. бэкапы по расписанию
ops/basebackup.sh                      # 7. первая базовая копия — сейчас, не в воскресенье
```

**Ячейка ничего не собирает, и `APP_IMAGE_TAG` обязателен.** Образ приложения
собран один раз в CI и лежит в реестре — выкладка его только забирает
(задача 0074). Поэтому в шаге 3 стоит `pull`, а не `--build`: собирать нечем
и нечего, рядом не нужны ни исходники, ни Dockerfile, ни JDK с node. Нужны
`docker-compose.prod.yml`, каталог `ops/` с настройками и `.env`.

Тег — **полный SHA** коммита, образ которого опубликовал CI:

```bash
git rev-parse HEAD    # 40 символов; это и есть APP_IMAGE_TAG, если CI на нём зелёный
```

Сорок символов, а не семь: короткого тега в реестре нет вовсе, и попытка
отвечает `manifest unknown`. Тот же SHA печатает сам прогон CI — задача
«Публикация образа», последняя строка: `Выкладка ячейки: APP_IMAGE_TAG=…`.

Незаполненный тег останавливает выкладку **до** того, как что-нибудь
запустится:

```
error while interpolating x-app-image-tag-required: required variable
APP_IMAGE_TAG is missing a value: укажите APP_IMAGE_TAG — SHA коммита,
собранного CI
```

Умолчания у него нет намеренно: подставленный `latest` означал бы «неизвестно
что» ровно в тот день, когда надо назвать, какая версия работает у клиента.

Входить в реестр не нужно: пакет публичного репозитория читается анонимно.

Шестой шаг не «на потом»: правила тревог начинаются с `absent()`, то есть
ячейка, на которой забыли расписание, сообщает об этом сама. Без него
«тревог нет» означало бы «бэкапов нет» ровно до того дня, когда они
понадобятся.

Седьмой — тоже не «на потом», и по той же причине. Базовую копию расписание
снимает по воскресеньям; пока её нет, архив WAL накатывать не на что, то есть
точки возврата у ячейки нет вовсе — при исправно работающей архивации
и снимающихся дампах. Тревога `БазоваяКопияНеСнималась` про это скажет,
но между подъёмом ячейки и первым воскресеньем может уложиться вся неделя
подключения клиента.

Приложение поднимется на `:8080`, хранилище фотографий на `:9000`. Общая схема
`catalog` накатывается при старте сама — руками её гонять не нужно.

Первого клиента заводит `POST /api/provisioning/tenants` под секретом
`APP_PROVISIONING_TOKEN`. Секрет задавайте на время подключения и убирайте
после: забытый включённым, он даёт любому желающему заводить схемы, пока
не кончится диск.

### Шаг 4 обязателен, и вот почему

Пока приложение ходит в базу одной ролью, оно владелец всех таблиц —
а владелец возвращает себе любое право одной командой. Значит журнал движений,
журнал изменений и журнал лицевых счетов правятся прямым SQL, и `REVOKE`
этого не отбивает. Это единственная дыра в доказуемости журналов: «куда делась
деталь» и «кто уронил цену» перестают быть доказательством ровно тогда, когда
их спрашивают.

`ops/create-roles.sh` заводит рабочую роль и отдаёт ей общую схему на чтение.
Права на схемы арендаторов выдаёт само приложение — при провижининге нового
клиента и при каждом накате миграций, включая те схемы, которым накатывать
нечего. То есть скрипт запускается **один раз на ячейку**, дальше всё
расходится само.

Роль создаётся скриптом, а не миграцией, и это не небрежность:

- пароль в changeset — это секрет в git навсегда, включая историю;
- роль принадлежит кластеру, а не базе, и версионировать её по схемам нечем;
- `pg_dump` роли не выгружает — при восстановлении ячейки её всё равно
  заводят отдельно, как и расширения Postgres;
- миграции идут владельцем, а `CREATE ROLE` требует `CREATEROLE`: пришлось бы
  расширить права владельца ради одной операции.

Пропущенный шаг ловится сам. При старте приложение спрашивает у базы, может
ли оно переписать движение склада, и если может — пишет в лог:

```
WARN  Журналы правятся прямым SQL из приложения: [stock_movement, audit_log,
      customer_account_entry] доступны на UPDATE роли app…
```

При верной настройке там `INFO Журналы защищены`. Запуск не валится: в
разработке одна роль законна, и падение на старте означало бы, что локально
ничего не поднять без двух ролей.

В `.env` для этого нужны четыре значения:

```
APP_RUNTIME_ROLE=partsflow_app
APP_RUNTIME_PASSWORD=<пароль рабочей роли>
APP_DDL_USERNAME=<владелец схем, тот же DB_USER>
APP_DDL_PASSWORD=<его пароль>
APP_DDL_URL=jdbc:postgresql://postgres:5432/parts
```

## Один артефакт, один домен

PWA собирается внутрь jar и отдаётся тем же приложением. Это не экономия
контейнера: сессия живёт в cookie, а CSRF-токен читается из cookie скриптом —
и то и другое работает только на одном источнике. Разнести фронтенд и API
по разным доменам значит сломать вход.

Сборка образа тесты не гоняет: они поднимают Postgres через Testcontainers,
то есть требуют докера изнутри сборки. Их место в CI, и там они уже есть.

## Новая версия: что знать до выкладки

Версия ячейки — это **тег образа**, и меняется она не перезапуском
приложения. Сборок в ячейке две (`app-blue` и `app-green`): новая поднимается
рядом с работающей, доказывает готовность, получает трафик — и только потом
старую гасят. Готовиться к выкладке отсюда, выполнять — по разделу
«Переключение трафика: синяя и зелёная сборки» ниже, подраздел «Выкладка
по шагам»; команды выкладки стоят там одним списком и только там.

**Сервиса `app` в боевом compose нет** — с 13 сентября 2026 (задача 0079) их
двое, по имени сборки. Команды вида `pull app` или `up -d app` отвечают
`no such service: app`; какая сборка под трафиком сейчас, говорит
`ops/switch-build.sh --current`.

**Настройки берутся тем же SHA, что и образ, а не `git pull`** (задача 0111,
подтверждено владельцем 14 сентября 2026). Иначе на машине оказывается код
одной версии и конфигурация терминатора другой, и этому не препятствует
ничто: `git pull` тянет произвольный свежий `main`. Кнопка так и делает —
`rsync` из checkout'а по выкладываемому коммиту; ручной путь приведён
к тому же задачей 0114. Командами это шаг 0 подраздела «Выкладка по шагам»
ниже, и он же — первое, что делают перед `ops/deploy.sh`: тот берёт `ops/`
и `docker-compose.prod.yml` из рабочего дерева машины.

**Из репозитория ячейке нужен не код, а настройки** — сам
`docker-compose.prod.yml` и каталог `ops/`: семь файлов монтируются
в терминатор, Postgres, Prometheus и alertmanager, и пропажу такого файла
docker не сообщает, а создаёт на его месте пустой каталог (у Postgres после
этого `archive_command` падает с кодом 126 при внешне работающей базе).
Поэтому шаг 0 кончается `ops/config-guard.sh`.

**Версия ячейки живёт в `.env`, а не в памяти выкладывающего.** `APP_IMAGE_TAG` —
единственный ответ на вопрос «какая версия работает у клиента». На время
выкладки рядом с ним стоит тег второй сборки (`APP_IMAGE_TAG_GREEN` — в `.env`
либо перед командой), а после успеха новый SHA переносят в `APP_IMAGE_TAG`
и временный убирают: пока это не сделано, `.env` описывает состояние выкладки,
а не ячейки.

**О невыложенном коммите узнаёте до того, как что-то поднимется.** `pull`
на теге, которого в реестре нет, отвечает `manifest unknown` и ничего
не трогает: людей продолжает обслуживать работающая сборка. Так бывает, когда
прогон CI на этом коммите ещё идёт или покраснел — публикация ждёт всех
проверок.

**Откат после выкладки — это выкладка прежнего SHA, а не обратное
переключение** (задача 0112): `ops/deploy.sh --tag <прежний SHA>
--migrate-with none`, кнопкой — то же самое. Откатывается только приложение,
база остаётся новее него и чинится вперёд. Обратное переключение
(`ops/switch-build.sh blue`) после выкладки вредно: у прежней сборки
прежняя база, замороженный слепок на момент переключения, и люди увидели бы
вчерашний склад. Переключатель поэтому на сборку с замороженной базой
не переводит и говорит, что делать вместо этого. Пока выкладка не прошла
точку невозврата, возврат делает она сама — и вот он стоит секунды.

**Встало ли — спрашивают у приложения, а не смотрят глазами:**
`/actuator/readiness` и `healthy` у поднятой сборки (раздел «Готовность
приложения» ниже).

Порядок, когда вместе с кодом едет и схема, — expand/contract: сначала
совместимая миграция, потом накат схем арендаторов, и только потом код
(раздел «Обновление схемы клиентов» ниже).

## Что обязательно задать

| Переменная | Почему без неё нельзя |
|---|---|
| `APP_IMAGE_TAG` | Версия приложения: полный SHA коммита, образ которого опубликовал CI. Ячейка ничего не собирает — без тега `docker compose` отказывается стартовать, называя переменную. Умолчания нет намеренно: `latest` означал бы «неизвестно что» в тот день, когда надо назвать работающую версию |
| `APP_CRYPTO_KEY` | Без него нельзя завести ключ кабинета площадки. **Потеряете — ключи не расшифруются**, запрашивать их придётся заново. Копию держите отдельно от бэкапа базы: вместе они дают то же, что и хранение открытым текстом |
| `S3_PUBLIC_ENDPOINT` | Внешнее имя хранилища. Хост входит в подпись ссылки, и подписанная внутренним адресом ссылка с телефона приёмщика не откроется |
| `PUBLIC_ORIGIN` | Уходит в CORS хранилища. Телефон грузит снимок прямо туда из браузера; без CORS браузер отбивает запрос до отправки, а приложению это выглядит как обрыв связи |
| `DB_PASSWORD` | Пароль в репозитории — это пароль, который знают все |
| `APP_RUNTIME_ROLE`, `APP_DDL_*` | Без них приложение работает владельцем схем, и журналы правятся прямым SQL. Ячейка поднимется и будет работать одинаково — разница видна только в тот день, когда журнал предъявляют как доказательство |

## Секреты ячейки: что это, где лежит, что при потере

Значений здесь нет и быть не может: документация в git, а секрет, попавший
в репозиторий, остаётся там навсегда — вместе с историей, ветками и клонами.
Здесь — реестр: что за секрет, зачем он и что делать, если потерялся.

| Секрет | Зачем | Если потерять | Если утечёт |
|---|---|---|---|
| `APP_CRYPTO_KEY` | шифрует ключи кабинетов площадок (`marketplace_account.credentials`) | **невосстановимо**: ключи не расшифруются, запрашивать заново у площадки | вместе с бэкапом базы даёт ключи кабинетов открытым текстом |
| `DB_PASSWORD` (владелец схем) | миграции, провижининг, выдача прав | пароль меняется `ALTER ROLE`, данные целы | полный доступ к базе, включая правку журналов |
| `APP_RUNTIME_PASSWORD` | рабочая роль приложения | меняется `ALTER ROLE` + перезапуск | доступ к данным, но **не** к правке журналов |
| `APP_PROVISIONING_TOKEN` | заведение арендаторов и накат миграций | задаётся заново в `.env` | чужой заводит схемы, пока не кончится диск |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | доступ к хранилищу снимков | заводятся заново в MinIO | чтение и удаление всех фотографий клиентов |
| `ALERT_TELEGRAM_TOKEN_FILE` | бот, шлющий тревоги | новый бот через BotFather | чужой шлёт вам ложные тревоги |

**Где они лежат.** Все — в `.env` рядом с `docker-compose.prod.yml`, права `600`,
файл в `.gitignore`. Это рабочая копия, которую читает Docker Compose.

**Где должна лежать вторая копия.** `APP_CRYPTO_KEY` — **отдельно от бэкапа
базы**: в менеджере паролей, на другом носителе, у другого человека. Вместе они
дают то же, что хранение открытым текстом, — и это единственный секрет,
потеря которого необратима. Остальные пересоздаются за минуты.

**Чего в реестре нет намеренно.** Пароль клиента от кабинета площадки: Дром
выдаёт отдельный ключ на кабинет, и пароль нам не нужен вовсе. Разговора
«отдайте нам пароль от вашего кабинета» при подключении не будет.

**Когда заводить секрет-менеджер.** Не сейчас. При одной машине и одном
человеке `.env` с правами `600` закрывает ту же угрозу, а Vault добавляет
компонент, который надо поднимать, бэкапить и который может не ответить
в момент старта ячейки. Поводы вернуться: вторая ячейка, второй человек
с доступом, требование ротации.

## Грабли, на которые уже наступили

**Своё имя проекта у боевого compose** (`name: partsflow-cell`). Без него тома
совпадают с теми, что поднимает `docker-compose.yml` для разработки. Postgres
инициализирует пользователя только на пустом каталоге данных, поэтому боевая
ячейка либо молча поднимается на базе с dev-паролем, либо не поднимается вовсе
с «password authentication failed» — и причина этого не видна ни в одном логе.

**Хранилище доступно снаружи, но через терминатор, а не открытым портом.**
Фотография идёт в S3 мимо приложения: приёмщик делает их десятками при плохой
связи, и гонять многомегабайтные файлы через бэкенд значит занимать его потоки
на минуты. Но порт MinIO на хосте **не** публикуется — телефон грузит снимок
на `s3.<домен>`, а Caddy проксирует запрос внутрь на `minio:9000`
(`ops/Caddyfile`: `reverse_proxy minio:9000`). «Мимо приложения» — это про
бэкенд-потоки, а не про терминатор: TLS всё равно на нём, и открытого порта
у хранилища наружу нет. Порт Postgres наружу тоже не выставлен — к базе ходит
только приложение.

Раньше здесь стояло «порт хранилища выставлен наружу»: так и было, пока MinIO
публиковал `9000` на хост напрямую. Порт убрали за терминатор, а формулировка
отстала — и противоречила разделу «HTTPS» ниже. Теперь оба говорят одно:
наружу смотрит только Caddy.

## HTTPS

Терминатор — Caddy, в том же compose (`ops/Caddyfile`). Сертификаты получает
и продлевает сам: без крона и без забытого продления, о котором узнают в день,
когда у приёмщиков перестаёт открываться приложение.

**Это не гигиена, а условие работы приёмки.** Камера в браузере доступна
только в защищённом контексте: по http нет ни съёмки деталей, ни сканирования
ячеек и VIN. Половина продукта, а не замочек в адресе.

Наружу смотрит только терминатор — 80 и 443. Порты приложения и хранилища
на хосте не публикуются: открытый 8080 сводит на нет и сертификат,
и ограничение управляющего контура по адресам.

**Управляющий контур закрыт по адресам.** `/api/provisioning` — создание
арендаторов и накат миграций на все схемы ячейки — доступен только
из `PROVISIONING_ALLOW`, остальным отвечает 404: чужому незачем знать,
что он вообще существует. Умолчание — петля, то есть управление только
с самой машины.

Диапазон задавайте по тому адресу, который видит **сам терминатор**: за NAT
провайдера или чужим балансировщиком это будет их адрес, а не ваш. Смотреть
в `docker compose -f docker-compose.prod.yml logs caddy` после заведомо
отбитого запроса.

**Приложение за терминатором работает в режиме `native`** (`FORWARD_HEADERS`).
С `framework` флаг `Secure` получает только CSRF-cookie: фильтр Spring
оборачивает запрос выше уровня, на котором Tomcat создаёт `JSESSIONID`.
Проверено живым прогоном, не выведено из документации.

## Обновление схемы клиентов

Схемы арендаторов **не мигрируют при старте приложения** — пятьсот схем
на подъёме это минуты недоступности всей ячейки, и падение одной миграции
не дало бы подняться остальным клиентам. Их приводит к версии образа
отдельный шаг — **одноразовый контейнер того же образа**, который ничего
не обслуживает и завершается кодом возврата:

```bash
APP_IMAGE_TAG_GREEN=<новый SHA> ops/schema-sync.sh          # кто не на версии образа; ненулевой код, если есть
APP_IMAGE_TAG_GREEN=<новый SHA> ops/schema-sync.sh --apply  # привести к версии образа
```

**Сборка берётся та, которую выкладывают, — то есть НЕ та, что под трафиком.**
Имя активной шаг спрашивает у `ops/switch-build.sh --current` (единственное
место, где оно записано) и берёт вторую; назвать её можно и явно —
`ops/schema-sync.sh --apply green`. Это противоположно `ops/migrate-tenants.sh`,
и намеренно: тот разговаривает с работающим приложением, а здесь нужен
changelog **нового** артефакта. Взяв сборку под трафиком, шаг накатил бы
changeset'ы прежней версии, то есть молча не сделал бы ничего. Поэтому перед
запуском он печатает, какую сборку и какой образ взял, — прочитать эти две
строки дешевле, чем разбирать потом, почему схема не двинулась.

**Почему контейнер, а не запрос к работающему приложению.** Changelog лежит
**внутри jar**: накатить новые changeset'ы может только новый артефакт — то
есть тот, который уже подменил работающий. Прежний шаг
(`ops/migrate-tenants.sh`, `POST /api/provisioning/migrations`) стучится
в работающее приложение, и из этого следовало, что **записанный ниже порядок
выполнить было нельзя**: он требует сначала схему, потом код, а одним
артефактом получалось наоборот. Между шагами оставалось окно, в котором новый
код работает на старых схемах. На 12 сентября 2026 боевая ячейка отставала
на девять changeset'ов (058–066), и выкладка означала такое окно на минуту-две:
журнал входов, память витрины, срок резерва и номер позиции опираются
на `login_session`, `member_setting`, `company_setting` и `part.number`.
Теперь миграцию гонит контейнер нового образа рядом с работающей старой
сборкой — и окна нет.

**Порядок выкладки важнее самого скрипта.** Expand/contract, и теперь он
выполним:

1. **слепок** — `ops/backup.sh`, до наката;
2. миграция, совместимая со старым кодом (добавить колонку, не удалять и
   не переименовывать) — в образе с новым SHA;
3. `APP_IMAGE_TAG_GREEN=<новый SHA> ops/schema-sync.sh --apply`;
4. проверка без `--apply`: код возврата ноль;
5. и только теперь поднять саму сборку тем же тегом — код, который на новую
   схему рассчитывает (раздел «Переключение трафика» ниже, шаги 2–5).

**Тег в шагах 3 и 5 обязан быть один и тот же.** Одноразовый контейнер берёт
changelog из образа, и разойдись эти два тега — схему привели бы к версии
одного артефакта, а людей обслуживал бы другой, то есть получилась бы ровно
та пара «код одной версии, база другой», ради которой всё написано.
Проверяется это не памятью: шаг печатает образ, которым запустился, а после
подъёма сборки `ops/schema-sync.sh` без `--apply` обязан ответить нулём.

**С задачи 0112 копию делает сама выкладка** (`ops/deploy.sh`, раздел
«База едет вместе со сборкой»): схема накатывается на копию, а прежняя база
остаётся нетронутой до точки невозврата. Порядок ниже — для выкладки руками,
на общей базе. **Первый шаг там — шаг самой выкладки, а не дело перед ней.**
Слепок, снятый до наката, парен прежней сборке, и он единственное, чем тогда
возвращают схему вниз (раздел «Откат вниз» ниже). Снятый после наката, он пареному
не равен — а снятый «когда вспомнили» не равен ничему: ночной дамп трёхчасовой
давности означает потерянную смену. Поэтому он стоит в списке номером, а не
в голове у выкладывающего.

**Версия — это число changeset'ов набора арендатора**, то же, что в отметке
`tenant_registry.schema_version` и в `./db/rollback-cost.py`. Без `--to` целью
берётся версия самого образа: пара «код и схема» получается свойством
построения, а не внимательностью выкладывающего.

**Приводит, а не накатывает — и это решение владельца от 12 сентября 2026:**
«не должно быть такого, чтобы версия приложения была 100, а база
соответствовала версии 103». Схему **выше** цели шаг опускает, а не
пропускает молча:

```bash
APP_IMAGE_TAG_GREEN=<SHA той сборки> ops/schema-sync.sh --apply --to 132
```

**Чего образ не может — снять changeset'ы, которых в нём нет.** Тело
`--rollback` лежит в файле самого changeset'а, то есть в чужом jar;
`rollbackCount` таких changeset'ов не видит вовсе и снял бы вместо них
последние **свои** — то есть не те. Поэтому схема, побывавшая под более
новой сборкой, называется по имени вместе с лишними changeset'ами и
**не трогается**, а код возврата ненулевой. Опускает её образ той сборки,
которая эти changeset'ы завела, — её тегом и с `--to`. **В путь кнопки это
больше не входит** (задача 0112): откат выкладки — прежний образ на той же,
более новой базе. Опустить схему образом ветки — инструмент стенда, когда
ветку с несовместимой миграцией надо убрать совсем; на ПРОМ — слепком
(раздел ниже).

Отсюда и четыре сочетания, которые на стенде теперь выразимы:

| Код | Схемы | Как получить |
|---|---|---|
| новый | накатить | шаг новым тегом, затем поднять сборку тем же тегом |
| новый | не трогать | поднять сборку, не запуская шаг: репетиция окна, которое иначе видно только на живом клиенте |
| прежний | накатить | шаг новым тегом, сборку оставить прежнюю |
| прежний | не трогать | вернуть трафик на прежнюю сборку (`ops/switch-build.sh blue`) |

Сорвавшийся арендатор не останавливает остальных: схемы независимы, и отказ
на седьмом клиенте не повод оставить пятьсот на старой версии. Сорвавшиеся
называются по имени с причиной, шаг при этом падает ненулевым кодом — релиз,
оставивший клиента не на той схеме, обязан быть заметен сразу, а не на его
первом запросе.

Повторный запуск дешёв и безопасен: своего журнала прохода нет, состояние
каждого арендатора лежит в его же `DATABASECHANGELOG`. Продолжение после
сбоя — это просто повторный запуск.

**Общая схема ячейки (`catalog` и `public`) идёт первой и без замка**, потому
что сам замок (`public.shedlock`) заводит она же. Дальше проход по арендаторам
берёт тот же замок `tenant-migrations`, что и эндпоинт работающего приложения:
два прохода по одной схеме её и ломают.

**Что считается истиной.** `schema_version` в реестре — быстрый индикатор
для дашборда, а не истина: он врёт, если в схему лазили руками. И накат,
и проверка спрашивают сам Liquibase — сколько changeset'ов набора на схеме
есть, сколько нет и что лежит сверх набора; отметку только обновляют.
Проверено живым прогоном на трёх арендаторах: у одного таблица снесена
руками — шаг назвал именно его и домигрировал двух остальных.

**Прежний путь остался и не отменён.** `ops/migrate-tenants.sh` и
`GET|POST /api/provisioning/migrations` работают как раньше — ими удобно
спросить «кто отстал» у уже работающей ячейки, не поднимая контейнера,
и они же единственный путь, когда образа под рукой нет. Чего они не умеют —
накатить то, чего нет в работающем приложении, и опустить схему вниз.

**Секрет — в заголовке `X-Provisioning-Token`,** не в адресе: адреса пишут
access-лог терминатора, логи промежуточных прокси и история. Скрипт передаёт
его curl'у файлом, а не аргументом: аргументы видит в `ps` любой, у кого есть
учётка на машине. Одноразовому контейнеру секрет не нужен вовсе — он ходит
в базу напрямую подключением владельца схем, а не через HTTP.

Сами эндпоинты стоят вне аутентификации (`permitAll`), их защищает только
секрет — поэтому `/api/provisioning` стоит закрыть на терминаторе
по адресам, а не полагаться на один ключ.

Порядок подключения клиента — от пустой ячейки до первой позиции на Дроме —
в `docs/onboarding.md`. Здесь про то, как поднять ячейку; там про то,
что делать в день, когда клиент рядом.

## Откат вниз: слепком, а не миграцией

> **С задачи 0112 это не путь отката выкладки.** Откатывается только
> приложение — `ops/deploy.sh --tag <прежний SHA> --migrate-with none`, —
> а база остаётся новее и чинится вперёд (раздел «База едет вместе
> со сборкой»). Всё ниже — инструменты **стендов и аварий**: опустить
> схему на ИФТ, вернуть клиента из слепка после порчи данных. Цену они
> по-прежнему обязаны печатать до нажатия.

Схему можно вернуть вниз двумя способами, и на ПРОМ годится **только один**.

```bash
./db/rollback-cost.py --from 138 --to 132    # чем откат обойдётся, ДО отката
```

**Сначала прочитайте цену.** Структурно верный откат теряет данные молча:
откат `064-part-number` снимает порядковые номера позиций, повторный накат
раздаёт их заново — и если между откатом и накатом удалена хоть одна позиция,
номера сдвинутся. «Посмотри позицию 347» станет другой деталью, а схема при
этом цела: колонка на месте, тип тот же, индекс тот же. Проверено живым
прогоном: три позиции, удалена вторая, «Бампер передний» вернулся с номером 2
вместо 3. Тем же прогоном проверено и второе: срок резерва, выставленный
владельцем в 7 дней, после отката `066` и повторного наката стал **три дня** —
внешне всё цело, настройка клиента молча заменена.

Цену печатает не память человека, а `db/rollback-cost.py`: каждый changeset,
чей откат делает `DROP TABLE`, `DROP COLUMN`, `DELETE` или `UPDATE`, обязан
нести пометку `--rollback-теряет` рядом со своим `--rollback`, и без неё
не проходит CI.

**На ИФТ и ПСИ откат вниз делается миграцией** — `liquibase rollback-count`,
его и проверяет `db/verify-rollback.py`. Потерянные там номера — пустяк.
Гоняет его тот же шаг, что и накат: `ops/schema-sync.sh --apply --to 132`
образом сборки, которая эти changeset'ы завела (снять чужие она не может —
раздел «Обновление схемы клиентов» выше).

**На ПРОМ откат вниз делается возвратом парного слепка плюс прежним SHA.**
Не потому, что миграция плоха, а потому, что цена разная: на живом клиенте
это склад, где детали назвали новыми числами, пока продавец говорил
с покупателем по телефону. Прежний SHA — это `APP_IMAGE_TAG` в `.env`
и те же `pull` с `up -d` (раздел «Новая версия» выше).

```bash
ops/restore-cell.sh <каталог-набора>              # ячейку целиком
ops/restore-tenant.sh t_000042 <каталог-набора>   # одного клиента
```

Оба разворачивают **в пустую** схему и спрашивают подтверждение: всё, что
появилось после снятия набора, будет потеряно. Это не предосторожность
сверх меры, а ровно тот вопрос, на который отвечает абзац ниже.

### Откат слепком безопасен только в узком окне

Это правило не выводится из механики, поэтому записано здесь.

Парный слепок снят **до** наката. Возврат к нему через пять минут после
выкладки стоит пяти минут работы. Возврат к нему на следующий день стоит
**суток работы клиента**: принятых деталей, проданных позиций, принятых денег,
выданного товара.

Значит откат слепком — инструмент первых минут, а не способ отменить релиз.
**Обнаружили поломку через день — чинить вперёд:** новая выкладка
с исправлением, слепок не трогать. Где проходит граница, решает не механика,
а объём работы, который клиент успел сделать.

Поэтому **шаг отката обязан назвать возраст слепка и сколько с тех пор
записано**, а не молча разворачивать. Возраст — по `ops/backup.sh`
(отметка `partsflow_backup_success_timestamp_seconds` и время каталога набора),
работа — запросом по схеме клиента:

```sql
-- :snapshot — момент снятия слепка; у платежа своя колонка времени (paid_at),
-- и подставленная не та даёт ноль там, где работы полная смена
SELECT (SELECT count(*) FROM t_000042.deal           WHERE created_at > :'snapshot') AS сделок,
       (SELECT count(*) FROM t_000042.payment        WHERE paid_at    > :'snapshot') AS платежей,
       (SELECT count(*) FROM t_000042.stock_movement WHERE created_at > :'snapshot') AS движений;
```

```bash
docker compose -f docker-compose.prod.yml exec -T postgres \
    psql -U app -d "$(ops/switch-build.sh --current-db)" -v snapshot='2026-09-13 03:00:00+07' -f - <<'SQL'
…запрос выше…
SQL
```

Ноль по всем трём — возврат стоит ровно ничего. Двузначные числа — это
работа смены, и её вернуть будет нечем: решение принимает человек, а не
скрипт. Точка возврата при этом сама по себе слабее, чем кажется: между
базовой копией и последним сегментом WAL может быть до пяти минут («Точка
возврата: архив WAL» ниже).

## Готовность приложения: чем проверяется «встало штатно»

Порядок выкладки (решение владельца от 12 сентября 2026) ставит третьим
шагом «само приложение встало штатно, всё в порядке — и только тогда можно
убирать старую сборку». Проверяется это машинно:

```bash
docker compose -f docker-compose.prod.yml exec caddy \
    wget -qO- "http://$(ops/switch-build.sh --current):8080/actuator/readiness"
```

Ответ — `{"ready":true|false,"checks":[…]}` и код 200 либо 503, чтобы шагу
выкладки хватило `curl -f`. Готовность складывается из пяти ответов:

| Проверка | Что означает «нет» |
|---|---|
| `database` | база не отвечает рабочей ролью |
| `catalog` | общая схема ячейки принята не целиком — её накат идёт при старте и ещё не закончился (либо не может закончиться) |
| `schemas` | схемы арендаторов **позади** версии этой сборки — площадка заберёт пустой прайс |
| `journals` | приложение работает владельцем схем (журналы изменяемы) либо рабочей роли не выдали прав вовсе |
| `metrics` | `/actuator/prometheus` не отображён: собирать нечего, тревоги ячейки молчат |

То же самое видно в `docker compose ps`: healthcheck на этот адрес стоит
у обеих сборок (`app-blue`, `app-green`), и шаг выкладки ждёт `healthy`
от той, которую поднял.

**Схема впереди — это норма, схема позади — нет.** Накат идёт до подъёма
новой сборки, и всё это время людей обслуживает старая: её схема к этой
минуте уже впереди. Считай готовность равенством версий — старая сборка
объявила бы себя негодной ровно тогда, когда обязана работать. Равенство
проверяет шаг выкладки у новой сборки, а не сборка о себе: это разные
утверждения — «я могу обслуживать» и «эта пара кода и схемы та, которую
выкладывают».

**Наружу адрес не смотрит** и смотреть не должен: терминатор отдаёт
на `/actuator` 404, порт приложения не публикуется. Учётной записи он
не спрашивает — у docker'а и у шага выкладки её нет, как и у сборщика
метрик.

**Отдельной проверки «контекст поднялся» в списке нет намеренно.** Этот
адрес отвечает только после обновления контекста — Tomcat поднимается в самом
его конце, — то есть сам ответ и есть доказательство. Флаг «все стартовые
шаги отработали» в первой редакции был, но оказался и ненадёжным в прогоне,
и обещающим больше правды: порядок `ApplicationRunner`'ов между собой
не задан. Окно, ради которого он стоял (накат общей схемы `catalog` идёт
runner'ом), закрыто по существу — без реестра арендаторов проверка `schemas`
отвечает «версии не проверены». Остаётся узкое место, названное прямо:
при перезапуске, когда реестр уже есть, а новому changeset'у общей схемы
накатиться ещё нужно, готовность ответит «готов» на несколько секунд раньше
правды.

**`/actuator/health` — другая поверхность и мягче.** Там контекст и база,
то есть живость; им проверяет себя образ, и он обязан оставаться зелёным
в разработке, где одна роль законна, а схема между накатами отстаёт.
Отставшие схемы и незащищённые журналы запуск не валят — «не готов
к выкладке» и «не запускаться» разные вещи.

## Переключение трафика: синяя и зелёная сборки

Порядок владельца требует, чтобы **старая сборка гасла последней**: новая
поднимается рядом, доказывает готовность, получает трафик — и только потом
старую убирают. Тогда неудачная версия не оставляет людей без приложения,
а возврат стоит секунды, потому что старая ещё работает.

Сборок поэтому две — `app-blue` и `app-green`, — и отличаются они ровно
двумя вещами: именем и тегом образа. Какие работают, говорит
`COMPOSE_PROFILES` в `.env` (без строки — синяя, прежняя: задача 0110);
какая **под трафиком** — записано
в `ops/active-build.caddy`, и это единственное место, где стоит её имя
(его же читают `ops/migrate-tenants.sh`, `ops/schema-sync.sh` и сам
`ops/switch-build.sh --current`). Первые двое читают его по-разному
и намеренно: накат по HTTP идёт в сборку **под трафиком**, а одноразовый
контейнер схем — образом той, которую **выкладывают**.

**Всё, что ниже, делает одна кнопка** — форма в браузере с выбором стенда,
ветки, миграций и данных: `docs/deploy-button.md` (задача 0075). Она же
гоняет пять самопроверок после переключения. **И с задачи 0112 она делает
больше, чем шаги ниже: база едет вместе со сборкой** — раздел «База едет
вместе со сборкой» следом. Шаги ниже работают на одной общей базе; руками
по ним выкладывают только версию старше самой кнопки, и тогда
«всё новое или ничего» не выполняется — схема общая, старая сборка работает
на уже накатанной.

### База едет вместе со сборкой: копия и заморозка записи

Решение владельца от 14 сентября 2026, дословно: «база всегда соответствует
сборке которая едет на деплой, а если что то пошло не так то всё
откатывается. То есть у нас должна быть атомарность по принципу всё катим
новое или ничего». Уточнение того же дня: **откатывается только приложение,
база чинится вперёд** (`tasks/0112-baza-edet-vmeste-so-sborkoy.md`).

**Перед любой из этих команд идёт шаг 0** — «Выкладка по шагам» ниже:
настройки ячейки приводятся к тому же SHA, что и образ. `ops/deploy.sh`
берёт `ops/` и `docker-compose.prod.yml` **из рабочего дерева машины**,
а не из образа, и на дереве, оставшемся от `git pull`, выложил бы код одной
версии с настройками другой (задача 0111). Сам скрипт этого не проверяет:
он первым делом зовёт `ops/config-guard.sh`, а тот отвечает на вопрос
«файлы на месте», не на вопрос «той ли они версии».

```bash
ops/deploy.sh --tag <SHA>                              # выкладка
ops/deploy.sh --tag <прежний SHA> --migrate-with none  # откат приложения
ops/deploy.sh --abort                                  # доделать оборвавшуюся
ops/deploy.sh --drop-previous                          # убрать прежнюю базу, когда её сменщицу забэкапили
ops/deploy.sh --tag <SHA> --dry-run                    # шаги, ничего не трогая
```

Порядок, и каждый шаг проверяется самопроверкой `ops/deploy.sh --selftest`
по плану `--dry-run`:

1. **До единого изменения**: образ в реестре, место под копию, не снимается ли
   сейчас дамп, нет ли у ролей своей настройки `default_transaction_read_only`
   (она старше настройки базы и отменила бы заморозку). Прежнюю базу
   выкладываемой сборки — слепок прошлой выкладки — здесь **не трогают**:
   она удаляется последним шагом и с условием (пункт 10).
2. **Заморозить запись** в базе работающей сборки: `ALTER DATABASE … SET
   default_transaction_read_only = on` и обрыв соединений, открытых раньше.
   Результат проверяется попыткой, а не верой команде.
3. **Снять копию**: `CREATE DATABASE parts_<сборка>_<SHA> TEMPLATE …
   STRATEGY FILE_COPY`, с переносом прав на базу. Источник на эти секунды
   закрыт для соединений — шаблон этого требует.
4. **Привести схему копии** образом выкладываемой сборки
   (`ops/schema-sync.sh`); имя базы сборки уже записано в `.env`.
5. **Поднять новую сборку рядом — уже на копии** и дождаться `healthy`:
   по умолчанию **две минуты** (`DEPLOY_HEALTH_WAIT`). Всё это время запись
   заморожена, и неудачная выкладка держит её замороженной до самого отказа —
   поэтому решением владельца от 15 сентября 2026 ожидание сокращено с пяти
   минут до двух: ложный отказ стоит одной повторной выкладки, долгая
   заморозка стоит продаж. Точное число даст замер на ПСИ.
6. **Заморозить и копию**: до точки невозврата в неё не должна лечь ни одна
   запись людей — упади самопроверки, её удалят.
7. **Перевести трафик**, 8. **пять самопроверок**.
9. **Точка невозврата**: открыть запись в копии, погасить старую сборку,
   перенести тег ячейки.
10. **Прежняя база прошлой выкладки** — удалить, но только если по сменившей
    её базе уже снялся бэкап (абзац ниже). Не снялся — база остаётся, и шаг
    говорит об этом словами.

**Упавший шаг 2–8 возвращает всё**: трафик на старую сборку (с
принуждением), новую гасит, копию удаляет, прежнюю базу выкладываемой сборки
возвращает в `.env`, профили — на одну сборку, запись в старой базе
открывает. Старая база за это время не менялась вовсе. Оборвалась сама
выкладка — `ops/deploy.sh --abort` доделывает откат по метке `DEPLOY_COPY_*`
в `.env`; пока метка стоит, новая выкладка не начинается.

**Имя базы каждой сборки живёт в `.env`** (`APP_DB_BLUE`, `APP_DB_GREEN`;
незаданное — `parts`), ведёт его выкладка, а спрашивают его у
`ops/switch-build.sh --db <сборка>` и `--current-db` — так же, как его читает
compose. Бэкап, проверка бэкапа, возврат клиента, возврат ячейки и заведение
ролей берут базу сборки под трафиком оттуда же: литерал `parts` после первой
выкладки копией — это замороженная прежняя база, и бэкап с неё отчитывался бы
успехом каждую ночь.

**Прежняя база остаётся замороженной, пока по сменившей её базе не снялся
бэкап** — решение владельца продукта от 15 сентября 2026 (`tasks/0117`).
Это слепок на момент переключения — инструмент первых минут, а не способ
отменить релиз: всё записанное после переключения живёт только в новой.
Удалять её сразу нельзя по другой причине: до первого бэкапа новой базы
слепок — единственная полная копия данных на момент выкладки, снятая вне
архива WAL. Поэтому условие **спрашивается у отметок бэкапа**, а не
подразумевается: выкладка (и `ops/deploy.sh --drop-previous` между
выкладками) ищет в pushgateway отметку ночного дампа **с именем этой базы**
(`partsflow_backup_success_timestamp_seconds{db="…"}`, её кладёт
`ops/backup.sh`) и отметку базовой копии свежее него. Нет хотя бы одной —
база остаётся, и шаг говорит, чего именно не хватает.

Цена этого названа вслух: базовая копия снимается **раз в неделю**
(`ops/install-cron.sh`), значит на спокойной ячейке слепок живёт до неё,
и всё это время база на диске занимает вдвое больше. Место считается
в задаче 0089; снимать базовую копию шагом выкладки — отдельный вопрос
владельцу, здесь он не решался.

**Удалить её потом, ничего не выкладывая:**

```bash
ops/deploy.sh --drop-previous     # то же условие; идёт выкладка — откажется
```

В cron эта команда не поставлена: расписание ячейки — решение оператора,
и лишняя ночная задача, удаляющая базы, заводится с открытыми глазами.

**Прежняя сборка на ней поднимется — но только на чтение** (задача 0122).
До 18 сентября 2026 она не поднималась вовсе: накат общей схемы при старте
выдаёт права, на замороженной базе это 25006, и контейнер уходил в круг
перезапусков. Это было опасно в другом месте — перезапустись **работающая**
сборка посреди выкладки, ячейка закрылась бы целиком, включая чтение, —
и теперь такой отказ пропускается с `WARN`. Обратная сторона названа вслух:
сборка, поднятая на прежней замороженной базе, работает и показывает
**вчерашний склад**. Вернуться к прежней базе — по-прежнему сознательно её
разморозить (`ALTER DATABASE … RESET default_transaction_read_only`),
понимая, что всё записанное после переключения там отсутствует; трафик
туда сам не уйдёт — `ops/switch-build.sh` на замороженную базу не переводит
и спрашивает об этом саму базу, а не приложение.

**Kafka и копия вместе не проверены**, и выкладка на ячейке с
`SPRING_PROFILES=kafka` останавливается до единого изменения: офсеты
потребителей живут в брокере, и событие, прочитанное сборкой на копии, при
откате стало бы для старой базы прочитанным, но не обработанным.

### Первое обновление боевой ячейки: в нерабочее время и с предупреждением клиента

Решение владельца продукта от 15 сентября 2026 (`tasks/0117`): **первую
выкладку копией на боевой ячейке делают в нерабочее время и предупредив
клиента заранее.**

Почему первая особенная. На ячейке сейчас стоит сборка, которая про заморозку
записи **не знает**: её код старше задачи 0112. Пока идёт выкладка, запись
в базе заморожена, и такая сборка отвечает на попытку записи «Внутренняя
ошибка», а не «Идёт обновление, подождите…». Около полуминуты продавец видит
поломку там, где на самом деле идёт обновление. **Данные при этом целы** —
заморожена база, а не приложение, — и офлайн-очередь приёмки повторяет сама.
Со второй выкладки обе сборки про заморозку уже знают, и человек видит
понятные слова; особенная здесь ровно одна выкладка.

Поэтому:

1. время — **нерабочее**: у разборки это вечер после закрытия или выходной,
   а не обеденный перерыв;
2. клиента предупредить **заранее**, а не в минуту выкладки: «с 21:00 около
   минуты система не будет принимать записи; если увидите ошибку — повторите
   через минуту, ничего не потеряется»;
3. дальше обычная выкладка: `ops/deploy.sh --tag <SHA>` или кнопка.

Сама выкладка про это напоминает: увидев, что обе сборки смотрят в одну базу
(то есть копией здесь ещё не выкладывали), она печатает шаг «Первая выкладка
копией на этой ячейке» с этим же предупреждением. Останавливать выкладку
она при этом не станет — время выбирает человек, а не скрипт.

**Ячейку старого образца — ту, где `.env` ещё без `COMPOSE_PROFILES` и без
имён баз сборок, — перед этим надо привести к нынешнему виду.** Порядок
такого перевода руками здесь не расписан намеренно: он идёт отдельной
задачей (`tasks/0114`), а выдуманный порядок хуже отсутствующего.

### Выкладка по шагам — без копии, для версии старше кнопки

```bash
C="docker compose -f docker-compose.prod.yml"
ops/switch-build.sh                       # кто сейчас под трафиком, скажем app-blue

# 0. НАСТРОЙКИ — тем же SHA, что и образ. Не `git pull`: он тянет свежий main,
#    и тогда код одной версии, а конфигурация терминатора другой (задача 0111)
git fetch --no-tags origin main
git checkout --detach <новый SHA>
ops/config-guard.sh                       # настройки на месте — файл, а не каталог
git rev-parse HEAD                        # обязан совпасть с APP_IMAGE_TAG в .env

# 1. схема — до подъёма новой сборки (expand/contract), образом НОВОЙ сборки:
#    changelog лежит внутри jar, и накатить новые changeset'ы может только он
APP_IMAGE_TAG_GREEN=<новый SHA> ops/schema-sync.sh --apply

# 2. новая сборка РЯДОМ, своим тегом; старая продолжает обслуживать людей
COMPOSE_PROFILES=blue,green APP_IMAGE_TAG_GREEN=<новый SHA> $C up -d app-green

# 3. дождаться готовности — это healthcheck, а не «порт отвечает»
$C ps                                     # app-green: healthy

# 4. перевести трафик: caddy reload, без перезапуска терминатора
ops/switch-build.sh green

# 5. проверить живьём — и только теперь гасить старую
$C stop app-blue
```

После успеха перенесите новый SHA в `APP_IMAGE_TAG` и уберите
`APP_IMAGE_TAG_GREEN`, а в `COMPOSE_PROFILES` оставьте одну сборку. Пока
этого не сделано, `.env` описывает состояние выкладки, а не ячейки.

**Шаг 0 оставляет машину на отцепленном `HEAD`, и это свойство, а не
неряшливость.** `git rev-parse HEAD` на машине отвечает «какой версии здесь
настройки», и ответ обязан совпадать с `APP_IMAGE_TAG` в `.env` — то есть
пара «код и настройки» стала проверяемой одной командой, а не памятью
выкладывающего. Заодно прежняя привычка не возвращается молча: `git pull`
на такой машине отказывает словами «You are not currently on a branch».

**`ops/active-build.caddy` git трогать не должен — это состояние ячейки,
а не настройка.** Кнопка исключает его из `rsync` ровно поэтому; у ручного
пути то же место тонкое, и ведёт он себя так (проверено репетицией):

- **обычный случай** — между версией на машине и выкладываемой этот файл
  не менялся. `git checkout` его не трогает вовсе: местная правка остаётся,
  **inode тот же**, терминатор продолжает видеть свой файл. Это и есть
  случай пилота;
- **редкий случай** — какой-то коммит между версиями правил этот файл
  (шапку переписывали 0079 и 0112). Тогда `git checkout` **отказывается
  до единого изменения**: «Your local changes to the following files would
  be overwritten by checkout». Ничего не сделано, выкладка не начата.

Почему местная правка там есть всегда: `ops/switch-build.sh` переписывает
файл, оставляя короткую шапку в три строки вместо девятнадцати
из репозитория, — то есть на любой ячейке, где хоть раз переводили трафик,
файл локально правлен. **По той же причине `git pull` на боевой машине
не просто тянул лишнее, а отказывал** тем же сообщением про merge: команда,
стоявшая в этом документе, на такой ячейке не отрабатывала вовсе.

Редкий случай разводят так — и у этого есть цена, которую надо знать:

```bash
cat ops/active-build.caddy > ~/active-build.caddy.bak   # запомнить состояние
git checkout -- ops/active-build.caddy                  # снять местную правку
git checkout --detach <новый SHA>
cat ~/active-build.caddy.bak > ops/active-build.caddy   # вернуть состояние
$C up -d caddy                                          # ОБЯЗАТЕЛЬНО, см. ниже
```

**Цена — пересоздание терминатора.** `git checkout` записывает файл заново,
то есть подменяет inode, а `ops/active-build.caddy` смонтирован в Caddy
**отдельным файлом**: контейнер держит прежний inode и новое содержимое
уже не увидит — `caddy reload` перечитал бы старое при верном файле
на хосте. Поэтому после этой развилки терминатор пересоздают (`up -d caddy`,
не `restart`), иначе следующее `ops/switch-build.sh` «пройдёт» и не
случится. Возврат делается `cat > файл`, а не `cp`: на macOS `cp` inode
меняет — замерено, — и привычка писать `cp` однажды приедет на сервер.

**`.env` и `ops/secrets/` шаг 0 не трогает**: оба в `.gitignore`, git о них
не знает. Секреты машины переезду не подлежат — это то же исключение, что
у `rsync` кнопки.

**Шаг 1 делает одноразовый контейнер, а не работающее приложение** (задача
0073). `ops/migrate-tenants.sh` стучится в сборку под трафиком — то есть
накатывает changeset'ы **прежней** версии, которых в ней и нет: changelog
лежит внутри jar. Поэтому шаг схемы берёт образ выкладываемой сборки тем же
тегом, что и шаг 2, ничего не обслуживая и не занимая порт. Прежний скрипт
не отменён и остаётся тем, чем удобно спросить «кто отстал» у работающей
ячейки, — подробности в разделе «Обновление схемы клиентов» выше.

**Откат — шаг 4 в обратную сторону**, пока старая сборка жива:
`ops/switch-build.sh blue`. Это секунды и ни одного обращения к реестру.
Погасили старую и обнаружили беду позже — поднимайте её прежним тегом
и переключайтесь: дороже на время подъёма, но образ из реестра никуда
не делся.

### На уже работающей ячейке: шага руками нет

Сервис `app` заменён на `app-blue` и `app-green`, и оба стоят под профилями
compose. `.env`, написанный до этого, про профили не знает — и **обычный
`docker compose -f docker-compose.prod.yml up -d` поднимает синюю сборку**,
ту же, что работала раньше; `ops/active-build.caddy` из репозитория уже
указывает на неё. Дописывать в `.env` ничего не нужно.

С 13 по 18 сентября 2026 это было не так: без строки `COMPOSE_PROFILES`
не поднималось **ни одной** сборки — терминатор вставал, а приложения за ним
не было, 502 всем. Забывал строку тот, кто обновлялся **по инструкции**,
написанной до появления двух сборок, и узнавал об этом в ту минуту, когда
приложение уже погашено. Решение владельца от 18 сентября 2026: нет строки
про сборки — поднимать прежнюю версию, как было (задача 0110).

Строка в `.env` осталась, и нужна она ровно для одного — **переключаться**:

```
COMPOSE_PROFILES=blue,green   # на время выкладки работают обе
COMPOSE_PROFILES=green        # после неё — та, что осталась под трафиком
```

Ведёт её `ops/deploy.sh` сам; руками её задают только при выкладке по шагам.
Названный профиль погашенную сборку **не воскрешает** — ради этого профили
и заводились, и обе стороны стережёт `ops/builds-guard.sh` шагом CI.

### Чего переключатель не сделает

**Не переведёт трафик на неготовую сборку.** `ops/switch-build.sh` сперва
спрашивает у цели `/actuator/readiness` и при `ready:false` не трогает
ни файла, ни терминатора: печатает, чего именно не хватает, и выходит
с ненулевым кодом — трафик остаётся на старой, а шаг выкладки краснеет.
Проверено на ячейке: зелёная сборка, поднятая владельцем схем вместо
рабочей роли (то есть с изменяемыми журналами), переключения не получила.

**Не перезапустит терминатор.** `caddy reload` перечитывает конфигурацию
в том же процессе; контейнер держит сертификаты, и его перезапуск в разгар
неудачной выкладки — это лишний шанс упереться в недельный предел
Let's Encrypt на выпуск.

**И честно про соединения — замерено, а не выведено.** Ответ, начатый
до переключения, **дочитывается целиком** (500 КБ тянули через момент
reload дважды — обрыва нет). А вот простаивающее keep-alive соединение
терминатор закрывает, и закрывает без `Connection: close`: клиент, пославший
в него запрос в ту же миллисекунду, получает сетевую ошибку и переоткрывает
соединение. Замер: 180 запросов подряд, ровно один такой на переключение,
в обе стороны; без переключения — ноль на 182. Для браузера это обычный
повтор, для офлайн-очереди приёмки — временная ошибка, которую она и так
повторяет. Перезапуск контейнера вместо reload стоил бы того же самого
плюс секунды полного простоя.

### Память: предел ставится контейнеру, а не аргументом JVM

Образ считает кучу от предела контейнера (`-XX:MaxRAMPercentage=70`), а
предела не было вовсе: JVM видела всю машину и брала 70 % от неё. Одной
сборке это сходило с рук, двум рядом — нет. Теперь у каждой
`mem_limit: ${APP_MEM_LIMIT:-2g}`, и второго способа задать то же самое
(`-Xmx` в аргументах) нет намеренно.

Замерено на ячейке прогона с двумя работающими сборками: предел кучи,
который посчитала JVM, — **1434 МБ** (70 % от 2 ГиБ, то есть предел
доезжает); занято кучи 87 и 145 МБ; RSS контейнеров 446 и 506 МБ, то есть
**около 950 МБ на две сборки**. Четырёхкратный запас взят под то, чего
в прогоне не было: переезд клиента (снимки пачками по двести) и сборка
прайса на 35 тысяч позиций.

## Сколько держит ячейка

Замерено пробой на 500 арендаторах (август 2026): один крупный клиент
с полной выгрузкой на 37 585 позиций, остальные по 3 000. Итого 1,56 млн
позиций, 22 582 таблицы, 116 295 объектов с индексами, база 7,3 ГБ.

| Что | Результат |
|---|---|
| Провижининг одного арендатора | 1,0–1,4 с |
| Накат миграций по всем 500 схемам | 34 с |
| Проверка перед выкладкой (`deep=true`) | 40 с |
| Дамп одного арендатора при полной базе | 3–4 с |
| Дамп всей ячейки | 51 с, 148 МБ |
| `VACUUM ANALYZE` всей базы | 100 с |
| Старт приложения | 9 с |
| Холостой обход релея по 500 схемам | ~120 мс |
| Планирование запроса при 22 582 таблицах | 7,5 мс |

**Число схем само по себе почти ничего не стоит.** Планировщик от 22 тысяч
таблиц не деградирует (7,5 мс против 19,8 мс на базе из 217 таблиц с холодным
кэшем), приложение стартует за девять секунд, обход релея — доли секунды.

**Упирается ячейка в память под рабочий набор.** При 199 арендаторах и базе
в 2 ГБ нагрузка в 32 потока давала 261 запрос в секунду; при 500 арендаторах
и базе в 7,3 ГБ — 172 запроса. Причина не в схемах: рабочий набор четырёх
активных клиентов вырос до 716 МБ при `shared_buffers` в 512 МБ, попадания
в кэш упали до 98,6 %. Значит правило простое: **`shared_buffers` должен
вмещать данные тех клиентов, кто работает одновременно**, а не всю базу.

**Две настройки обязательны, и без них ячейка на сотни клиентов ломается
не сразу, а в день аварии:**

- `shm_size: 1gb` у контейнера Postgres. Умолчание Docker — 64 МБ, и обход
  системного каталога параллельными воркерами падает с «could not resize
  shared memory segment».
- `max_locks_per_transaction=512`. Транзакция, трогающая всю базу, берёт
  блокировку на каждый объект: при 116 295 объектах умолчания в 64 не хватает,
  и `pg_dump` ячейки целиком падает с «out of shared memory». Дамп по одному
  арендатору при этом работает — ломается ровно то, чем ячейку восстанавливают
  после потери диска.

Обе прописаны в `docker-compose.prod.yml`.

## Вторая ячейка

Ячейка — это самостоятельный комплект: своя база, своё хранилище, свой сбор
метрик, свой реестр арендаторов. Общего между ячейками нет ничего, и в этом
весь смысл: авария одной не касается второй.

Поднимается она тем же compose с другим `.env`:

```bash
APP_CELL=cell02
APP_CELL_NUMBER=2
APP_DOMAIN=cell02.example.ru
S3_DOMAIN=s3.cell02.example.ru
# ...остальные секреты свои: у второй ячейки своя база и своё хранилище
```

**`APP_CELL` задаёт имя проекта compose, а значит, и имена томов.** Две ячейки
с одинаковым именем делят базу и хранилище — то есть перестают быть двумя
ячейками, и обнаруживается это по чужим клиентам в реестре.

**Менять `APP_CELL` у работающей ячейки нельзя.** Другое имя проекта — другие
тома, то есть пустая база на месте живой. Данные при этом никуда не делись,
они в томах со старым именем, но выглядит это как потеря всего.

**`APP_CELL_NUMBER` — старший разряд номера арендатора.** У второй ячейки
клиенты начинаются с `t_2000001`. Иначе схема `t_000001` есть в обеих, и дамп
из одной нельзя развернуть в другую без переименования — а переносить клиента
между ячейками придётся при первой же перебалансировке. Заодно по номеру
видно, где искать клиента: `2 000 003` — третий клиент второй ячейки.
У работающей ячейки не менять: заведённые номера не двинутся, а новые уедут
в чужой диапазон.

**Код компании уникален внутри ячейки, а не между ними.** Две разные компании
в разных ячейках могут называться одинаково, и это не ошибка: код разрешается
только в той ячейке, на домен которой пришёл вход.

**Тревоги подписаны именем ячейки** — `[cell02] приложение не отвечает`.
Без подписи уведомление от одной из двух ячеек не говорит, куда идти.

**На одной машине две ячейки не живут.** Порты 80 и 443 на хосте одни,
и терминатор второй их не получит. Прогон на одной машине возможен без
терминатора (и `PUSHGATEWAY_PORT` тогда тоже свой), но это проверка
независимости данных, а не боевая конфигурация.

**Реестр ячеек ведётся снаружи** — в вашем списке хостов, а не в базе.
Приложение про соседние ячейки не знает и знать не должно: знание о них
означало бы связь, а связи между ячейками нет по построению.

**Проверено двумя ячейками на одной машине.** У второй первый клиент получил
`t_2000001`, тома, реестры и отметки бэкапа раздельные, тревога пришла
подписанной. Совпадающий код компании в обеих ячейках ничему не помешал.

## Бэкапы

```bash
ops/backup.sh                       # снять набор
ops/verify-backup.sh                # проверить восстановлением (последний набор)
ops/restore-tenant.sh t_000042      # поднять одного клиента из набора
```

Это половина защиты — та, что возвращает одного клиента на 3:00. Вторая
половина, возврат к минуте перед поломкой, — раздел «Точка возврата: архив
WAL» ниже.

По расписанию — обычным cron на хосте, и ставится он скриптом, а не
копированием строк из документации:

```bash
ops/install-cron.sh          # пять задач: архив WAL, базовая копия, дампы, обе проверки
ops/install-cron.sh --show   # что стоит сейчас
ops/install-cron.sh --remove # снять
```

**Скриптом, а не строчками для копирования.** Строчку однажды копируют
с опечаткой в пути или не копируют вовсе, и узнают об этом в тот единственный
день, когда бэкап нужен. Скрипт ставит одно и то же и умеет показать,
что стоит.

**Проверка восстановлением — еженедельная, а не ежедневная.** Она поднимает
весь набор в отдельную базу; на ячейке с двумя сотнями арендаторов это часы
диска. Раз в неделю отвечает на тот же вопрос — «получится ли вернуть
клиента», — не мешая работать. Замерено на прогонной ячейке: снятие пяти
арендаторов 12 секунд, проверка восстановлением 37.

**И бэкап, и проверка кладут отметку об успехе** (`partsflow_backup_success_
timestamp_seconds`, `partsflow_backup_verified_timestamp_seconds`). Отметка
ставится ПОСЛЕ всех шагов: поставленная в начале, она означала бы
«запускался», а знать надо «получилось». Отдельная отметка у проверки нужна
потому, что «дамп открылся» и «клиента можно вернуть» — разные утверждения.

**Переменная из файла окружения перебивает командную строку.** Скрипты
читают файл через `set -a; . file`, и `APP_CELL=cell02 ops/backup.sh` молча
уходит в ячейку, записанную в файле. Способ работать с другой ячейкой один —
свой файл и `ENV_FILE`. Наступил на это при уборке прогонной ячейки: она была
поднята под старым именем проекта, переопределение на лету не сработало,
и бэкап пытался сняться с несуществующего комплекта.

**Каждый арендатор выгружается отдельным дампом.** Ради этого схема-на-арендатора
и выбиралась: из кластерного дампа поднять одного клиента можно только подняв
всех, то есть остановив ячейку. Общие схемы (`public` с реестром и `catalog`
со справочниками) идут отдельным файлом — дублировать 800 КБ справочника
в каждый из двухсот дампов незачем.

**«Дамп снялся» — это не бэкап.** `verify-backup.sh` разворачивает набор
в отдельную базу и сверяет с живой то, что клиент заметит первым: число
позиций, остаток на складах, длину журнала движений, число сделок
и сотрудников. Расхождение — ненулевой код возврата, то есть письмо от cron.
Проверено, что проверка умеет падать: добавленная в живую базу строка ловится.

**Фотографии копируются зеркалом, а не датированным слепком.** До этого
их не копировал никто: бэкап был Postgres и только он, а снимки лежали
в одном экземпляре на одном диске MinIO, поднятом одним томом без резервирования.
У одного переехавшего клиента снимков 192 755 и около 29 ГБ — ежесуточный
полный слепок забил бы диск за неделю, поэтому `mc mirror` докладывает
недостающее. Объекты неизменяемы (uuid в ключе), так что инкремент здесь
не приближение, а точная копия.

**Зеркало без `--remove`.** Удаление в живом хранилище доезжать до копии
не должно: иначе стёртая по ошибке папка клиента исчезает и из бэкапа
в ту же ночь — ровно тогда, когда он нужен. Плата — мусор в копии.

**Клиент хранилища — сервис `mc` под профилем `backup`.** Постоянно он
не работает и в `docker compose ps` не виден: скрипты запускают его разово
через `run --rm`. Сервисом, а не `docker run`, чтобы он оказался в сети
ячейки и ходил к MinIO по имени, не открывая порт наружу; ключи приезжают
переменной `MC_HOST_cell`, то есть не попадают ни в аргументы команды,
ни в `docker ps`. Каталог бэкапов монтируется флагом при запуске: его путь
знает скрипт из файла окружения, и повторять тот же расчёт в compose значит
однажды разойтись с ним и писать копию не туда.

**У снимков своя отметка** (`partsflow_photo_backup_success_timestamp_seconds`)
и своя тревога `ФотоНеБэкапились`. Общая с дампами сказала бы «бэкап снят»
при складе без единой картинки: шаги разные, хранилища разные, и сорваться
они могут по отдельности. По той же причине шаг со снимками идёт **после**
отметки о дампах — она обязана означать ровно то, что за ней стоит.

**Проверка и восстановление тоже про снимки.** `verify-backup.sh` сверяет
не число файлов, а сами `part_photo.s3_key` восстановленной схемы: совпадение
количеств ничего не значит, если файлы другие. `restore-tenant.sh` возвращает
папку арендатора в хранилище вместе со схемой — восстановленный склад
со ссылками в никуда это не возвращённый клиент, а список наименований.
Проверено, что и это умеет падать: спрятанный из копии снимок ловится
и обрывает проверку.

**Локальная копия — защита от удаления и от порчи данных, но не от потери
машины.** Поэтому у `ops/backup.sh` есть шаг «Офсайт»: заданный
`OFFSITE_REMOTE` увозит весь каталог бэкапов наружу (rclone: другой хост,
другой бакет), а тревога `ОфсайтНеУезжал` следит и за сорвавшимся шагом,
и за незаданным адресом. Архив WAL уезжает тем же путём, но чаще —
каждые пять минут (`ops/wal-archive.sh`), потому что сегменты появляются
постоянно. Эта запись раньше говорила, что офсайта в скриптах нет; неверно
с тех пор, как шаг появился.

**Восстановление одного клиента не трогает остальных** — проверено на двух
арендаторах: у одного схема пересоздана из набора, у второго не изменилось
ничего.

**Дампы надо беречь как саму базу.** В них хеши паролей сотрудников
и зашифрованные ключи кабинетов площадок. Ключ шифрования держите **отдельно**
от бэкапа: вместе они дают ровно то же, что хранение открытым текстом.

## Точка возврата: архив WAL

Дампы по схемам отвечают на вопрос «вернуть одного клиента». На вопрос
«вернуть его к минуте перед поломкой» они не отвечают вовсе: дамп — снимок
на момент снятия, а снимается он в 3:00. Отказ, требующий возврата к бэкапу,
стоил бы клиенту всего, что он наработал с трёх часов ночи, — в 18:00 это
рабочая смена: принятые детали, проданные позиции, принятые деньги, выданный
товар. Учётная система, потерявшая день продаж, отвечает клиенту «такого
платежа не было» на деньги, которые он получил.

Поэтому у ячейки две защиты, и они про разное:

| Что | Чем | Отвечает на вопрос |
|---|---|---|
| Дампы по схемам, ежедневно | `ops/backup.sh` | вернуть ОДНОГО клиента, не трогая остальных |
| Базовая копия + архив WAL | `ops/basebackup.sh`, `archive_command` | вернуть состояние на ЛЮБОЙ момент, покрытый архивом |

Заменить одно другим нельзя. Накат WAL возвращает кластер целиком, то есть
всех арендаторов на один момент; дамп одной схемы не догоняется журналом.
Вместе они дают то, чего нет ни у одного по отдельности: **возврат одного
клиента к минуте перед поломкой** — через временный кластер (см. ниже).

```bash
ops/basebackup.sh                # физическая копия кластера (по воскресеньям)
ops/wal-archive.sh               # цепочка цела? уехала наружу? (каждые 5 минут)
ops/wal-archive.sh --chain       # до какого момента можно вернуться
ops/restore-pitr.sh --verify     # репетиция возврата (по понедельникам)
```

Расписание ставит `ops/install-cron.sh` — все пять задач сразу.

**Архивирует сегменты отдельный скрипт, а не строка в конфигурации**
(`ops/archive-wal.sh`, `archive_command` в `docker-compose.prod.yml`).
Ему нужны три вещи, и каждая — цена отдельной аварии. Атомарность: сегмент,
записанный в архив наполовину, читается накатом как целый и обрывает
восстановление на середине, поэтому пишем во временный файл и переименовываем.
Честный ответ на повтор: Postgres зовёт команду снова после любого отказа,
и на «файл уже есть» отвечать успехом можно только если это ТОТ ЖЕ сегмент —
другой с тем же именем означает, что в один архив пишут два кластера, и тихий
успех затирает историю, по которой восстанавливаются. Сжатие: сегмент всегда
16 МБ, сколько бы в нём ни было записей, а `archive_timeout=300` переключает
их каждые пять минут даже на спокойной ячейке — 288 файлов в сутки. Замерено
на прогонной ячейке: почти пустой сегмент уезжает в архив **16 КБ** вместо
16 МБ.

**`archive_timeout=300` — это предел того, что теряется вместе с диском.**
Незакрытый сегмент в архив не уехал; без принудительного переключения
спокойная ячейка может не закрывать его часами, и «точка возврата до минуты»
превратилась бы в «до утра».

**Каталог архива готовит отдельный контейнер** (`wal-archive-init`). Он
монтируется с хоста, docker создаёт отсутствующий от `root`, а `archive_command`
выполняет пользователь `postgres`: без подготовки архиватор получает
«permission denied» на каждый сегмент. Молча это не проходит — неархивированный
WAL копится в `pg_wal` и в конце концов останавливает базу, — но узнать об этом
в день аварии значит потерять точку возврата. Поэтому у `postgres` стоит
`depends_on: service_completed_successfully`: без права записи в архив базу
лучше не поднимать вовсе.

**Архив лежит рядом с дампами** (`backups/<ячейка>/wal`), а не в томе базы:
том умирает вместе с диском ячейки, а офсайт-шаг увозит каталог бэкапов
целиком — то есть архив уезжает наружу вместе с дампами. Плюс `ops/wal-archive.sh`
увозит его **каждые пять минут** отдельно: дампы за день не меняются,
а сегменты появляются постоянно, и архив, уезжающий раз в сутки, при гибели
диска стоил бы той же потерянной смены, ради которой всё и делалось.

**Глубина архива считается от самой старой хранимой базовой копии.** Уборку
делает `pg_archivecleanup` в конце `ops/basebackup.sh`: убрать больше — значит
оставить копию без наката, то есть без точки возврата; убрать меньше — забить
диск. `BASEBACKUP_KEEP=2` при недельной копии даёт окно возврата около двух
недель и столько же места под сегменты. **Диск здесь кончается раньше памяти**
(`docs/cloud-bringup.md`): к снимкам, зеркалу и дампам добавился архив.

## Возврат к моменту времени

`ops/restore-pitr.sh` разворачивает базовую копию и накатывает на неё архив
в **отдельный временный кластер** (том docker, контейнер `partsflow-pitr-<ячейка>`),
а не поверх живой базы. Причин две, и обе про схему-на-арендатора.

Первая: накат возвращает кластер целиком, то есть всех арендаторов на один
момент. Если у одного клиента авария, а остальные работают, возврат поверх
живой базы отнял бы у остальных всё, что они наработали с этого момента, —
и именно от этого schema-per-tenant защищает. Во временном кластере состояние
на нужный момент есть у всех, а забрать оттуда можно ОДНОГО.

Вторая: разворот поверх живого невозвратим. Ошибся с моментом — второй попытки
нет, потому что то, чем пользовался, уже перезаписано.

**Часовой пояс в `--to` обязателен, и это половина цены ошибки здесь.** Архив
WAL живёт в UTC, а время, которое называет человек, — чьё-то местное: журнал
контейнера пишет UTC, клиент по телефону называет своё, часы машины, с которой
разбирают аварию, показывают третье. Возврат на три часа мимо проходит
**успешно** — кластер поднимается, данные на месте, просто не те, — и проверить
это оператору нечем. Поэтому пояс не угадывается, а пишется, и инструмент
говорит, как он понял введённое:

```
==> Момент возврата
    введено:  2026-09-12 13:59:00 MSK
    это:      2026-09-12 13:59:00 MSK (+03:00)  =  2026-09-12 10:59:00 UTC
    на ЭТОЙ машине это 2026-09-12 17:59:00 (+07:00) — пояс машины ДРУГОЙ, сверьте
```

Пять написаний, все равноправные: `MSK` (время клиента), `+03:00` (смещением),
`UTC` (он же `Z` — так пишет журнал контейнера), `local` (пояс этой машины,
названный явно) и любое имя из базы поясов (`Europe/Moscow`,
`Asia/Novosibirsk`). Момент без пояса **отбивается словами** и с готовыми
строками, которые остаётся скопировать; `--to latest` пояса не требует —
там момента нет. До 13 сентября 2026 момент молча толковался в поясе машины,
и на этом ошибся не оператор в четыре утра, а разбор задачи 0083 — человек,
читавший код целиком и специально проверявший работу.

**Вернуть одного клиента к моменту:**

```bash
ops/restore-pitr.sh --to '2026-09-12 13:59:00 MSK' --tenant t_000042
# дальше — тем же скриптом, которым разворачивают ночной дамп:
PHOTO_DIR=./backups/cell01/photos ops/restore-tenant.sh t_000042 \
    ./backups/pitr/cell01/<набор>
```

Дамп одной схемы из временного кластера разворачивается **обычным**
`ops/restore-tenant.sh`: вторая дорога к тому же месту разъехалась бы с первой.

**Переключить ячейку целиком** (погиб кластер, а не один клиент). Порядок
отрепетирован на прогонной ячейке, а не выведен из документации:

```bash
ops/restore-pitr.sh --to '2026-09-12 13:59:00 MSK' --keep # 1. поднять черновик
                                  # (+ --db <база>, если момент раньше последней выкладки)
docker exec partsflow-pitr-cell01 psql -U <владелец> -d <база на тот момент> \
    -c "SELECT number, customer FROM t_000042.deal ORDER BY number DESC LIMIT 5"
                                                          # 2. сверить, что момент ТОТ
docker exec partsflow-pitr-cell01 psql -U <владелец> -d postgres \
    -tAc "SELECT pg_promote(true, 60)"                    # 3. повысить черновик
docker stop partsflow-pitr-cell01                         #    и остановить по-хорошему
docker compose -f docker-compose.prod.yml stop "$(ops/switch-build.sh --current)" postgres   # 4. остановить ячейку
docker run --rm -v partsflow-pitr-cell01:/from \
    -v partsflow-cell01_pgdata:/to postgres:16-alpine \
    sh -c 'rm -rf /to/* /to/.[!.]* ; cp -a /from/. /to/ && chown -R postgres:postgres /to'
docker compose -f docker-compose.prod.yml start postgres "$(ops/switch-build.sh --current)"  # 5. поднять ячейку
ops/basebackup.sh                                         # 6. НОВАЯ базовая копия
```

Шаг 6 обязателен, и вот почему: после повышения кластера **меняется линия
времени**. Сегменты новой линии едут в тот же архив, а прежняя базовая копия
к ним уже не подходит — накатить одно на другое нельзя. Скрипты об этом
говорят прямо («базовая копия снята на линии времени 00000001, а архив
считается по 00000002 — снимите новую базовую копию»), но до следующего
воскресенья ячейка стояла бы без точки возврата. Проверено репетицией
переключения: сообщение появилось ровно там, где ожидалось, а после новой
копии репетиция возврата снова зелёная.

**Восстановление отказывается вместо тихого успеха, и это главное свойство.**
Разрыв в архиве Postgres переживает молча: накат останавливается на пропавшем
сегменте и — если момент не задан — кластер поднимается на том, что успел
накатить. Снаружи это выглядит успехом: база работает, данные есть, просто
не все. Поэтому сторожей два.

1. **До разворота** — цепочка сегментов (`ops/wal-archive.sh --chain`, тот же
   код, что ходит по расписанию). Разрыв → отказ с названным доступным
   моментом: «вернуться можно НЕ ПОЗЖЕ 2026-09-12 23:55:19 (последний целый
   сегмент 000000010000000000000008)».
2. **После разворота** — сверка, что накат дошёл: до запрошенного момента
   (кластер обязан остановиться именно на нём) либо до последнего сегмента
   архива. Встал раньше — отказ: «накат встал на …09, а в архиве есть …0B —
   восстановлено НЕ всё».

Проверено потерей сегмента посередине на прогонной ячейке: три входа
(`--to МОМЕНТ`, `--to latest`, `--verify`) отказались и назвали доступный
момент. Со снятым первым сторожем ловит второй; со снятыми обоими возврат
отчитался **успехом и нулевым кодом**, поднял кластер, в котором из четырёх
сделок клиента осталась одна. Ровно это и есть то, чего быть не должно.

**Репетиция возврата — по понедельникам, и накатывает она весь архив**,
а не «десять минут назад». Дважды покраснело на исправной ячейке, прежде чем
стало ясно, почему: последний сегмент ещё не закрыт (`archive_timeout`), записи
последних минут лежат в живом `pg_wal` и накату недоступны; а цель по времени
Postgres считает достигнутой, только встретив в журнале запись ПОЗЖЕ неё —
и ночью, когда коммитов нет вовсе, отказывается подниматься с «recovery ended
before configured recovery target was reached». Репетиция стоит в понедельник
в 6:00, то есть ровно после такой ночи. Накат до конца архива от коммитов
не зависит и проверяет то же самое: дошёл ли он до последнего уехавшего
сегмента или тихо встал на разрыве.

**Момент уезжает в Postgres со смещением того пояса, которым его назвали.**
Без смещения Postgres толкует строку в поясе сервера (в контейнере это UTC),
и «вернуться к 13:59» молча становится «к 16:59» — возврат уносит три часа
работы, выглядя успешным. В логе наката смещение видно: «накат до
2026-09-12 13:59:00+03:00 (= 2026-09-12 10:59:00 UTC)».

**Времена, которые печатает сам инструмент, тоже подписаны поясом.** «Вернуться
можно не позже 23:55:19 +07» и «последняя накатанная транзакция 10:58:57+00»:
первое считается по времени файлов в архиве (пояс машины), второе спрашивается
у самой копии (UTC). Молчащее время читается как время читающего — а в аварию
его сверяют с тем, что назвали по телефону.

**Снимки при возврате не откатываются, и это намеренно.** Ключи в S3
содержат uuid и неизменяемы, а зеркало бэкапа ничего не удаляет — значит все
снимки, на которые ссылаются восстановленные карточки, на месте. Обратное
(снимок, загруженный после момента возврата) остаётся в хранилище мусором,
на который никто не ссылается. Согласованность нужна в одну сторону — чтобы
карточка не ссылалась в никуда, — и она есть.

**Сколько занимает возврат — замерено** (13 сентября 2026, задача 0084):
разворот базовой копии в 1 ГБ в черновик 3,7 с, накат 14 сегментов журнала
(224 МБ) с подъёмом кластера 5,2 с, дамп одной схемы из черновика 2,7 с —
целиком `--to latest --tenant` 12 и 13 секунд в двух прогонах. Длительность
растёт с числом сегментов, накопленных после базовой копии: частота
`ops/basebackup.sh` задаёт не окно возврата, а время наката. Объём, разбивка
и то, чего эти числа не обещают, — в разделе «Сколько занимает возврат
на объёме живого клиента».

## Восстановление ячейки целиком

Восстановление одного клиента делает `ops/restore-tenant.sh`, и его проверяет
`ops/verify-backup.sh` каждую неделю. А «поднять ячейку заново после потери
диска» до августа 2026 не проверялось ни разу — и не работало:

- полный `pg_dump` не снимался вовсе, пока в Postgres стояли умолчания
  (см. «Сколько держит ячейка»);
- расширения `pg_trgm`, `ltree` и `pgcrypto` принадлежат базе, а не схеме,
  и в дампы схем не попадают. Без них разворот арендатора падает на первой
  же таблице: `public_code` выдаётся умолчанием колонки через `gen_random_bytes`.

Обе дыры закрыты, восстановление отрепетировано на живой ячейке: пять
арендаторов, 4 327 позиций, полный цикл «снять бэкап → уничтожить тома →
поднять пустую базу → развернуть» занял **4 секунды**, после чего владелец
вошёл, склад открылся, все три сверки пусты. Четыре секунды — это те самые
4 327 позиций; сколько выходит на складе живого клиента, в следующем разделе.

    ENV_FILE=.env.cell02 ops/restore-cell.sh              # последний набор
    ENV_FILE=.env.cell02 ops/restore-cell.sh backups/cell02/2026-08-04  # нужный

Порядок жёсткий: расширения → общие схемы (реестр и справочники) → схемы
арендаторов → фотографии из зеркала. Скрипт разворачивает в пустую базу
и не перезаписывает существующие схемы: восстановление поверх работающей
ячейки означало бы смешать старое с новым.

После разворота обязателен `ops/migrate-tenants.sh` — он догонит схемы
до версии кода и выдаст права рабочей роли, если разделение ролей включено.

## Сколько занимает возврат на объёме живого клиента

Замерено 13 сентября 2026 (задача 0084) на локальной ячейке, набитой объёмом
переехавшего клиента: 35 841 позиция, 440 машин, 12 001 сделка, 197 124 строки
снимков, 143 364 записи журнала изменений, 49 148 движений склада — схема
398 МБ, дамп 14 МБ. В боевую ячейку с этим замером не ходили.

| Что | На чём | Сколько |
|---|---|---|
| Снять дамп одного арендатора | схема 398 МБ | 2,4 с |
| **Вернуть базу одного клиента** (`pg_restore`) | она же | **9 с** (8,8 · 9,3 · 9,7) |
| — снос схемы и создание таблиц | | 1,0 с |
| — данные (`COPY`) | | 3,0 с |
| — индексы и внешние ключи | | 4,4–5,9 с |
| **Вернуть снимки** (зеркало в пустое хранилище) | 15 000 объектов, 1,82 ГиБ | **36 с** (33,5 · 39,5) |
| Холостой проход зеркала (хранилище цело) | те же 15 000 | 5–8 с |
| Возврат к моменту времени (`ops/restore-pitr.sh`) | копия 1 ГБ + 14 сегментов | 12–13 с |
| Полный возврат клиента целиком | схема + 15 000 снимков | 52,8 и 60,4 с |

**Два числа, которые можно назвать клиенту: база — девять секунд, снимки —
около семи минут.** Первое замерено на полном объёме. Второе пересчитано,
и вот как: 24 ГБ снимков на этой машине не поднять — свободного диска было
13 ГБ, а дерево снимков живёт в трёх копиях сразу (хранилище, зеркало бэкапа
и то, что льётся обратно). Поэтому мерено на двух наборах со средним размером
объекта, как у клиента (130 КБ = 24 ГБ ÷ 192 755): 15 000 объектов и 3 000.
Две точки дают постоянную часть (5,4 с — поднять `mc` и обойти дерево)
и цену объекта (2,1 мс, 482 объекта/с); на 192 755 объектов это 6,8 минуты.
Пересчёт по байтам (60 МиБ/с) даёт 6,4 минуты — сходится, потому что средний
объект тот же. Отсюда «около семи минут», а не число с запятой.

**База возвращается за секунды, а снимки за минуты, и это не выправится.**
Дамп схемы сжат (14 МБ на 398 МБ данных), а снимки — россыпь мелких объектов,
где платят за каждый отдельно. Для отката ПРОМ это значит: **минута, если
хранилище снимков цело** (при откате выкладки оно цело — выкладка его
не трогает), и около восьми минут, если возвращать и снимки. Ни то, ни другое
не час, то есть откат слепком остаётся дешёвым.

**Восстановление одного клиента не требует остановки остальных** — проверено
работой соседа, а не рассуждением. Пока большого клиента возвращали (пять
полных прогонов, базовая копия и возврат к моменту), сосед по ячейке раз
в секунду читал склад и заводил покупателя: 665 попыток, 665 успешных, ни
одного отказа; его склад как был 200 позиций, так и остался. После каждого
возврата все три сверки (`v_stock_discrepancy`, `v_reservation_discrepancy`,
`v_account_discrepancy`) пусты, владелец входит, склад открывается, поиск
продавца находит.

**Мерить надо не первым прогоном.** Самый первый возврат занял 138 секунд
против 10–17 у следующих, а возврат сразу после `ops/backup.sh` — 55. Разница
не в базе (её разворот трижды дал 8,8–9,7 с), а в зеркале снимков: машина
в этот момент дописывала на диск 1,8 ГБ копии. В день аварии она занята ровно
тем же, поэтому верхняя половина вилки честнее нижней.

**Чего эти числа не обещают.** Мерено на ноутбуке под Docker Desktop, где
каталог бэкапов проброшен в контейнер с хоста: на Linux-машине ячейки проброса
нет, зато процессор слабее. Это замер порядка величины — секунды против минут,
минуты против часа, — а не обещание секунд на конкретном VPS. И объём взят
по складу и снимкам: у клиента, отработавшего год, журнал изменений будет
больше 143 364 записей, а время разворота растёт со строками, не с байтами —
индексы съедают больше половины.

## Наблюдение

Метрики отдаёт `/actuator/prometheus`. Наружу этот адрес не выставлен —
он живёт на порте приложения, а тот виден только терминатору; собирают их
изнутри сети docker три контейнера, поднимающиеся вместе с ячейкой:

| Контейнер | Зачем |
|---|---|
| `prometheus` | опрашивает приложение, держит две недели истории, считает правила |
| `alertmanager` | шлёт тревогу в Telegram и повторяет, пока не починили |
| `pushgateway` | принимает отметки от бэкапа — задачу по расписанию опрашивать некому |

**Все три обязательны, а не «на будущее».** Без сборщика метрики отдаются
в пустоту, без адресата тревога никуда не уходит — то есть об остановившемся
релее оператор узнаёт от клиента. Пустой `ALERT_TELEGRAM_CHAT_ID` валит
запуск намеренно: тревога, уходящая в никуда, хуже отсутствия тревог, потому
что создаёт уверенность, что за ячейкой смотрят.

**Токен бота — файлом, а не переменной.** В переменной он виден в
`docker inspect` любому, кто дошёл до хоста. Путь задаётся
`ALERT_TELEGRAM_TOKEN_FILE`, права на файл — **644**, а не 600, и это
не небрежность: контейнер Alertmanager бежит под `nobody` (uid 65534),
а файл принадлежит владельцу ячейки (`deploy`). При 600 контейнер его
не прочитает — `permission denied`, и тревога сработает, но не уйдёт
в Telegram. Поймано живым прогоном на боевом сервере: правило `firing`,
а в логе Alertmanager `could not read /etc/alertmanager/telegram-token`.
На машине с одним администратором 644 ничего не ослабляет — защита была
в том, что токен не в переменной окружения, а не в разрешениях файла.

Номер чата подставляется в конфигурацию при запуске: Alertmanager окружение
в ней не разворачивает — это проверено его же `--help`, а не выведено из того,
что так умеют соседние программы.

Наружу ни один из трёх портов не выставлен. Исключение — `pushgateway`
на `127.0.0.1:9091`: бэкап запускается на хосте по cron, а не в контейнере,
и дотянуться до отметки ему больше неоткуда.

Четыре числа отвечают на вопрос «плохо ли с событиями»:

| Метрика | О чём |
|---|---|
| `partsflow_outbox_pending` | сколько событий ждёт отправки |
| `partsflow_outbox_oldest_seconds` | возраст самого старого неотправленного |
| `partsflow_deadletter_unresolved` | неразобранные отказы обработчиков |
| `partsflow_deadletter_attention` | из них те, что робот уже бросил |

И десять — на вопрос «есть ли точка возврата». Первые восемь кладёт
`ops/wal-archive.sh` (каждые пять минут), остальные две — `ops/basebackup.sh`
и `ops/restore-pitr.sh --verify`:

| Метрика | О чём |
|---|---|
| `partsflow_wal_archive_gaps` | разрывов в цепочке сегментов |
| `partsflow_wal_archive_pending` | сегментов ждёт архивации (растёт — архиватор встал) |
| `partsflow_wal_archive_broken` | 1, если архиватор не работает: сегмент ждёт дольше предела либо последняя попытка отказала |
| `partsflow_wal_archive_oldest_ready_seconds` | сколько ждёт архивации самый старый сегмент (на исправной ячейке — единицы) |
| `partsflow_wal_archive_failed_count` | отказов архивации за жизнь процесса базы |
| `partsflow_wal_archive_success_timestamp_seconds` | когда сегмент последний раз уехал в архив |
| `partsflow_wal_offsite_success_timestamp_seconds` | когда архив последний раз уехал наружу |
| `partsflow_wal_check_timestamp_seconds` | когда сторож последний раз ходил (отсутствие = задачи нет в cron) |
| `partsflow_basebackup_success_timestamp_seconds` | когда снята базовая копия кластера |
| `partsflow_pitr_verified_timestamp_seconds` | когда возврат последний раз проверялся разворотом |

Правила лежат в `ops/alerts.yml`, тринадцать штук:

| Тревога | Условие | Почему |
|---|---|---|
| `ЯчейкаНеОтвечает` | нет ответа 2 минуты | две минуты — это выкладка, больше — уже нет |
| `РелейВстал` | возраст события > 5 минут | остаток на площадке разъезжается с настоящим |
| `НедоставленноеЖдётЧеловека` | брошенное роботом > 0 | пока робот повторяет, делать нечего |
| `БэкапНеСнимался` | отметки нет или ей > 26 часов | сутки плюс запас на длинный дамп |
| `ФотоНеБэкапились` | отметки нет или ей > 26 часов | снимки в одном экземпляре, копия одна |
| `ОфсайтНеУезжал` | отметки нет или ей > 26 часов | или сорвался, или `OFFSITE_REMOTE` не задан — диск гибнет вместе с бэкапом |
| `БэкапНеПроверялся` | отметки нет или ей > 9 дней | недельное расписание плюс запас |
| `АрхивWALНеПишется` | в очереди > 5 сегментов 15 минут | точка возврата замерла, а `pg_wal` растёт и в конце остановит базу |
| `АрхиваторWALОтбит` | сегмент ждёт архивации дольше 10 минут либо последняя попытка отказала, 5 минут | очередь отвечает «не справляется», а это «не работает»; и `pg_stat_archiver` не считает отказ, убивающий архиватор, — проверено живым прогоном |
| `РазрывВАрхивеWAL` | разрывов > 0 | вернуться можно только до разрыва, и Postgres поднимется молча на том, что накатилось |
| `СторожАрхиваНеХодит` | отметки нет или ей > часа | задача стоит каждые 5 минут: цепочку никто не проверяет |
| `АрхивWALНеУезжалНаружу` | отметки нет или ей > 2 часов | сегменты появляются каждые 5 минут; суточный офсайт стоил бы смены |
| `БазоваяКопияНеСнималась` | отметки нет или ей > 8 дней | архив WAL накатывать не на что |
| `ВозвратНеПроверялся` | отметки нет или ей > 9 дней | «архив есть» и «клиента можно вернуть к минуте» — разные утверждения |

**Правило в файле — ещё не тревога.** Prometheus не перечитывает
`ops/alerts.yml` сам, а выкладка перезапускает приложение и до него
не доходит: правило, добавленное после подъёма ячейки, лежит смонтированным
и не действует. Так `ФотоНеБэкапились` неделю не знала ячейка — шесть правил
в файле, пять в памяти, и ни одной ошибки нигде. После правки правил:

```bash
docker compose -f docker-compose.prod.yml exec -T prometheus \
  wget -qO- --post-data='' localhost:9090/-/reload
docker compose -f docker-compose.prod.yml exec -T prometheus \
  wget -qO- localhost:9090/api/v1/rules | grep -o '"type":"alerting"' | wc -l
```

Второе число обязано совпасть с `grep -c 'alert:' ops/alerts.yml`. Счёт
через `grep -o … | wc -l`, а не `grep -c`: ответ приходит одной строкой.

**Тревога на возраст, а не на глубину.** Сто событий, появившихся секунду
назад, — обычная работа; те же сто возрастом в пять минут — вставший релей.

**Отсутствие отметки — это тоже тревога.** `absent()` в правилах про бэкап
не для красоты: ячейка, на которой забыли `ops/install-cron.sh`, сообщит
об этом сама. Иначе «тревог нет» означало бы «бэкапов нет» ровно до того дня,
когда они понадобятся.

**Всё, на что ответ «ну и ладно», сюда не попадает.** Через месяц лишних
уведомлений их перестают читать, и настоящая авария приходит в общей куче.

**Проверено живым прогоном, а не чтением конфигурации.** Приложение
остановлено — через две минуты `ЯчейкаНеОтвечает` в состоянии firing,
Alertmanager её принял и сходил в Telegram (404 на тестовом токене — то есть
последний участок пути тоже рабочий, ему нужен только настоящий токен).
Приложение поднято — тревога снялась сама. Бэкап с проверкой погасили обе
свои.

Числа считаются по ячейке целиком, а не по арендатору: метрика на клиента при
пятистах арендаторах — это пятьсот временных рядов на каждое число, то есть
хранилище метрик размером с базу. Кому именно плохо, показывает экран разбора.

С включённой Kafka Spring Boot добавляет к этому метрики клиента, в том числе
`kafka_consumer_fetch_manager_records_lag_max` — отставание потребителя.

**Два экземпляра проверены.** Прогон на общей базе: 40 событий, ноль
дубликатов — распределённые блокировки ShedLock держат и релей, и накат
миграций (второй заход получает 409, а не второй прогон).

## Kafka

По умолчанию выключена: транспорт событий работает в памяти, и первым клиентам
этого достаточно. Брокер нужен, когда экземпляров приложения становится больше
одного — при транспорте в памяти событие обрабатывается там же, где родилось,
и второй экземпляр про него не узнает.

```bash
# сначала брокер, потом переключение приложения
SPRING_PROFILES=kafka docker compose -f docker-compose.prod.yml \
    --profile kafka up -d
```

Порядок важен только для аккуратности: без брокера релей крутится вхолостую,
но событий не теряет — неопубликованное лежит в `outbox`, пока не уедет.

**Первое событие каждого нового типа ждёт обновления метаданных.** Топик
заводится на каждый тип, слушатель подписан шаблоном, а новый топик потребитель
замечает только при обновлении метаданных. С умолчанием в пять минут это
и получалось: живой прогон дал 195 секунд от публикации до обработки при
полностью исправном брокере — и выглядит это как потерянное событие. Поэтому
`metadata.max.age.ms` снижено до 30 секунд; после правки тот же прогон дал
11 секунд.

**Реплика на одном узле одна.** Пара `acks=all` + `min.insync.replicas=2`
защищает от потери только вместе; на одном брокере вторая половина
недостижима, и появление второго узла — повод поднять
`KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR` до 3, а `MIN_ISR` до 2.

## Чего здесь нет

**Protobuf и Schema Registry.** Payload'ы едут JSON'ом по контракту-record'у
(`platform/outbox/contract`), имена полей на проводе застолблены тестом.
Реестр схем согласовывает схему между издателем и потребителем, которые
выкладываются порознь; сейчас это один процесс и один артефакт, а контейнер
реестра и кодогенерация в сборке — цена вперёд платы. Возвращаться к этому,
когда события начнёт читать что-то, выкладываемое отдельно от нас.
