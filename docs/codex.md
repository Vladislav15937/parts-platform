# Работа в Codex

Адаптация от 11 ноября 2026 по запросу владельца: сохранить накопленные
правила проекта и проверить их загрузку в Codex. Файлы Claude остаются
на местах: их пути используют `agent-contract-guard.py`, `verdict-check.py`
и CI. Код продукта, миграции и решения по продукту адаптация не меняет.

## Что загружается и когда

| Материал | Механизм Codex |
|---|---|
| Корневой `AGENTS.md` | Автоматическая инструкция проекта |
| Вложенный `AGENTS.md` | Стартовая цепочка от корня до cwd; при работе из корня прочитать нужные вложенные файлы явно |
| `.agents/skills/*/SKILL.md` | Обнаружение метаданных; тело читается при использовании |
| `.codex/agents/*.toml` | Штатные описания ролей; подробный договор читается при запуске роли |
| `CLAUDE.md`, памятки модулей, `docs/` | Явное чтение по инструкциям и области задачи |
| `.claude/rules/*.md` | Явное чтение правил, выбранных `tools/codex-context.py` по исходным `paths:` |

Ссылки не загружают документы рекурсивно. Не следует копировать 84 КБ
корневого `CLAUDE.md` в `AGENTS.md` или увеличивать глобальный лимит ради
этого: автоматическая цепочка должна помещаться в стандартные 32 КиБ.
Существующая пользовательская конфигурация может добавлять инструкции,
отключать скиллы или менять лимит; проверка проекта не отменяет её.

Перед правкой перечисли затронутые пути:

```sh
python3 tools/codex-context.py ops/backup.sh tools/date-mine-guard.py
```

Инструмент выводит файлы для чтения, но не читает их за модель и не доказывает
их наличие в контексте. Он берёт шаблоны непосредственно из `.claude/rules/`,
а не из второй вручную поддерживаемой таблицы. Для пути каталога показывает
все относящиеся к его поддереву памятки и правила. Проверки не сканируют
брошенные деревья `.claude/worktrees/` и зависимости.

Для Java-тестов маршрут учитывает как пакет теста, так и импортируемые
производственные модули: сквозной тест отчёта со `StockLedger` требует
памяток отчётов, склада и используемого платформенного модуля.

## Скиллы

Пять обёрток Codex ссылаются на исходные процедуры `.claude/skills/`.
В начале каждой указаны различия механизмов; менять общий порядок следует
в исходной процедуре, а различия Codex — в обёртке.

- `$nachalo-smeny` — заново измерить CI, SHA и состояние доски.
- `$tsikl-zadachi` — выполнить одну задачу по договору проекта.
- `$volna` — свести уже разрешённую волну; сам выбор скилла не разрешает слияние.
- `$uborka` и `$vykladka` — только явный вызов человека. Для них
  `agents/openai.yaml` содержит `allow_implicit_invocation: false`, что
  сохраняет исходное `disable-model-invocation: true` Claude. Это политика
  обнаружения, не отдельный механизм выдачи разрешений.

`MEMORY.md`, история прошлой сессии и пути `~/.claude/` не считаются
автоматически доступными. `${CLAUDE_PROJECT_DIR}` в исходной процедуре
означает корень, полученный `git rev-parse --show-toplevel`; не требуется
заводить переменную Claude в окружении Codex.

## Роли и изоляция

В `.codex/agents/` зарегистрированы те же 11 ролей. Модель и reasoning effort
не фиксируются: используются настройки родительской сессии. Роли загружают
свой договор `.claude/agents/<роль>.md`, root `AGENTS.md` и этот документ.

`model: sonnet`, `tools: Bash, Read, ...`, `Explore`, `Plan`, `ToolSearch`,
`SendMessage`, `Task` и `isolation: "worktree"` в исходных договорах описывают
Claude. В Codex:

- Для сообщения и ожидания используются доступные инструменты субагентов;
  отсутствие нужного инструмента нужно сообщить, а не имитировать выполнение.
- Контракт роли сохраняется. `planner`, `doc-check`, `live-run`, `ops`,
  `reviewer`, `triage` не запускают других агентов. Само наличие описания роли
  не разрешает начать волну: дирижёр и разведка запускаются по слову человека.
- До запуска пишущего агента или разбора вызывающий выделяет отдельный git
  worktree и передаёт абсолютный путь в задаче. Агент до первой записи
  переходит в него и сравнивает `git rev-parse --git-dir` с
  `git rev-parse --git-common-dir`. Одинаковые каталоги означают основное
  дерево — писать и ломать код там нельзя. Обе стороны проверяют изоляцию.
- Обычный субагент Codex разделяет файловую систему с родителем. Параметр
  Claude `isolation` не существует в инструменте запуска Codex; не передавай
  вымышленный параметр. Создание worktree выполняется доступным штатным
  инструментом либо `git worktree add` с соблюдением разрешений среды.
- Области tools в Claude не создают песочницу Codex. Роли наследуют права
  родителя; запрет роли менять данные или делегировать — инструкция, а не
  технически отдельный профиль разрешений. `reviewer` может временно ломать
  код только у себя и обязан восстановить дерево; не путать с автором правки.
- Браузерные инструменты Claude не появляются в Codex. Используй имеющийся
  браузерный инструмент; если его нет, укажи непроверенный живой сценарий.

Остальной порядок работы, PR, доказательства и слияние остаются в
`docs/agent-workflow.md`. Адаптация не разрешает автоматически публиковать
PR-комментарии, сливать ветки, выкладывать, удалять ветки или менять ПРОМ.
Первичная адаптация по прямому поручению владельца выполнялась в его
рабочей копии без запуска волны и без коммита. Последующим поручением от
11 ноября 2026 владелец потребовал оформить результат классической задачей:
это задача 0392, отдельная ветка и PR с независимым разбором и CI. Ни одна
из этих разовых инструкций не меняет порядок обычных продуктовых задач.

## Хуки и разрешения

`.claude/settings.json` и `settings.local.json` не являются настройками Codex.
Разрешения не копируются; пользовательский `~/.codex/config.toml`, auth и
настройки sandbox остаются в ведении пользователя и среды.

У Claude два хука: перехват тестовой команды и журнал `InstructionsLoaded`.
Они остаются рабочими для Claude и проверяются существующим CI. В Codex
этим хукам не приписывается автоматический запуск:

- Вывод тестов сохраняй или ограничивай средствами инструмента, сохраняя
  исходный exit code. Не добавляй пайп, превращающий отказ теста в успех.
- Маршрутизация правил идёт через `AGENTS.md` и `codex-context.py`.
  Проверка `codex-context-probe.py` перехватывает реальный стартовый запрос
  локального CLI и проверяет то, что действительно включено в него.

Дополнительные хуки Codex не устанавливаются: они требуют отдельного доверия
к исполняемым обработчикам и не нужны для загрузки этих инструкций. Ни
проверка структуры, ни наличие пути в журнале не доказывают, что модель
прочла полный документ или выполнила его требования.

## Воспроизводимая проверка

```sh
python3 tools/codex-context.py --check
python3 tools/codex-context.py --selftest
python3 tools/codex-context-probe.py
```

Первые две проверки работают без Codex и сети, проверяют ссылки, покрытие
памяток, frontmatter, политику скиллов и размер стартовых цепочек. CI
исполняет их в задаче «Договоры агентов».

Последняя запускает установленный Codex CLI в свежем временном профиле,
с локальным HTTP-приёмником вместо модели. Она не отправляет запрос в OpenAI,
не использует ключи и не исполняет команды модели: проверяет фактический
запрос, собранный самим Codex, для корня и вложенных каталогов. Дополнительно
`skills/list` app-server проверяет пять скиллов и explicit-only policy.
Проверка не доказывает поведение удалённой модели и не проверяет настройки
каждого пользовательского профиля. Протокол проверки хранится вне git,
по умолчанию во временном каталоге.

Для текущего приложения после добавления инструкций начни новую сессию:
состав автоматически загруженного стартового контекста уже идущего диалога
задним числом не меняется. В этой сессии новые файлы можно читать явно.

Официальные форматы: [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md),
[скиллы](https://learn.chatgpt.com/docs/build-skills),
[роли](https://learn.chatgpt.com/docs/agent-configuration/subagents).

`skills/list` проверен как в свежем временном, так и в действующем
пользовательском профиле: все пять проектных скиллов видны из корня и
`frontend`, все включены. Проверки структуры и маршрутизации, валидатор пяти
скиллов, YAML CI и прежние сторожа договоров, вердиктов, подделок и обоих

из установленного nvm; это не изменение пользовательской конфигурации.

Это проверка интеграции и фактической сборки стартового запроса. Удалённая
модель не вызывалась, продуктовые тесты Java/React не запускались: код
приложения и схема не менялись. Новые проверки добавлены в CI; результат
будущего серверного прогона этим локальным отчётом не подменяется.
