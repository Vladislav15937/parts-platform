# Учётная система для авторазборок: архитектура и план разработки

Редакция 2. Изменения относительно первой версии: событийная шина на Kafka с паттерном Outbox и абстрагированным транспортом, схема БД на каждого арендатора, ячеистая (cell-based) топология под быстрый рост.

Документ описывает техническую архитектуру и план вывода продукта на первых 10 клиентов с расчётом на кратный рост. Целевой функциональный паритет — уровень Bazon; реализация и модель данных проектируются с нуля.

---

## 1. Исходные условия и целевой масштаб

**Сегодня.** Десять компаний, склады от 3 000 до 50 000 позиций, около 500 тысяч товаров суммарно, 30–60 пользователей.

**Горизонт планирования.** Проектируем под 500–1000 арендаторов в течение двух-трёх лет. Это меняет требования качественно: то, что при десяти клиентах делается руками, при пятистах должно быть автоматизировано полностью, а то, что стоит копейки на одного клиента, при умножении на 500 определяет, есть ли у бизнеса маржа.

**Приоритеты, заданные явно:** скорость и надёжность. Отсюда два следствия, которые проходят через весь документ. Скорость означает, что тяжёлые операции (выгрузки, обработка фото, пересборка магазина) никогда не выполняются в HTTP-запросе и распараллеливаются по арендаторам. Надёжность означает, что ни одно изменение данных не может потеряться между БД и шиной событий, а отказ одного компонента не должен затрагивать всех клиентов сразу.

**Юридический контур.** Персональные данные хранятся в РФ (152-ФЗ). В перспективе — Единый реестр российского ПО.

## 2. Ключевые решения

| Вопрос | Решение | Главный аргумент |
|---|---|---|
| Форма системы | Модульный монолит с выделяемыми воркерами | Один разработчик; границы модулей позволяют выделить сервис, когда это понадобится |
| Изоляция данных | Схема PostgreSQL на арендатора | Независимый бэкап и восстановление одного клиента |
| Топология | Ячейки (cells): группа арендаторов на общем комплекте инфраструктуры | Ограничение радиуса поражения без инфраструктуры на каждого клиента |
| События | Outbox в Postgres → релей → Kafka | Атомарность записи данных и события; без Outbox гарантий нет в принципе |
| Транспорт | Скрыт за интерфейсом `DomainEventPublisher` | Домен не знает про Kafka; замена транспорта — вопрос конфигурации |
| Изоляция в Kafka | Топики с префиксом ячейки, ключ = `tenant_id`, ACL и квоты | Порядок событий на арендатора и защита от шумного соседа |
| Выделенный кластер | Только как платный корпоративный тариф | Экономика: см. расчёт в разделе 6.5 |
| Фото | Presigned URL напрямую в S3, обработка асинхронно | Трафик мимо бэкенда, главная статья расходов под контролем |

### Про фронтенд

Соблазн для Java-разработчика — Thymeleaf или HTMX. Для десктопной части это сработало бы. Но ключевой сценарий — приёмка запчасти с телефона: камера, серия снимков, сканирование штрих-кода, плохая связь в ангаре. Это интерактивный клиент с локальным состоянием и офлайн-очередью, на серверных шаблонах он получается плохо.

PWA вместо нативного приложения на старте: `getUserMedia` даёт камеру, `BarcodeDetector` с полифилом на ZXing — сканирование, Service Worker и IndexedDB — офлайн-очередь. Нативное приложение в v2, когда упрётесь в качество сканера и фоновую загрузку фото.

## 4. Ячеистая топология

Это структурное решение, задающее рамку для всего остального.

**Ячейка (cell)** — самодостаточный комплект инфраструктуры, обслуживающий группу арендаторов: инстанс Postgres, пул приложений и воркеров, доля кластера Kafka, бакет S3. Арендатор целиком живёт в одной ячейке. Соответствие «арендатор → ячейка» хранится в отдельной служебной БД (control plane), которая не содержит бизнес-данных.

```
                    ┌─────────────────────────┐
                    │   Control Plane          │
                    │   реестр арендаторов,    │
                    │   маршрутизация, биллинг │
                    └───────────┬─────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
   ┌────▼─────┐           ┌─────▼────┐            ┌─────▼────┐
   │ Cell-01  │           │ Cell-02  │            │ Cell-N   │
   │ ~100     │           │ ~100     │            │          │
   │ tenants  │           │ tenants  │            │          │
   ├──────────┤           ├──────────┤            ├──────────┤
   │ Postgres │           │ Postgres │            │ Postgres │
   │ App/Wrkr │           │ App/Wrkr │            │ App/Wrkr │
   │ Kafka    │           │ Kafka    │            │ Kafka    │
   │ S3 bucket│           │ S3 bucket│            │ S3 bucket│
   └──────────┘           └──────────┘            └──────────┘
```

Зачем это нужно именно тебе:

**Радиус поражения ограничен.** Сбой Postgres, неудачная миграция, отравленное сообщение в Kafka затрагивают одну ячейку, а не всех клиентов. При десяти клиентах это приятно, при пятистах — единственный способ спать по ночам.

**Рост линейный и предсказуемый.** Ячейка заполнилась — разворачиваешь следующую по тому же шаблону. Не нужно перепроектировать систему на каждом порядке роста.

**Поэтапный выкат.** Новая версия сначала уходит в ячейку с самыми лояльными клиентами, потом дальше. Это же решает твою проблему «десять компаний из одного города знают друг друга»: разложи их по разным ячейкам, тогда один инцидент не заденет весь город сразу.

**Корпоративные клиенты.** Крупному клиенту продаётся выделенная ячейка со своим Kafka и своим Postgres — за отдельные деньги. Именно так реализуется твоя идея про отдельный кластер: как тариф, а не как правило.

На старте ячейка одна и живёт в Docker Compose на одном сервере. Вся ценность решения в том, что переход к трём ячейкам не требует переписывания — только развёртывания.

## 5. Мультиарендность: схема на арендатора

### 5.1 Устройство

Каждому арендатору выделяется схема Postgres: `t_000042`. Внутри — одинаковый набор таблиц. Общие справочники (марки, модели, поколения, кузова, категории узлов) лежат в общей схеме `catalog` и доступны всем через `search_path` — дублировать их на каждого арендатора бессмысленно, это сотни тысяч строк, одинаковых для всех.

```
public       — служебное: реестр арендаторов ячейки, версии схем
catalog      — общие справочники, только чтение
t_000042     — данные арендатора 42
t_000043     — данные арендатора 43
```

Сильные стороны, ради которых это делается:

**Восстановление одного клиента.** Сценарий не гипотетический: сотрудник снёс полсклада, обнаружили через два дня. Здесь это `pg_restore -n t_000042` из ночного дампа плюс накат WAL. С общей таблицей и `tenant_id` пришлось бы поднимать копию всей БД на момент до инцидента и переливать строки при живой работе остальных.

**Изоляция без надежды на дисциплину.** Отсутствие `tenant_id` в `WHERE` физически не может привести к утечке: данных другого арендатора в схеме просто нет. Для клиентов из одного города, которые друг другу конкуренты, это решающий аргумент.

**Отчуждаемость.** Клиент уходит или требует свои данные — `pg_dump -n t_000042`, и всё. Удаление по 152-ФЗ — `DROP SCHEMA`.

**Точечная оптимизация.** Крупному клиенту с 50 тысячами позиций можно добавить индексы, которые остальным не нужны.

### 5.2 Миграции — главная цена решения

При 500 арендаторах у тебя 500 схем, и наивный прогон Flyway по очереди займёт часы, а при падении на 300-й оставит систему в разъехавшемся состоянии. Это нужно строить как отдельный механизм с первого дня.

Правила:

**Expand–contract, всегда.** Изменения только обратно совместимые: сначала добавили колонку (nullable, с дефолтом), выкатили код, умеющий и старую и новую форму, заполнили данные, потом отдельным релизом убрали старое. Никогда не выкатывай схему и код, требующий её, одновременно.

**Миграции — это job'ы, а не шаг деплоя.** Оркестратор берёт список схем ячейки, гонит их пачками с ограничением параллелизма, ведёт таблицу состояния (схема, версия, статус, ошибка), умеет продолжить с места падения и откатить на подмножестве. Приложение при старте не блокируется миграциями и умеет работать со схемами двух смежных версий.

**Канареечный прогон.** Сначала на внутренней тестовой схеме, потом на 1% арендаторов, потом на остальных.

**Обязательный контроль времени.** `lock_timeout` и `statement_timeout` на каждой миграции: `ALTER TABLE`, взявший тяжёлую блокировку на таблице крупного клиента в разгар рабочего дня, положит ему работу. Индексы — только `CREATE INDEX CONCURRENTLY`.

### 5.3 Ловушка: PgBouncer и `search_path`

Это место, где схема-на-арендатора чаще всего ломается в проде, поэтому фиксирую отдельно.

PgBouncer в transaction mode отдаёт физическое соединение другой транзакции после коммита. Если ты выставил `SET search_path TO t_000042` как сессионную настройку, следующая транзакция другого арендатора может получить то же соединение с чужим `search_path`. Это ровно та утечка между клиентами, ради предотвращения которой всё и затевалось.

Решение — одно из двух, и оба должны быть закреплены тестом:

1. `SET LOCAL search_path` внутри транзакции (действует только до конца транзакции), выставляемый в перехватчике на открытии транзакции.
2. Полностью квалифицированные имена таблиц, генерируемые из контекста арендатора; `search_path` не используется вообще.

Практично: вариант 1 для основного кода, плюс интеграционный тест, который прогоняет через один пул соединений транзакции двух арендаторов вперемежку и проверяет, что данные не перепутались.

### 5.4 Пределы и когда шардировать

Postgres нормально живёт с сотнями схем, но каждая схема — это десятки записей в системном каталоге. При тысячах схем растёт каталог, замедляются `pg_dump`, автовакуум и планировщик на первом запросе к новой схеме.

Практический ориентир: **до 200–300 арендаторов на инстанс**, дальше — новая ячейка. Не потому что Postgres не выдержит больше, а потому что время `pg_dump` всей ячейки и время прогона миграций растут линейно, и на них завязано твоё время восстановления.

Крупных арендаторов (свыше 100 тысяч позиций) считай за пять обычных при заполнении ячейки.

## 6. События: Outbox → Kafka

### 6.1 Почему Outbox обязателен

Транзакция в Postgres и публикация в Kafka не атомарны. Сохранил товар, отправил событие, брокер не ответил — событие потеряно, объявление на Авито не обновилось, клиент продал деталь, которой нет. Обратный порядок не лучше: отправил событие, транзакция откатилась — потребители обработали то, чего не произошло.

Единственное корректное решение — писать событие в таблицу той же транзакцией, а в Kafka его переливает отдельный процесс:

```sql
CREATE TABLE outbox (
    id             bigserial PRIMARY KEY,
    aggregate_type text        NOT NULL,   -- 'part', 'deal', 'donor'
    aggregate_id   bigint      NOT NULL,
    event_type     text        NOT NULL,   -- 'part.price_changed.v1'
    partition_key  text        NOT NULL,   -- обычно tenant_id, иногда tenant:part
    payload        bytea       NOT NULL,   -- Protobuf
    headers        jsonb       NOT NULL DEFAULT '{}',
    created_at     timestamptz NOT NULL DEFAULT now(),
    published_at   timestamptz
);
CREATE INDEX ON outbox (id) WHERE published_at IS NULL;
```

Релей читает неопубликованные записи в порядке `id`, публикует в Kafka с идемпотентным продюсером, помечает опубликованными. Гарантия — at-least-once, поэтому **все потребители обязаны быть идемпотентными**: либо операция естественно идемпотентна, либо есть таблица обработанных `event_id` с уникальным индексом.

Два способа реализации релея. Свой воркер — просто, полностью под контролем, добавляет задержку в сотни миллисекунд. Debezium через CDC на логической репликации — задержка в единицы миллисекунд, не нагружает БД запросами, но это ещё один компонент в эксплуатации и настройка слотов репликации на каждую схему. Начинай со своего воркера, переходи на Debezium, когда задержка станет проблемой.

### 6.2 Абстракция транспорта

Домен не знает про Kafka. Это не academic purity, а страховка: транспорт — единственный компонент, который ты вероятнее всего захочешь заменить.

```java
public interface DomainEventPublisher {
    void publish(DomainEvent event);          // пишет в outbox, в текущей транзакции
}

public interface EventTransport {             // реализации: Kafka, NATS, in-memory для тестов
    void send(List<OutboxRecord> batch);
}
```

В тестах транспорт — in-memory, что даёт быстрые интеграционные тесты без поднятия брокера. В проде — Kafka. При смене брокера домен не меняется вообще.

### 6.3 Топики и партиционирование

Именование: `{cell}.{domain}.{event}.v{n}`, например `cell01.parts.part-changed.v1`.

**Ключ сообщения — `tenant_id`** (для событий, где важен порядок внутри одной сущности — `tenant_id:aggregate_id`). Kafka гарантирует порядок внутри партиции, а один ключ всегда попадает в одну партицию. Это решает главную проблему параллельной обработки: события «цена изменена» и «товар продан» по одной запчасти не переставятся местами и на площадку не уедет устаревшая цена.

Партиций на топик — 12–24 на ячейку. Считается от желаемого параллелизма потребителей: число партиций задаёт потолок числа воркеров в группе. Увеличивать партиции позже можно, но это ломает соответствие «ключ → партиция», а значит и порядок для существующих ключей — закладывай запас сразу.

Топики по назначению: события домена (`parts`, `deals`, `donors`), команды на выгрузку (`publishing.avito`, `publishing.drom`), обработка фото (`media.process`), мёртвая очередь на каждый потребитель (`*.dlq`).

Retention: события домена — компактируемые (`log.compaction`) с ключом по сущности, что даёт возможность восстановить актуальное состояние реплеем; команды — 7 дней; DLQ — 30 дней.

### 6.4 Изоляция арендаторов внутри общего кластера

Твоё требование по изоляции выполняется без отдельного кластера на клиента:

**ACL по префиксу.** Если у арендатора когда-либо появится прямой доступ (вебхуки, интеграции), права выдаются на префикс топиков и на конкретную consumer group.

**Квоты.** Kafka умеет ограничивать пропускную способность на клиента (`producer_byte_rate`, `consumer_byte_rate`) и долю CPU на запросы. Это прямое лекарство от шумного соседа: арендатор, заливающий 200 тысяч товаров, не тормозит остальных.

**Справедливая обработка.** Одного tenant_id, породившего очередь на миллион событий, недостаточно, чтобы заблокировать других: воркеры читают из партиций по кругу, а тяжёлые пакетные операции идут в отдельные топики с меньшим приоритетом. При необходимости — отдельная consumer group и отдельный пул воркеров под крупных арендаторов.

**Радиус поражения.** Отравленное сообщение или залипший потребитель затрагивают одну ячейку. Именно ячейка, а не отдельный кластер на клиента, — правильная единица изоляции.

### 6.5 Почему не кластер Kafka на каждого арендатора

Идея понятна и мотив правильный, но арифметика её не выдерживает.

Продакшн-кластер с настоящей отказоустойчивостью — это минимум 3 брокера (`replication.factor=3`, `min.insync.replicas=2`) плюс кворум контроллеров.

**Расчёт по действующим ставкам Yandex Cloud** (тарифы Compute Cloud, Intel Ice Lake, март 2026; сверены автором источника с фактической детализацией биллинга):

| Ресурс | Ставка | На брокер (4 vCPU / 16 ГБ / 200 ГБ) | ₽/мес (720 ч) |
|---|---|---|---|
| vCPU, 100% | 1,1529 ₽/ядро·час | 4 ядра | 3 320 |
| RAM | 0,3074 ₽/ГБ·час | 16 ГБ | 3 541 |
| Диск (HDD) | 0,004453 ₽/ГБ·час | 200 ГБ | 641 |
| | | **Итого на брокер** | **≈ 7 500** |

Отсюда кластер из 3 брокеров — **около 22 500 ₽/мес без НДС**, то есть ~27 500 ₽ с НДС 22%.

Две поправки вверх, обе существенные. Первая: под Kafka нужен SSD, а не HDD — ставка за сетевой SSD в разы выше, и диск перестаёт быть копеечной статьёй. Вторая: если брать управляемый сервис вместо самостоятельной эксплуатации, к стоимости вычислительных ресурсов добавляется наценка сервиса, а при двух и более брокерах Yandex автоматически поднимает ещё три служебных хоста координации — это ещё порядка 10 000 ₽/мес. Реалистичная вилка на отказоустойчивый кластер: **25 000 ₽ при самостоятельной эксплуатации на HDD, 40 000–50 000 ₽ за управляемый на SSD.**

| Арендаторов | Кластеров | По 25 000 ₽ | По 45 000 ₽ |
|---|---|---|---|
| 10 | 10 | 250 000 ₽/мес | 450 000 ₽/мес |
| 100 | 100 | 2,5 млн ₽/мес | 4,5 млн ₽/мес |
| 500 | 500 | 12,5 млн ₽/мес | 22,5 млн ₽/мес |

При десяти клиентах, платящих в сумме порядка 50–100 тысяч рублей в месяц, инфраструктура одной только шины стоит в 3–9 раз больше всей выручки. Экономика перевёрнута с первого дня, причём независимо от того, какой конец вилки брать.

Для сравнения: **одна ячейка** с общим кластером на 100–200 арендаторов — те же 25–45 тысяч рублей в месяц на всех, то есть 150–450 ₽ на арендатора вместо 25 000–45 000 ₽. Разница в два порядка.

*Оговорка: ставки актуальны на март 2026 и приведены для Yandex Cloud. Перед планированием бюджета перепроверь текущий прайс и посчитай в калькуляторе провайдера — цены пересматриваются, а у Selectel и VK Cloud структура тарификации отличается.*

Операционная сторона хуже финансовой. Обновление версии Kafka — это 500 обновлений. Ротация TLS-сертификатов — 500 раз. Мониторинг — 500 наборов алертов. Ребаланс, деградировавшая реплика, заполнившийся диск — умножается на 500. Один человек это не эксплуатирует, и даже команда из пяти будет заниматься только этим.

Есть и техническая сторона: изоляция, которую даёт отдельный кластер, почти полностью достигается ACL, квотами и ячейками. Дополнительная гарантия сверх этого — «физически другие процессы» — редко стоит трёхкратной стоимости бизнеса.

**Где отдельный кластер оправдан** и где я его сохраняю в архитектуре: как выделенная ячейка для корпоративного клиента, который этого требует и платит за это отдельно; при выходе в юрисдикцию с требованием физического разделения; для клиента, чей объём сам по себе сопоставим с целой ячейкой. Схема ячеек оставляет эту дверь открытой: выделенная ячейка — это тот же шаблон развёртывания на одного арендатора.

### 6.6 Настройки надёжности

Не декоративные, а именно те, без которых Kafka теряет данные при отказах:

**Продюсер:** `acks=all`, `enable.idempotence=true`, `max.in.flight.requests.per.connection=5` (при включённой идемпотентности порядок сохраняется), `retries` большой, `delivery.timeout.ms` осмысленный.

**Топик:** `replication.factor=3`, `min.insync.replicas=2`. Пара «acks=all + min.insync=2» — то, что реально защищает от потери при падении брокера; по отдельности каждая настройка бесполезна.

**Потребитель:** ручной коммит офсетов **после** успешной обработки, никогда не `enable.auto.commit=true`. Идемпотентность обязательна. При ошибке — повтор с экспоненциальной задержкой, после исчерпания — в DLQ с сохранением исходных заголовков и причины.

**Мёртвая очередь.** DLQ без интерфейса бесполезна. Нужен экран: что застряло, по какому арендатору, с какой ошибкой, кнопка «переотправить». Половина инцидентов разбирается здесь.

**Контракты.** Schema Registry с Protobuf и проверкой обратной совместимости на CI. Версия в имени топика (`.v1`). Меняешь событие несовместимо — заводишь `.v2` и какое-то время пишешь в оба.

## 7. Модуль публикации

Именно от него зависит, останутся ли клиенты: площадки — их канал продаж.

```java
public interface MarketplaceAdapter {
    MarketplaceCode code();
    PublishResult publish(TenantId tenant, List<Listing> listings);
    List<ListingStatus> pullStatuses(TenantId tenant);
}
```

Событийный поток: изменение товара → `outbox` → Kafka → потребитель помечает арендатора «грязным» → по расписанию (или по накоплению) собирается фид. Промежуточная агрегация обязательна: пересобирать фид на каждое изменение товара при 50 тысячах позиций бессмысленно.

**Авито.** Модель pull: формируешь XML-фид, выкладываешь по постоянному URL, Авито забирает по расписанию (обновление около часа, до 50 000 объявлений в файле). Пиши потоково через StAX прямо в S3 — материализация 50 тысяч объявлений в DOM съест гигабайты. Обязательно прогоняй через официальный валидатор формата перед публикацией. Отдельная сущность — маппинг твоей номенклатуры на категории и параметры Авито: самая кропотливая часть и главный источник отказов модерации. Для клиента нужен тариф «Расширенный» или «Максимальный» и статус «Компания»; API-ключ создаётся в его кабинете, отдельного партнёрского соглашения тебе не требуется.

**Дром.** Не push и не pull, а **оба сразу** — и это лучшая из доступных схем. Подробный разбор справки: `drom-integration.md`.

*Полный прайс — pull по ссылке.* Кладёшь по постоянному URL в S3, Дром забирает сам: раз в сутки при подключенном платном позиционировании, иначе раз в трое суток, в 00:00 по Владивостоку. Тот же StAX-писатель, что для Авито, другая схема на выходе.

*Дельты — push через API.* `POST multipart/form-data` на `https://baza.drom.ru/good/packet/api/sync`, поля `packetId`, `auth`, `data` (≤ 5 МБ). Мгновенно и без ограничений по частоте: продали деталь — отправили одну позицию с количеством `0`.

`auth` = `hash('sha512', X)`, где X — **ключ, уникальный на кабинет, который Дром выдаёт по запросу**. Логин и пароль клиента не нужны: не проси их и не храни. Ключ шифруется как и всё в `marketplace_account.credentials`.

Лимит 5 МБ относится только к `data`, то есть к дельте. Полный прайс идёт по ссылке и под него не подпадает — резать на пакеты не нужно.

Автообновление по ссылке снимает и вопрос устаревания: пороги у Дрома жёстче, чем принято думать — больше 30 дней без обновления прайс не отображается, на 45-й день товары уходят в архив. При ежедневном заборе по ссылке отдельная задача переподтверждения не нужна вовсе. Дополнительный мотив держать прайс свежим: при равной ставке за просмотр выше в выдаче тот, кто обновился раньше.

Две неприятности, которые надо принять заранее. Первая: **фиксированного формата прайса не существует** — «названия элементов могут быть любыми, мы произведём настройку под ваш формат». Разбор настраивает их техспециалист вручную под каждый прайс-лист. Значит: одна каноническая схема на всех наших арендаторов и шаг онбординга «дождаться настройки на стороне Дрома» — с живым человеком и неопределённым сроком. Пока не настроено, API отвечает `ERROR_REASON_PACKET_NOT_FOUND`. Вторая: **API не возвращает ни статусов позиций, ни замечаний по товарам**, только `200 OK`; всё это живёт в кабинете клиента (см. ниже про экран «что не выгрузилось»).

Приятность в обмен: применимость можно не заполнять самим. При заданных `manufacturer` и `oem_number` Дром подтягивает её из своей базы, для неоригинала ищет кросс. Чего нет в их базе — можно прислать своим каталогом с кроссами, загрузят вне очереди. То есть `catalog.oem_cross` отдаётся Дрому и возвращается применимостью.

**На практике мы её всё-таки отдаём, и это не противоречие.** Их эталон для раздела «Автозапчасти» начинается ровно с требования указать применимость отдельными тегами — марка, модель, кузов, двигатель. Вывести её из номера площадка умеет только для оригинала и только для номера, который знает, а у б/у детали с разборки половина номеров ей неизвестна: без марки позиция не находится фильтром покупателя. Данные у нас есть с самого начала — марка и модель в машине-доноре, у контрактной в `part_applicability`, — и теперь доезжают в прайс. У контрактной детали кузова и двигателя нет намеренно: машина у неё не одна, а подставленный чужой кузов врёт тому, кто именно по нему и подбирает.

**Auto.ru** не нужен: раздел запчастей закрыт с февраля 2022 года.

**JapanCar** — по остаточному принципу, платное размещение по числу объявлений.

С первого дня, потому что потом больно: журнал каждой публикации с телом запроса и ответа, статус по каждому объявлению с текстом ошибки модерации, экран «что не выгрузилось и почему». Половина обращений в поддержку — про это.

Оговорка про этот экран: **по Дрому он из API не наполняется**. Ответ на sync — `200 OK` и всё; статусы прайс-листа (их семь) и «замечания к товарам» с расшифровкой доступны только в кабинете клиента. Значит `listing.status` и `listing.error_text` по Дрому либо остаются пустыми, либо наполняются парсингом чужого интерфейса со всеми его рисками. Реши это до того, как пообещаешь клиентам такой экран по всем площадкам.

## 8. Фотографии

Самая дорогая и самая ломкая часть.

Телефон запрашивает presigned URL и грузит оригинал прямо в S3 мимо бэкенда — это снимает трафик и таймауты на плохой связи. Дальше событие `media.uploaded` → потребитель делает варианты (миниатюра, размер под площадки, ватермарк), сохраняет метаданные, привязывает к товару. Оригиналы — в холодное хранилище, варианты — в горячее.

Считай деньги заранее. Цифры уже не гипотетические: на складе реального клиента в 35 841 позицию — 193 тысячи фотографий, средний размер 138 КБ, **5,4 фото на товар** (замерено по выгрузке, см. `bazon-parity.md` §10). Отсюда на текущих десяти клиентах, 500 тысяч товаров: **около 355 ГБ**, а не 900 ГБ, как оценивалось изначально по 6 фото и 300 КБ. При росте в 50 раз это по-прежнему десятки терабайт и заметная статья расходов. Лимит фото на товар, агрессивное сжатие и жизненный цикл объектов (перевод старого в холодный класс) — не жадность, а экономика продукта.

**Про перенос фото при миграции.** Предыдущая система клиента отдаёт фотографии обычной статикой без авторизации, с `ETag` и `Accept-Ranges` — то есть перенос сводится к обходу списка ссылок из выгрузки и допускает докачку. 25 ГБ одного клиента переносятся примерно за два часа в восемь потоков. Складывай по URL, а не по товару: 2% ссылок повторяются, одно фото бывает привязано к нескольким позициям. И качай, пока подписка клиента у конкурента активна — после отключения доступ к их CDN, скорее всего, пропадёт.

## 9. Развёртывание и эксплуатация

**Старт:** одна ячейка, Docker Compose на VPS в российском ЦОД, 8 vCPU / 32 ГБ (Kafka требует памяти). Kafka в KRaft-режиме, 3 брокера — можно на одной машине для разработки, но для прода лучше три отдельных, иначе `replication.factor=3` не даёт ничего.

**С третьей ячейки:** Kubernetes и Strimzi для Kafka. Раньше — не окупается.

**Postgres:** лучше управляемый, с автоматическими бэкапами и point-in-time recovery. Если сам — `pgBackRest`, ежедневный полный бэкап, непрерывная архивация WAL, копия в другом ЦОД. И обязательно **проверенное восстановление**: бэкап, который ты никогда не разворачивал, бэкапом не является.

**Сделано так** (подробно — `docs/deployment.md`): свой Postgres в ячейке, `ops/backup.sh` снимает дамп **по арендатору**, а не по кластеру — ради этого схема-на-арендатора и выбиралась, из общего дампа одного клиента не поднять, не остановив ячейку. Непрерывной архивации WAL и копии в другом ЦОД пока **нет** — это ближайший долг по эксплуатации, и до первого платящего клиента он терпит, после — нет.

Проверка бэкапа еженедельная и умеет падать: `ops/verify-backup.sh` разворачивает набор в отдельную базу и сверяет остаток, журнал и `part_photo.s3_key`. Отметки у дампа и у проверки **разные**: «дамп снялся» и «клиента можно вернуть» — разные утверждения, и следить надо за вторым. Фотографии бэкапятся зеркалом со своей отметкой: общая сказала бы «бэкап снят» при складе без единой картинки. Полный цикл «снять → уничтожить → развернуть» отрепетирован и занял 4 секунды; до репетиции он не проходил вовсе — расширения Postgres в дампы схем не попадают.

**CI/CD:** сборка, тесты, образ в реестр, миграции как отдельный оркестрируемый шаг, деплой по ячейкам волнами. Feature flags в control plane, чтобы включать незрелое отдельным арендаторам.

**Что мониторить в первую очередь:** лаг потребителей Kafka по группам, глубину `outbox` (растёт — релей встал), возраст самой старой неопубликованной записи, размер DLQ, время генерации фида по арендаторам, долю успешной модерации на площадках, время последнего успешного бэкапа каждой схемы.

### Неделя 0. Разведка

Не пропускай, экономит месяцы. День на двух-трёх разборках: как идёт приёмка, как ищут деталь по звонку, как оформляют продажу. Операции, повторяющиеся десятки раз в день, и составляют MVP.

Параллельно — главный технический вопрос: **выгружаются ли их текущие базы**, включая фотографии и применимость. Если фото не отдаются, план миграции меняется целиком, и узнать это надо сейчас, а не на неделе 15.

И возьми предоплату за пилот. «Мы перейдём» — не обязательство.

### Недели 1–3. Платформа

Проект, Docker Compose с Postgres и Kafka, CI. Control plane: реестр арендаторов, ячейки, маршрутизация. Провижининг арендатора: создание схемы, накат миграций, бакет, топики. Оркестратор миграций по схемам с состоянием и продолжением после сбоя. Перехватчик транзакции, выставляющий `SET LOCAL search_path`, и тест на перемешанные транзакции через один пул. Аутентификация, роли, филиалы. Аудит-лог на триггерах.

*Готово, когда:* новый арендатор создаётся одной командой за минуты, а тест на изоляцию через PgBouncer зелёный.

**Сделано, с двумя отличиями.** Арендатор создаётся одним запросом
(`POST /api/provisioning/tenants`) и получает заодно филиал и первый склад.
Аудит-лог **не на триггерах**, а на слушателе Hibernate: логика живёт в Java,
а неизменяемость журналов держат права роли `partsflow_app`
(`docs/triggers-to-java.md`). PgBouncer не поднят — пул внутри приложения,
но сброс `search_path` при возврате соединения сделан и стережётся тестом.

### Недели 4–5. Событийный контур

`outbox`, релей, `DomainEventPublisher` и `EventTransport` с двумя реализациями (in-memory и Kafka). Schema Registry, Protobuf-контракты, проверка совместимости на CI. Базовые топики, consumer groups, идемпотентность потребителей, DLQ с экраном разбора. Метрики лага и глубины outbox.

*Готово, когда:* убийство брокера под нагрузкой не теряет ни одного события, а перезапуск потребителя не приводит к двойной обработке. Проверяется тестом с Testcontainers и принудительным падением.

**Сделано, кроме контрактов.** Outbox, релей, два транспорта, идемпотентность
через `processed_event`, разбор недоставленного с повтором и экраном
«Доставка», метрики глубины и возраста очереди. Проверено на двух работающих
экземплярах: 40 событий — 40 обработок, ноль дублей. **Schema Registry
и Protobuf не заведены**: потребитель пока один и лежит в этом же
репозитории.

### Недели 6–7. Каталог и справочники

Марки, модели, поколения, кузова, категории узлов в общей схеме. Товар с характеристиками, состоянием, ценой, OEM и кросс-номерами. Применимость. Поиск на FTS и `pg_trgm`.

Наполнение справочников — отдельная задача, не откладывай: без нормального дерева марок и моделей продукт не работает, а быстро его не собрать.

**Сделано, и оказалось больше работы, чем строчка в плане.** Дерево машин
собрано из каталога площадки (308 марок, 4 354 модели, 12 430 поколений).
Справочник видов деталей писался руками и дополнялся по живому складу
дважды: 178 эталонов стало 376, плюс 519 сопоставлений, разобранных
глазами. Итог на живом складе — вид детали есть у 34 183 позиций
из 35 841. Отдельно понадобился словарь русских написаний марок и моделей:
без него продавец набирает «камри» и не находит ничего.

### Недели 8–9. Приёмка

Донор: VIN, марка, модель, год, стоимость покупки и расходы. Занесение с телефона: камера, автоподстановка из справочников, шаблоны типовых деталей. Пакетное занесение, импорт из Excel. Офлайн-очередь в IndexedDB с досылкой.

*Готово, когда:* приёмщик заносит деталь с телефона быстрее, чем в текущей системе. Замерь секундомером на реальной разборке — это главный продуктовый показатель.

**Сделано; секундомером на живой разборке пока не мерено** — это к пилоту.
Офлайн-часть проверена обрывом, а не рассуждением: приложение остановлено
на середине партии, перезагрузка без сервера открылась на запомненной
личности, после подъёма сессия оказалась потеряна, очередь встала
и попросила войти, после входа партия ушла — одна позиция при шести
неудачных попытках, сверки пусты.

### Недели 10–12. Выгрузки

Критический путь. Авито: генератор XML на StAX, маппинг категорий и параметров, публикация в S3, валидатор, экран статусов и ошибок. Дром: канонический XML-прайс по постоянному URL плюс sync-endpoint для дельт, шифрованный ключ кабинета, заявка на подключение API и настройка разбора на их стороне (закладывай срок с запасом — там живой человек). Наценки, скидки, правила заголовков и описаний. Всё — через события и воркеры.

*Готово, когда:* объявления реального клиента живут на обеих площадках неделю без твоего вмешательства, а ошибки модерации видны ему в интерфейсе.

**Сделан Дром; Авито отложено решением владельца продукта.** Генератор фида
Авито и резолвер маппинга написаны, но наружу не отданы и доводить их
сейчас не нужно. По Дрому: прайс по постоянной ссылке, несколько прайс-листов
на кабинет со своим отбором у каждого, дельты по API, прайс колёс отдельным
форматом. Отбор выгрузки владелец настраивает сам теми же колонками, какими
смотрит склад. Чего **нет**: автоматического приёма заказов (ключ Дром
выдаёт по заявке) и недели живой работы у клиента — это пилот.

### Недели 13–14. Склад

Ячейки хранения, генерация этикеток со штрих-кодами и печать на термопринтере, сканирование камерой, перемещения между складами и филиалами, инвентаризация с расхождениями. Остаток — агрегат журнала движений, а не изменяемое поле.

**Сделано полностью.** Печатает браузер, а не драйвер принтера: команды ZPL
привязали бы нас к модели, а у первых клиентов они разные. Штрихкод рисуется
в SVG — растр, растянутый с экранных 96 точек до принтерных 203, читается
через раз. Адреса ячеек, которые Code128 не кодирует («Б», «Г», «Д»),
помечаются и не выбираются: подставить похожую латинскую нельзя, деталь
ляжет на другой стеллаж. Инвентаризация сравнивает факт с учётом **на момент
подсчёта строки**, а не на открытие сессии и не на проведение, — иначе
пересчёт портит склад ровно тем действием, которым его сверяют.

### Недели 15–16. Продажи и пилот

Сделки, резервирование, скидки, частичная оплата, возвраты с возвратом в остаток, история по клиенту, отправка ссылки в Telegram или SMS. Кассовые чеки через оператора (АТОЛ Онлайн, Модулькасса) — дольше, чем кажется, из-за 54-ФЗ; в MVP допустимо оставить продажу без фискализации.

Инструмент миграции: импорт из Excel, из выгрузки Авито, из экспорта текущей системы — с фото и применимостью.

**Сделано, кроме фискализации.** Продажи закрыты целиком: сделка с резервом,
выдача, оплата с переплатой на лицевой счёт, возврат документом, перенос
позиций, ссылка клиенту на его покупку, заказы с площадки. Переезд с прежней
системы — три файла (машины, товары, колёса) плюс отдельный проход
за фотографиями: замерено на живой выгрузке, 35 841 позиция и 440 машин
за 68 секунд. Фискализация не сделана намеренно: она начинается с договора
с оператором, а не с кода (`docs/fiscal-54fz.md`).

**Пилот на двух клиентах, не на десяти.** Разложи их по разным ячейкам. Десять компаний из одного города общаются между собой: одна потерянная база — и сарафан работает против тебя необратимо.

### Недели 17–24. Остальное и масштабирование

Интернет-магазин на поддомене клиента: каталог из остатков, генерируемые ссылки-подборки по марке и модели (по отзывам рынка заметно влияет на продажи), онлайн-оплата. Аналитика: окупаемость каждого донора, отчёты по сотрудникам, продажи по менеджерам для расчёта зарплат — на отсутствие этого прямо жалуются пользователи Bazon, так что это дифференциатор. Подключение остальных клиентов волнами, биллинг и тарифы, вторая ячейка.

### Дальше: чем обгоняешь, а не догоняешь

Распознавание запчасти по фото с определением детали и подсказкой OEM — резко ускоряет приёмку, у Bazon этого нет. Автогенерация описаний объявлений языковой моделью. Открытый API и вебхуки для интеграций с 1С и доставками — здесь событийная шина, построенная на неделях 4–5, окупается сразу. Прозрачный самообслуживаемый тариф для мелких разборок — сегмент, который лидер обслуживает плохо.

## 11. Риски

**Kafka куплена авансом.** Честно: на десяти клиентах очередь на Postgres справилась бы, и первые месяцы шина будет выглядеть избыточной. Это осознанная ставка на быстрый рост. Она оправдана тем, что переход с очереди на шину задним числом требует переписывания всех потребителей, а `outbox` + абстракция транспорта дают возможность в любой момент откатиться на простой релей без Kafka, если рост не случится.

**Модерация Авито.** Фид может работать годами и сломаться от изменения требований категории. Это постоянная операционная работа, а не разовая задача, и именно на ней держится ценность продукта.

**Миграции по сотням схем.** Самый вероятный источник ночного инцидента. Оркестратор, канареечный выкат и `lock_timeout` — обязательны с первого дня, а не когда станет больно.

**Миграция данных клиентов.** Если фото из старой системы не выгружаются, перенос превращается в многодневную ручную работу на каждого клиента. Выясняй на неделе 0.

**Ты — единственная точка отказа.** Десять компаний зависят от твоей доступности, а Kafka и ячейки повышают требования к квалификации эксплуатации. Минимум: понятный SLA, автоматические бэкапы с проверкой восстановления, документация по развёртыванию. Со второго-третьего клиента думай о напарнике.

**Соблазн сделать всё.** Bazon строился десять лет. Твой шанс не в паритете по числу фич, а в том, чтобы три-четыре ежедневные операции работали заметно лучше.
