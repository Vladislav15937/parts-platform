# Кнопка раскатки: ИФТ, ПСИ, ПРОМ

Как выложить версию на стенд, ничего не набирая в терминале. Задача 0075,
решение владельца продукта от 12 сентября 2026: «сейчас для меня самое
главное обеспечить непрерывную поставку желательно одной кнопкой
с возможностью выбора на какой стенд».

Jenkins для этого не заводили — тем же решением: параметризованный запуск
даёт `workflow_dispatch`, а второй сервис пришлось бы держать правдивым
(плагины, секреты, обновления, бэкапы).

---

## Что человек делает

1. Открывает на GitHub вкладку **Actions → «Выкладка на стенд» → Run
   workflow**.
2. Заполняет форму — четыре поля, все списками, кроме одного:

   | Поле | Что выбирают |
   |---|---|
   | **Стенд** | `ift` · `psi` · `prom` |
   | **Ветка или SHA** | любая ветка для ИФТ; для ПСИ и ПРОМ — **только полный SHA**, слитый в `main` и зелёный |
   | **Миграции** | `накатить` · `не трогать` · `только миграции` |
   | **Данные** | `не трогать` · `обезличенный слепок прома` · `эталонный набор` |

3. Нажимает **Run workflow**.
4. Через полминуты видит результат первой задачи — «Проверки перед
   выкладкой». Если что-то не так (ветка на ПСИ, красный CI, образа нет
   в реестре), выкладка останавливается **здесь**, не тронув стенда,
   и говорит, что именно не так.
5. Дальше идёт сама выкладка. На **ПРОМ** она ждёт подтверждения владельца
   (GitHub Environments, required reviewer) — исполнитель задачи на ПРОМ
   не выкладывает ни разу.
6. В конце открывает страницу прогона и видит табличку: стенд, версия,
   откуда, что стояло до этого, кто нажал, миграции, данные, итог. Плюс
   посчитанный план по схеме — куда она поехала и что потеряла бы откат.

**Что видно в конце удачной выкладки.** Под трафиком новая сборка, старая
погашена, четыре самопроверки зелёные. **Что видно в конце неудачной** —
строка, называющая, что упало («прайс ПУСТ: ни одного `<offer>`»), и трафик
**на прежней сборке**: она всё это время работала и людей не теряла.

## Что происходит после нажатия

```
    ┌ проверки, не трогающие стенд ────────────────────────────┐
    │  ветка/SHA разобраны · правила стенда · зелёный CI        │
    │  образ лежит в реестре · инструменты проверили себя       │
    └───────────────────────────────────────────────────────────┘
                              │  (ПРОМ: подтверждение владельца)
    ┌ на стенде ───────────────────────────────────────────────┐
    │ 0. что сейчас стоит      APP_IMAGE_TAG из .env стенда     │
    │ 1. план по ДВУМ версиям  tools/deploy-plan.py             │
    │ 2. настройки того же SHA rsync ops/ и compose             │
    │ 3. схема                 ops/schema-sync.sh               │
    │ 4. новая сборка РЯДОМ    docker compose up -d app-green   │
    │ 5. готовность            /actuator/readiness              │
    │ 6. трафик                ops/switch-build.sh — caddy reload│
    │ 7. четыре самопроверки   ops/deploy-checks.sh             │
    │ 8. и только теперь       stop app-blue                    │
    └───────────────────────────────────────────────────────────┘
```

Порядок — решение владельца от 12 сентября 2026, дословно: «Прогоняется
миграция, база поднялась без проблем, ошибок нет, само приложение встало
штатно, всё в порядке и только тогда можно убирать старую сборку и ставить
новую и красить её в зелёный».

**Упавший шаг 5 или 7 возвращает трафик на старую сборку.** Она ещё
работает, возврат мгновенный — это и есть причина, по которой её не гасят
раньше. Возврат идёт с принуждением (`ops/switch-build.sh <прежняя>
--force`): сборка, только что обслуживавшая людей, могла перестать быть
«готовой» из-за опущенной схемы, и отказ вернуть трафик оставил бы людей
на той, которая проверок не прошла.

## Чем мигрировать — знают обе версии, а не одна

Шаг миграции (`ops/schema-sync.sh`, задача 0073) знает только целевую
версию: «привести схемы к версии этого образа». Вверх этого хватает, вниз
нет.

**Образ версии 100, встретив схему 103, опустить её не может физически.**
Тела `--rollback` для changeset'ов 101–103 лежат в чужом jar, а
`rollbackCount` их не видит вовсе и снял бы вместо них последние **свои**.
0073 такую схему не трогает, называет по имени и возвращает ненулевой
код — поведение правильное, но требование владельца («не должно быть
такого, чтобы версия приложения была 100, а база соответствовала
версии 103») само по себе оно не выполняет.

**Выполняется оно порядком шагов**, и порядок считает `tools/deploy-plan.py`:

| Куда идёт схема | Чем мигрируем | Почему |
|---|---|---|
| вверх (100 → 103) | образом **выкладываемой** сборки | новые changeset'ы есть только в нём |
| вниз (103 → 100) | образом **развёрнутой сейчас** сборки, `--to 100` | тела откатов есть только у неё |
| версия не меняется | выкладываемой | накат будет пустой операцией |

То есть **мигрируем старшим образом, разворачиваем младший.**

Версию считает git, а не запущенный контейнер: версия образа — это число
changeset'ов набора арендатора в том коммите, из которого он собран
(`TenantSchemaMigrator.totalChangeSets`). Разбор changelog'а при этом
не свой — берётся `read()` из `db/rollback-cost.py`, чтобы порядок наката
считался одним выражением на весь проект.

**Цена отката печатается до нажатия.** Структурно верный откат теряет
данные молча (`db/rollback-cost.py`, задача 0082), и план выводит его
список прямо в лог прогона:

```
Откат с версии 138 до версии 134: 4 changeset'а, из них теряют данные 1.
  • tenant/066-company-settings.sql::tenant-066-company-settings
      теряется: срок резервирования, заданный владельцем …
```

**Чего этот порядок не убирает.** Выкладка вниз на минуты оставляет
старшую сборку (она ещё под трафиком) на уже опущенной схеме. Порядок
задан владельцем именно так; уменьшить окно можно было бы, опуская схему
**после** переключения, но это решение не исполнителя — вопрос назван
в задаче 0075 и в теле PR.

> **Путь ПРОМ не окончательный.** Решением владельца от 14 сентября 2026
> база на ПРОМ поедет **копией вместе со сборкой**, а откат станет
> «остаться на старой базе» — то есть перестанет быть миграцией вниз
> вовсе (задача 0112, `tasks/0112-baza-edet-vmeste-so-sborkoy.md`).
> До неё ПРОМ идёт тем же путём, что и стенды. Раздел выше остаётся верным
> для ИФТ и ПСИ при любом исходе 0112. **Исполнитель задачи 0075
> на ПРОМ не выкладывает ни разу.**

## Четыре самопроверки, без которых это не выкладка

`ops/deploy-checks.sh`, уже на переключённой сборке. До этого их делали
глазами (`docs/pilot-server.md`, «Повседневные команды»), то есть
не делали в половине случаев.

| # | Проверка | Чем спрашивается | Чего не допускает |
|---|---|---|---|
| 1 | приложение отвечает 200 | `GET /` **через терминатор**, по настоящему домену | выкладка «удалась», а страница не открывается |
| 2 | журналы защищены | `journals` в `/actuator/readiness` | ячейка работает одной ролью, журналы снова изменяемы — а разница видна в тот день, когда журнал предъявляют как доказательство |
| 3 | отставших схем ноль | `ops/migrate-tenants.sh` (deep=true, каждая схема) | код рассчитывает на миграцию, которой у арендаторов нет |
| 4 | прайс не пуст | число `<offer>` в выгрузке | пустой прайс площадка читает как «снять всё» — худший исход выкладки |

Каждая красит выкладку и **называет себя по имени** в итоговой строке:
«Самопроверки не прошли: прайс не пуст». Молча зелёный деплой, после
которого прайс пуст, хуже упавшего.

Первая идёт тем же путём, которым ходит человек, и заодно доказывает, что
трафик действительно переключился. Вторая и третья не читают лог и не верят
отметке в реестре: лог ротируется, отметка врёт, если в схему лазили руками.
Третья не пишет своего запроса — зовёт `ops/migrate-tenants.sh`, который
уже умеет обращаться с секретом так, чтобы тот не попал ни в адрес, ни в `ps`.

**Четвёртой нужны ссылки на прайсы, и без них она краснеет.** Их кладёт
на стенд сама кнопка (секрет `DEPLOY_FEED_URLS`), файлом под `umask 077`:
в постоянной ссылке зашит токен выгрузки. Стенду, где выгрузок нет вовсе,
ставят значение `нет` — тогда проверка говорит об этом вслух и пропускается.
Пустое значение пропуском не считается: непроверенный прайс и есть та беда,
ради которой проверка написана.

## Поле «Данные»: два значения сегодня отказывают

Форма названа владельцем дословно, и двух её значений в системе **нет**:

- **«обезличенный слепок прома»** — обезличивания не написано вовсе. Ни один
  файл ячейки не умеет снять с ПРОМ слепок без персональных данных, а возить
  его как есть нельзя: это данные клиента на стенде тестировщика.
- **«эталонный набор»** — `db/seed` наполняет справочники (марки, модели,
  виды деталей), но склада, сделок и денег там нет; это не тот набор,
  на котором проверяют сценарии.

Выбравшего любое из двух выкладка останавливает **до единого изменения**
и объясняет, чего нет. Молча не сделать ничего было бы хуже всего:
тестировщик увидел бы зелёную выкладку и смотрел вчерашние данные, считая
их сегодняшним слепком. Чем это закрывать — вопрос владельцу продукта
(назван в задаче 0075 и в теле PR).

**Сам эталонный набор теперь есть, а кнопка к нему ещё не привязана**
(задача 0076). `tools/ift-etalon.py вернуть` сносит эталонную компанию
и раскладывает её заново через API — шесть ролей, склад, сделки, краевые
случаи, — и отказывается работать не на ИФТ. Выкладка на значении
«эталонный набор» по-прежнему останавливается: привязка — это правка
этого прогона и доставка скрипта на машину стенда. Что в наборе и почему
так — `docs/ift-etalon.md`.

## Что должно быть на стенде

Машины, домены и секреты стендов заводит владелец — это не работа
исполнителя задачи. Кнопка на них **нацеливается**, и вот чем.

**Окружения GitHub** (Settings → Environments): `ift`, `psi`, `prom`.
У `prom` — **required reviewer**, иначе подтверждения владельца не будет.

**Секреты окружения:**

| Секрет | Что это |
|---|---|
| `DEPLOY_SSH_HOST` | адрес машины стенда |
| `DEPLOY_SSH_USER` | пользователь (по умолчанию `deploy`) |
| `DEPLOY_SSH_KEY` | закрытый ключ для входа |
| `DEPLOY_SSH_KNOWN_HOSTS` | отпечаток хоста. Не задан — берётся на месте, и прогон говорит об этом предупреждением; **на ПРОМ так нельзя**: принять любой ключ значит согласиться отдать секреты тому, кто перехватил адрес |
| `DEPLOY_FEED_URLS` | постоянные ссылки на прайсы через пробел, либо слово `нет` |

**Переменные окружения** (vars, не секреты): `STAND_URL` — адрес стенда
для ссылки на странице Environments; `DEPLOY_PATH` — каталог ячейки
(по умолчанию `parts-platform`); `DEPLOY_SSH_PORT`.

**На самой машине** — то же, что у пилотной ячейки (`docs/pilot-server.md`):
каталог с `docker-compose.prod.yml`, каталогом `ops/` и заполненным `.env`.
Ни исходников, ни Dockerfile, ни JDK: ячейка ничего не собирает
(задача 0074).

**Что кнопка на стенде не трогает:** `.env` (секреты стенда — кроме тегов
образов, которые она и ведёт), `ops/active-build.caddy` (имя сборки под
трафиком — это состояние ячейки; перезаписав его версией из репозитория,
выкладка объявила бы активной синюю, и накат схем ушёл бы не в ту сборку)
и `ops/secrets/`.

## Откуда берутся инструмент и настройки — это разные ответы

**Настройки ячейки** (`ops/` и `docker-compose.prod.yml`) едут **того же
SHA, что и образ** — задача 0111. Иначе на машине окажется код одной версии
и конфигурация терминатора другой, и этому не препятствует ничто: `git pull`
на боевой машине тянул произвольный свежий `main`.

**Инструмент выкладки** (`tools/deploy-plan.py`) берётся с той ветки,
на которой нажали кнопку. Откатываясь на старый коммит, мы обязаны иметь
сегодняшний планировщик, а в том коммите его может не быть вовсе.

Отсюда следствие, которое надо знать: **выложить кнопкой можно только
версию, в которой есть `ops/deploy.sh`** — то есть коммит не старше самой
кнопки. Более старую выкладывают руками, по `docs/pilot-server.md`,
«Повседневные команды». Прогон говорит об этом прямо, а не падает
на пропавшем файле.

## Прозрачность — это запись, а не кнопка

«Что сейчас на ПСИ» обязано отвечаться без расспросов, и отвечают на это
три места:

- **страница Environments** — кто и когда выкладывал на каждый стенд;
- **итог прогона** (Summary) — стенд, версия, откуда, что стояло до, кто
  нажал, миграции, данные, результат и посчитанный план по схеме;
- **`deploy-history.log` на самой машине** — строка на каждую выкладку,
  включая неудачную: с ними как раз и разбираются.

```
2026-09-13T20:57:43Z  ift  bbbb…  tester  выкладка         миграции: apply  успех
2026-09-13T20:58:44Z  ift  aaaa…  tester  выкладка         миграции: apply  самопроверки не прошли
2026-09-13T20:59:18Z  ift  aaaa…  tester  только миграции  миграции: only   успех
```

## Руками, без кнопки

Всё то же самое делает `ops/deploy.sh` на самой машине — кнопка только
считает план и заходит по ssh:

```bash
ops/deploy.sh --tag <SHA>                                   # обычная выкладка
ops/deploy.sh --tag <SHA> --migrations «не трогать»         # код без схемы
ops/deploy.sh --tag <SHA> --migrations «только миграции»    # схема без кода
ops/deploy.sh --tag <SHA> --migrate-with current --to 134   # откат вниз
ops/deploy.sh --tag <SHA> --dry-run                         # напечатать шаги
```

Версии при этом придётся назвать самому: git на стенде не нужен и его там
нет. Посчитать их можно у себя — `./tools/deploy-plan.py --current <SHA>
--target <SHA>`.

## Что проверяет себя само

Четыре самопроверки без стенда и без docker, в задаче CI «Развёртывание»:

```bash
./tools/deploy-plan.py --selftest   # «старшим образом» — правило отката
./ops/deploy-checks.sh --selftest   # каждая из четырёх краснеет на своём дефекте
./ops/deploy.sh --selftest          # ПОРЯДОК: старая гаснет последней
./ops/switch-build.sh --selftest    # разбор и запись имени активной сборки
```

Проверка, которая не краснеет на дефекте, хуже отсутствующей: каждая
из четырёх проверена подделкой — см. тело PR задачи 0075.
