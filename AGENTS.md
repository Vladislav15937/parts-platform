# parts-platform — инструкции Codex

Учётная SaaS для авторазборок. Общаемся и пишем объясняющие причины комментарии
на русском; идентификаторы кода — на английском.

## Как получить контекст

Этот файл — короткая точка входа. `CLAUDE.md` и `.claude/` остаются общим
источником предметных знаний и договоров: их читают оба инструмента.
Ссылка на документ не означает, что его содержимое уже загружено.

Перед первой правкой прочитай целиком `CLAUDE.md`, `docs/agent-workflow.md`
и `docs/codex.md`. Большие файлы читай частями без пропусков; обрезанный вывод
не считается прочитанным. Перед работой с конкретными файлами выполни:

```sh
python3 tools/codex-context.py <путь> [<ещё-путь> ...]
```

Прочитай перечисленные памятки, правила и вложенные `AGENTS.md`. Это нужно
и при запуске из корня: стартовая цепочка Codex зависит от рабочего каталога,
а не от всех файлов, которые планируется править. Если область работы
расширилась, запроси контекст для новых путей. Для Java-тестов прочитай также
памятку соответствующего модуля `src/main/java/ru/partsflow/<модуль>/CLAUDE.md`.
Не обходи `.claude/worktrees/`, `node_modules/`, `target/`, `dist/` при поиске.

## Неизменяемые решения

- Модульный монолит Java 21 / Spring Boot, React / TypeScript / Vite.
  Модули общаются интерфейсами и событиями, не чужими репозиториями.
- PostgreSQL: схема на арендатора. Доступ к ней только внутри транзакции;
  одного `TenantContext` недостаточно. Не ослабляй изоляцию и её тесты.
- События пишутся в outbox в одной транзакции с данными; не отправляй их
  прямо в Kafka из бизнес-кода.
- Бизнес-логика живёт в Java. Остатки меняет `StockLedger`; новые бизнесовые
  триггеры не добавляются. Миграции только Liquibase, применённые changeset'ы
  неизменяемы целиком, включая комментарии и rollback.
- Повторы приёмки и фото идемпотентны. Журналы неизменяемы. Внутренние ID
  и технические ошибки не показываются человеку.
- Авито отложено владельцем; текущая выгрузка — Дром. Не принимай продуктовые
  решения за владельца и не придумывай его ответы.

## Порядок работы

В свежей сессии используй `nachalo-smeny`; для реализации задачи —
`tsikl-zadachi`. Точки входа лежат в `.agents/skills/`. `uborka` и `vykladka`
вызываются только по явному запросу человека. Скилл не даёт дополнительных
разрешений на публикацию, удаление или доступ к серверу.

Перед изменениями запускай `./tools/can-start.sh` без пайпа; отдельно проверяй
нынешний SHA `origin/main` через `tools/head-green.sh`. Нет доступа к GitHub —
это отсутствие результата, а не зелёный CI. Не подменяй проверку самопроверкой.

Зелёный CI не означает свежую рабочую базу. После fetch отдельно сравни
`HEAD` с `origin/main`: новая работа начинается от актуальной `origin/main`.
Отстающую локальную `main` обновляй fast-forward, предварительно проверив
пересечение входящих изменений с незакоммиченной работой. Незакоммиченные
правки сохраняй; не используй reset, принудительный checkout или автоматический
stash. Для уже начатой ветки проверь включение актуальной `origin/main`
через `git merge-base --is-ancestor origin/main HEAD`; при отставании сначала
согласуй изменения с новой базой. Одна проверка исторически зелёной головы
или сообщение `tools/can-start.sh` не заменяют эту сверку.

Распределение ролей, волн, задач и право слияния — `docs/agent-workflow.md`;
перевод механизмов Claude на Codex — `docs/codex.md`. Не запускай дирижёра,
разведку или волну без запроса человека. Для делегирования используй договор
соответствующей роли; каждый, кто коммитит или ломает код для проверки,
работает в отдельном проверенном git worktree. Codex сам worktree не создаёт
при обычном запуске субагента. Мигратор один. Автор не заменяет независимый
`reviewer`. Слияние кода требует CI и вердикта на том же полном SHA головы.

На ПРОМ сессия и агенты не заходят: готовят человеку однострочную команду.
Не меняй чужую систему. Не удаляй чужие worktree и не запускай Docker prune.
Секреты из `.env`, ключей, токенов и файлов стенда не выводи в контекст.

## Проверка и документация

- Бэкенд: `./mvnw -o test`; фронтенд из `frontend/`: `npm test` и
  `npm run build`. Недостающие зависимости не скрывай как успешную проверку.
- Схема: `./db/verify.sh`; живой сценарий, если изменение видно человеку:
  `tools/dev-up.sh`, `tools/checks.sh`, `tools/smoke.sh` по договору задачи.
- Правила Java — `docs/java-rules.md`, экранов — `docs/frontend-rules.md`.
  Для инструментов выполняй их документированные самопроверки.
- Находки записывай в памятку модуля. Новые возможности — в §12
  `docs/bazon-parity.md`. Доска и формат PR — `tasks/README.md`.
- При изменении интеграции Codex: `python3 tools/codex-context.py --check`,
  `python3 tools/codex-context.py --selftest` и проверка настоящего стартового
  запроса `python3 tools/codex-context-probe.py` (нужен Codex CLI).

В отчёте различай: файл найден, инструкция автоматически передана,
документ прочитан инструментом, проверка исполнена. Не утверждай, что
Claude-хуки, его MEMORY.md, разрешения или ограничения tools действуют в Codex.
