# Миграции БД на Liquibase

Схема-на-арендатора, общий каталог, независимое версионирование каждого клиента.

## Быстрый старт

```bash
docker compose up -d
./verify.sh          # полная проверка на чистой базе
```

## Структура

```
changelog/
  db.changelog-catalog.xml    — общий каталог ячейки, один раз на базу
  db.changelog-tenant.xml     — схема арендатора, на каждого клиента
  catalog/001…019.sql         — formatted SQL changelogs: справочники машин,
                                видов деталей, написаний
  tenant/001…057.sql          — схема клиента: склад, продажи, выгрузки
seed/                         — сборка справочников из данных, см. seed/README.md
liquibase-catalog.properties
liquibase-tenant.properties
docker-compose.yml            — отдельная база под verify.sh
verify.sh                     — прогон и проверка инвариантов
```

## Запуск

Каталог — один раз на базу данных ячейки:

```bash
liquibase --defaults-file=liquibase-catalog.properties update
```

Арендатор — при провижининге и при каждой миграции:

```bash
liquibase --defaults-file=liquibase-tenant.properties \
          -Dtenant.schema=t_000042 \
          --default-schema-name=t_000042 \
          --liquibase-schema-name=t_000042 \
          update
```

## Почему именно так

### DATABASECHANGELOG внутри схемы арендатора

`liquibaseSchemaName` равен схеме арендатора — это ключевое решение, и оно даёт три вещи сразу.

Каждый клиент версионируется независимо, поэтому неудачная миграция у одного не блокирует остальных. Дамп схемы (`pg_dump -n t_000042`) забирает и данные, и историю миграций одним самодостаточным куском — восстановление клиента не требует ничего извне. И, что важно при сотнях арендаторов, `DATABASECHANGELOGLOCK` тоже свой у каждого, поэтому миграции разных клиентов гонятся параллельно без взаимных ожиданий.

Если бы changelog жил в одной общей схеме, всё это ломалось бы: общий лок сериализовал бы прогон по всем клиентам, а дамп одного арендатора терял бы историю версий.

### Formatted SQL, а не XML-теги

Схема плотно использует возможности Postgres, которых нет в абстракциях Liquibase: частичные индексы, индексы по выражению, GIN и GiST, `ltree`, `jsonb`. Описывать это через `<createTable>` невозможно, а смесь из XML-тегов и `<sql>`-вставок хуже читается, чем однородный SQL.

Ранние changeset'ы заводят ещё триггеры, функции и генерируемые колонки — их в схеме больше нет, но changeset неизменяем, поэтому история проигрывается как была, а `tenant/050` и `tenant/051` снимают их следом. Что чем стало — в `docs/triggers-to-java.md`.

Плата за выбор — Liquibase не сможет сгенерировать rollback автоматически, поэтому у каждого changeset'а `--rollback` написан руками. Проверено скриптом: changeset без rollback в наборе нет.

### Явная квалификация `${tenant.schema}`

Все объекты квалифицированы именем схемы, хотя `--default-schema-name` вроде бы избавляет от этого. Причина: для raw SQL Liquibase не подставляет схему сам, а полагаться на `search_path` между changeset'ами нельзя — границы транзакций не гарантированы. Неявная схема здесь означает риск однажды создать таблицу не тому арендатору. Многословно, зато детерминированно.

### `splitStatements:false` для функций

Liquibase режет SQL по `;`, а тело plpgsql-функции содержит точки с запятой внутри. Без этого атрибута любая функция ломается на полуслове. Дополнительно везде используются именованные долларовые теги (`$fn$`), а не голые `$$` — так тело не конфликтует с парсером и вложенными блоками.

### `runOnChange:true` для функций и представлений

Функции и вью переопределяются через `CREATE OR REPLACE`, поэтому их можно править в том же changeset'е: Liquibase увидит новую чек-сумму и накатит заново. Для таблиц так делать нельзя — только новый changeset.

## Правила, которые обеспечивают консистентность стендов

**Никаких contexts на структурных изменениях.** Contexts и labels допустимы только для тестовых данных (`context="dev"`). Если структура зависит от стенда, стенды разъедутся — а именно этого мы избегаем. Один и тот же changelog накатывается везде без исключений.

**Changeset неизменяем после первого прогона.** Отредактированный changeset ломает чек-сумму и валит деплой (`strict=true` включён намеренно). Исправление — только новым changeset'ом. `validCheckSum` — аварийный люк, а не рабочий инструмент.

**Expand–contract.** Изменения только обратно совместимые: добавили nullable-колонку → выкатили код, понимающий обе формы → заполнили данные → отдельным релизом убрали старое. Никогда не выкатывай схему и требующий её код одновременно.

**Индексы на живых таблицах — `CONCURRENTLY` и `runInTransaction:false`.** В шаблоне провижининга это не нужно (таблицы пустые), но любая последующая миграция обязана это соблюдать, иначе индекс на таблице крупного клиента заблокирует ему работу.

**Таймауты.** `lock_timeout=5s` и `statement_timeout` задаются в JDBC-URL. `ALTER TABLE`, взявший тяжёлую блокировку в разгар рабочего дня, положит клиенту работу — лучше упасть быстро и повторить ночью.

## Оркестратор миграций

Написан и работает: `TenantMigrations` на Liquibase Java API, а не вызовы CLI. Он идёт по `public.tenant_registry`, накатывает каждую схему, отмечает `schema_version` и отдаёт список отставших. Снаружи это два пути под секретом `app.provisioning-token`:

```bash
ops/migrate-tenants.sh          # накатить и упасть, если кто-то отстал
```

Скрипт ходит внутрь сети compose (`http://app:8080` из контейнера терминатора), а не на `localhost`: порт приложения у ячейки намеренно не опубликован. Шаг развёртывания падает, если после наката остался хоть один отставший.

**`schema_version` в реестре — индикатор, а не истина.** Он врёт, если в схему лазили руками: отметка на месте, объекта нет. Поэтому и накат, и проверка перед выкладкой спрашивают сам Liquibase (`pendingCount`), а отметку только обновляют. На актуальной схеме это один SELECT из её `DATABASECHANGELOG`.

Отметку в реестре ставит **владелец схем**, а не рабочая роль: прав на `UPDATE public.tenant_registry` у неё нет и быть не должно, и пока накат шёл ею, все арендаторы объявлялись отставшими.

Порядок выката — expand/contract: сначала совместимая миграция, потом накат по всем схемам, потом код. Расхождение версий видно одним запросом:

```sql
SELECT schema_version, count(*) FROM public.tenant_registry GROUP BY 1;
```

Если групп больше одной дольше, чем идёт выкат, — это инцидент.

Своего журнала прохода у оркестратора нет намеренно: состояние лежит в `DATABASECHANGELOG` каждой схемы, а второй источник правды с ним разойдётся.

## Что проверяет `verify.sh`

Семь шагов на **чистой базе**: каталог накатывается, два арендатора провижинятся независимо, `DATABASECHANGELOG` каждого лежит в его схеме, данные арендаторов не пересекаются, повторный `update` идемпотентен, `rollback` отрабатывает до пустой схемы.

Шаг 5 — то, за что база отвечает **после** переноса логики в код: умолчание публичного кода, `part_stock_reserved_ck` (резерв больше остатка), каскады, три сверки (`v_stock_discrepancy`, `v_reservation_discrepancy`, `v_account_discrepancy`) и, главное, отсутствие в схеме арендатора **триггеров, функций и генерируемых колонок**. Это правило «логика только в приложении», проверяемое, а не декларируемое. Поведение остатка, аудита и неизменяемости журнала теперь проверяют тесты приложения, а не миграции.

Шаг 7 — единственное место, где вообще выполняется откат: ни тесты, ни живая работа его не трогают. Именно на нём краснел стенд, пока откат `012` ронял снятую позже генерируемую колонку; чинится это мостом (`tenant/054-rollback-bridge.sql`), а не правкой того changeset'а, что сломал откат.

Скрипт возвращает ненулевой код при любом нарушении — его можно вешать в CI как есть, и он там висит.

Запускать его по базе, на которой работает приложение, **нельзя**: Liquibase считает changeset по пути файла, и два накатывающих процесса не видят историю друг друга.
