# parts-platform

Учётная система для авторазборок и продавцов б/у автозапчастей. Мультиарендная SaaS.

Этот файл — контекст для Claude Code. Читай его перед изменениями.

---

## Что это за продукт

Клиенты — авторазборки. Они покупают битые машины (доноры), снимают с них запчасти,
заносят в систему, выгружают объявления на Авито и Дром, продают со склада.

Первые 10 клиентов — компании из одного города, переходящие с конкурирующей системы.
Склады от 3 000 до 50 000 позиций.

Функциональный ориентир — система Bazon (probazon.ru). Паритет по возможностям,
собственная реализация. Дифференциаторы: простота входа, прозрачная цена,
учёт продаж по менеджерам, в перспективе распознавание запчасти по фото.

## Архитектура: решения, которые нельзя менять походя

Полное обоснование — в `docs/architecture-and-plan.md`. Кратко:

**Модульный монолит**, не микросервисы. Один разработчик. Модули (`platform`,
`catalog`, `intake`, `inventory`, `sales`, `publishing`) общаются через интерфейсы
и доменные события, не через чужие репозитории.

**Схема PostgreSQL на арендатора** (`t_000042`), не общая таблица с `tenant_id`.
Причина — независимый бэкап и восстановление одного клиента, плюс изоляция
не зависит от дисциплины в `WHERE`.

**Outbox → Kafka.** Событие пишется в таблицу `outbox` в той же транзакции, что
и данные. Прямая публикация в Kafka из бизнес-кода запрещена: транзакция БД и
отправка в брокер не атомарны, событие потеряется. Транспорт скрыт за
`EventTransport`, чтобы Kafka можно было заменить.

**Ячейки (cells).** Группа арендаторов (до ~200) на общем комплекте
Postgres + Kafka + S3. Отдельный кластер Kafka на арендатора не делаем: при 500
клиентах это 12–22 млн ₽/мес против 150–450 ₽ на арендатора в ячейке.

## Ловушки, на которых этот проект сломается

**`search_path` и PgBouncer.** PgBouncer в transaction mode отдаёт физическое
соединение другой транзакции после коммита. Сессионный `SET search_path` протечёт
к другому арендатору — это ровно та утечка данных, ради предотвращения которой
всё затевалось. Поэтому `TenantConnectionProvider` сбрасывает `search_path`
при возврате соединения в пул. Тест `TenantIsolationTest` это стережёт —
не отключай его.

**Liquibase changeset неизменяем.** После первого прогона правка ломает чек-сумму
и валит деплой (`strict=true` включён намеренно). Исправление — только новым
changeset'ом.

**`DATABASECHANGELOG` живёт внутри схемы арендатора** (`liquibaseSchemaName`).
Это даёт независимое версионирование и параллельные миграции. Не переноси в public.

**Остаток — агрегат журнала `stock_movement`.** Поле `part.qty_on_hand` — кэш,
поддерживаемый триггером. Никогда не пиши в него напрямую из кода: только
через вставку движения.

**Себестоимость фиксируется снимком** в `deal_item.cost_price_snapshot` на момент
продажи. Не пересчитывай из `part.cost_price` в отчётах за прошлые периоды.

**Фид Авито пишется потоково через StAX.** Материализация 50 000 объявлений
в DOM или в String съест гигабайты. Не заменяй на шаблонизатор.

## Структура

```
src/main/java/ru/partsflow/
├── PartsPlatformApplication.java
├── platform/
│   ├── tenant/     — контекст арендатора, маршрутизация соединений
│   ├── outbox/     — DomainEventPublisher, EventTransport, релей
│   └── config/
├── catalog/        — справочники (общая схема catalog)
├── intake/         — доноры, приёмка
├── inventory/      — запчасти, склад, движения
├── sales/          — сделки, оплаты, возвраты
├── publishing/     — выгрузки: Авито (pull-фид), Дром (pull-фид + API-дельты)
└── shared/
db/                 — миграции Liquibase (см. db/README.md)
docs/               — архитектура, доменная модель
```

---

## Как запустить

```bash
docker compose up -d              # postgres, kafka, minio
cd db && ./verify.sh              # проверка миграций (опционально)
mvn spring-boot:run               # приложение на :8080
```

Профиль по умолчанию `local`: транспорт событий — in-memory, Kafka не нужна.
Профиль `kafka` включает реальный транспорт.

## Состояние и что делать дальше

Готово: миграции всех таблиц, маршрутизация арендаторов, Outbox с релеем,
доменные сущности `Donor`/`Part`/`StockMovement`, REST для запчастей,
скелет генератора фида Авито и клиента Дрома.

Ближайшие задачи по плану (`docs/architecture-and-plan.md`, раздел 10):

1. Наполнить справочники марок, моделей, поколений — без них продукт не работает,
   и быстро это не собрать.
2. Доделать генератор фида Авито: маппинг категорий и параметров из
   `catalog.marketplace_mapping`, прогон через официальный валидатор формата.
3. Клиент Дрома: канонический XML-прайс по постоянному URL (Дром забирает сам)
   плюс API-дельты при продаже. Разбивать прайс на пакеты не нужно, отдельная
   задача переподтверждения тоже. Читай `docs/drom-integration.md` перед началом.
4. Приёмка с телефона: PWA, камера, офлайн-очередь в IndexedDB.
5. Импорт из выгрузки Авито и Excel — без него ни один клиент не перейдёт.

## Соглашения

Комментарии на русском и только там, где объясняют **почему**, а не что.
Названия классов и методов — на английском.

Тесты на бизнес-инварианты обязательны: изоляция арендаторов, идемпотентность
потребителей событий, неизменяемость журнала движений.
