## Ответ владельца — 18.10.2026

Вопрос был (по 0321): журнал показывает состояние позиции на момент действия, восстановленное по снимкам `audit_log`, — или нынешнее.

Ответ дословно: «1 - б, у детали только один номер произвоителя - остальное - кросс номера. 2 - а. 3 - а, все правки через UI должны фиксироваться . 4 - а . 5 - а . 6 - в, с предвыбором прошлого выбора клиента но с возможностью изменить . 7 - а». К этой задаче относится «3 - а, все правки через UI должны фиксироваться».

Принцип владельца: **все правки через интерфейс должны фиксироваться.** Разовые дозаполнения мимо интерфейса (0282, повтор файла переноса) — не правки через UI, их владелец не требует.

## Что человек сможет

Владелец, открыв журнал действий организации, видит **любую** правку, которую сотрудник сделал на экране: кто, когда, что было и что стало. Сегодня часть правок видна, часть — нет, и узнать о ней можно только по результату (позиция вдруг снята с выгрузки, затрата по машине исчезла).

Как часто: журнал читают при каждом разборе «кто это сделал»; правки из списка ниже делаются ежедневно («Выгружать» пачкой, затраты по машине, сопоставление написаний).

## Почему это важно

`AuditLogListener` видит только то, что прошло через Hibernate и только для таблиц из `AUDITED` (`part`, `part_drom_card`, `deal`, `deal_item`, `payment`, `donor_cost`). Прямой SQL (`JdbcTemplate`, нативный UPDATE) он не видит; по таблицам вне `AUDITED` журнала нет вовсе. Тот, кого спрашивают «кто это сделал», получает пустой журнал ровно в тех правках, которые делались «быстро, пачкой». Журнал неизменяем (роль без `UPDATE`) — задним числом это не восстановить.

## Что известно

**Читал код 18.10.2026 (перебор `JdbcTemplate.update`, `createNativeQuery`, `executeUpdate` в `src/main/java`), не запускал.** Уже пишет в журнал вручную через `AuditJournal` (задача 0267): выгрузки (`marketplace_account`, `MarketplaceAccountJournal`), номера производителя и кросс-номера в `PartIdentity` (`oem`, `crosses` в записи `part`), пересчёт `OemRecount`. Остальное — таблица ниже. Колонка «Экран» — что нажимает человек; **каждую строку исполнитель проверяет прогоном (правка через экран → запись в `audit_log`) прежде, чем считать пробелом**: список — результат чтения кода.

**А. Таблица из `AUDITED`, но пишется мимо Hibernate:**

| Место | Что делает человек | Что в журнале |
|---|---|---|
| `PartService.setPublished` (`POST /api/parts/publication`, UPDATE `part.is_published`) | «Выгружать»/«Не выгружать» пачкой по отмеченным или по отбору | ничего |
| `DonorCostService.add` / `remove` (INSERT и DELETE `donor_cost`) | затрата по машине записана/удалена | ничего, хотя `donor_cost` в `AUDITED` и в `OrganizationAuditService.KINDS` («Затрата записана/удалена») |
| `PartService.applyMatch`, `applyMatchedNames` (UPDATE `part`: `category_id`, `part_kind_id`) | «Сопоставить написание с видом детали» (экран «Наименования») — меняет вид и категорию у всех карточек написания | ничего (`applyMatchedNames` — доводка после переноса, мимо интерфейса: см. оговорку ниже) |
| `WheelService.attachWheel` (UPDATE `part SET product_line`) | в экране не вызывается кнопкой (только перенос) | не требуется — не правка через UI; проверить и записать |
| Проверить: `PartService.updateAll` (правка списком) и `PartService.update` | должны идти через сущность | прогоном подтвердить, что запись есть |

**Б. Правки через экран, по таблицам вне `AUDITED` (журнала нет вовсе):**

| Таблица | Где правится | Экран |
|---|---|---|
| `part_applicability` (INSERT/DELETE) | `CatalogService` — применимость из карточки добавить и снять | карточка позиции |
| `customer` (UPDATE ~267, INSERT) | `CustomerService` | карточка клиента |
| `donor` (Hibernate-сущность `Donor`, UPDATE `generation_id` — `DonorVehicleResolver`) | перевод в разбор, место машины, поколение | экран «Машины» |
| `warehouse` (UPDATE/INSERT, `print_details`) | `OrganizationService`, `PrintSettingsService` | «Склады», настройки печати |
| `tenant_member` (INSERT, смена пароля, `is_active`) | `MemberService` | «Сотрудники» |
| `payment_source`, `deal_source` (INSERT, архив) | `PaymentSourceService`, `DealSourceService` | справочники сделок |
| `company_setting` (резерв дней, печатные тексты) | `CompanySettingsService`, `PrintSettingsService` | настройки |

| ячейка позиции (перестановка) | `StockLedger` пишет движение `MOVE` в журнал склада (`stock_movement`, не `audit_log`) — след есть, но в журнале организации его нет; исполнитель называет, достаточно ли этого | «Переставить на полку» |

Что журнал неизменяем и пишется только `INSERT`-ом (роль `partsflow_app` без `UPDATE`/`DELETE`) — известно; `AuditJournal` метод `MANDATORY` (нужна транзакция), таблица без словаря в `AuditedColumns` отвергается, **«забытый вызов рядом с новым UPDATE молча не пишет ничего»** — записано в `platform/CLAUDE.md`. Показ журнала — `OrganizationAuditService` (`KINDS`, `CREATED`, `REMOVED` — словарь «вид вещи» словом).

**Что не требуется (по словам владельца):** разовые дозаполнения мимо интерфейса — `ExcelWarehouseImporter` (повтор файла 0282), `BazonImporter`, `OemRecount` (он и так пишет), `DromApplicabilityService` (массовый проход — исполнитель называет решение: записывается ли в журнал кнопка «Разложить «Подходит»», которая **нажимается на экране**, в отличие от разбора при загрузке; предложение — одна запись «разложено N позиций» на нажатие, не по записи на позицию).

**Что решает исполнитель (называет в PR), владельцу вопрос не нужен — принцип сказан «все»:**
* *Гранулярность массовых правок.* Одна запись на позицию (как слушатель сейчас — 35 000 записей на «Выгружать» по всему складу) или одна запись на нажатие с числом и отбором. Предложение: для пачек на сотни — запись на позицию (иначе «что случилось с позицией 347» не отвечается), для «весь склад» — одна запись с отбором и числом **плюс** запись на позицию; цену по объёму (`audit_log` растёт) исполнитель мерит и называет.
* *Что из таблицы Б сводится в журнал организации, а что остаётся в карточке позиции/сущности.* Минимум — запись в `audit_log` (см. требования), экран журнала организации (`KINDS`) расширяется теми видами, у которых есть что показать человеку словами.

## Требования

1. Для каждой строки таблиц А и Б исполнитель **прогоном** выясняет, пишется ли запись, и результат вносит в PR («было/стало» по строке). Строка, оказавшаяся записанной, из задачи уходит; строка, правка которой не через UI, закрывается словами «не правка через UI» с доказательством (кто зовёт).
2. Каждая оставшаяся правка через экран пишет запись в `audit_log` в той же транзакции (`AuditJournal` либо перевод на Hibernate, если это естественно): таблица, номер записи, «было» и «стало» по изменённым полям, автор и роль (`CurrentAuthor`). Словарь полей — `AuditedColumns`.
3. Секреты (пароль сотрудника, токены, `credentials`) в «было»/«стало» **не пишутся** — пишется факт замены, как `MarketplaceAccountJournal.secretReplaced`.
4. Новый путь записи **нельзя завести молча**: перебор (по образцу `endpoint-coverage.py` и `RefusalNamesPartWithOemTest.namedOnlyHere`) находит в `src/main/java` прямые `UPDATE/INSERT/DELETE` по таблицам, правка которых доступна с экрана, и требует рядом `AuditJournal` либо запись в перечне с причиной «не правка через UI». Перебор проверяется подложенным дефектом (убранный вызов краснит его) — проверка, которая не краснеет, хуже отсутствующей.
5. Журнал организации (`AuditJournalScreen`) показывает новые виды вещей словами (`KINDS`/`CREATED`/`REMOVED`), без внутренних номеров и кодов; поиск по журналу находит их.
6. Не ломает: `AuditLogListener` для уже записываемых таблиц, неизменяемость журнала, идемпотентность операций, отметку для Дрома (запись в журнал не ставит `part_change`).

## Как проверить, что сделано

1. По каждой строке перечня — тест через HTTP: нажатие на экране (запрос) → в `audit_log` появилась запись с автором, ролью, «было»/«стало»; откат (убрать вызов журнала) краснит именно его.
2. Перебор прямых записей по таблицам с экрана краснеет на убранном `AuditJournal` и молчит на разрешённом перечне.
3. Живой прогон: «Выгружать» пачкой, затрата по машине, сопоставление написания, смена клиента/склада/сотрудника — все видны в журнале организации словами.
4. Объём: замер размера `audit_log` на «Выгружать» по складу в 35 841 позицию и времени запроса журнала до и после; результат — в PR.
5. Записи: `platform/CLAUDE.md`, `inventory/CLAUDE.md`, `intake/CLAUDE.md`, `sales/CLAUDE.md`; таблица §12 `docs/bazon-parity.md`.
