## Ответ владельца — 18.10.2026

Вопрос был: ожидаемая позиция (ожидаемый товар по поставке, `registerExpectedPart`) заводится без вопроса о состоянии, и ей молча ставится «б/у». После 0318 это слово видно владельцу в «Ожидаемом», приёмщику в «Ожидалось по этой поставке» и продавцу при продаже под предзаказ — то есть показывает то, чего никто не выбирал.

Ответ дословно: «1 -б 2-а 4-a + номер производителя запчасти 5 - а 6-б 7-а 8-a с возможностью заводить без состояния»; к этому вопросу относится «8-a с возможностью заводить без состояния».

Следствие: при заведении ожидаемой позиции **спрашивать состояние**, по умолчанию «б/у», и дать **завести без состояния**.

## Ответ владельца — 18.10.2026 (второй набор вопросов)

Ответ дословно: «1 - б, у детали только один номер произвоителя - остальное - кросс номера. 2 - а. 3 - а, все правки через UI должны фиксироваться . 4 - а . 5 - а . 6 - в, с предвыбором прошлого выбора клиента но с возможностью изменить . 7 - а»; к этой задаче относятся пункты 4, 5 и 6.

* **4 - а.** Позиция «Не указано» не уходит на Дром (решение исполнителя 0322 принято): объявление появится, когда состояние выберут.
* **5 - а.** Правка карточки состояние не снимает, а выбирает (решение исполнителя принято): снять состояние правкой нельзя, выбрать позиции без состояния — можно.
* **6 - в, с предвыбором прошлого выбора клиента, но с возможностью изменить.** Открытый вопрос из «Что известно» («нужно ли состояние при приёмке ожидаемой позиции») закрыт: на приёмке ожидаемой позиции поле «Состояние» показывается всегда, предвыбрано то, что выбрали при заведении, и его можно поменять. Работа заведена: **0326**. Заведение ожидаемого она не блокирует.

## Ответ владельца — 18.10.2026 (подтверждение решения исполнителя)

Ответ дословно: «8-10 да» (вопросы 8–10 того же набора). К этой задаче относится вопрос 10: если форма заведения пришла без ключа `condition` (вкладка открыта до выкладки), позиция получает «Не указано», а не «б/у». **Решение исполнителя 0322 («нет ключа» = «Не указано», PR 460, 463) подтверждено владельцем продукта 18.10.2026.**

## Что человек сможет

Владелец, заводя по контейнеру в пути ожидаемую позицию, выбирает состояние — «новая», «б/у» (предложено сразу), «восстановленная», «контрактная» — или **не выбирает вовсе**, если не знает. Позиция без состояния показывается без слова состояния, а не с ложным «б/у».

Как часто: заведение ожидаемого — работа по каждой поставке «в пути» (несколько раз в неделю у тех, кто ведёт предзаказы). Тому, кому подходит «б/у», поле не должно прибавлять ни одного нажатия.

## Почему это важно

Состояние ожидаемой позиции не выбирается, а выставляется сущностью по умолчанию `USED`. До 0318 этого не было видно; теперь слово «б/у» показывается продавцу и покупателю предзаказа — и для контрактного агрегата, приехавшего партией, оно неверно. Владелец уже решил (9 октября 2026), что контрактные агрегаты приезжают партиями без машин, то есть именно ожидаемое часто не «б/у».

## Что известно

**Проверено по схеме и коду на `main` 18.10.2026 (читал, не запускал):**

* **Схема не допускает пустого состояния.** `db/changelog/tenant/004-parts.sql:15`: `condition text NOT NULL DEFAULT 'USED'`; `part_condition_ck CHECK (condition IN (...))` (четыре значения, переписан в `070-part-condition-contract.sql`). Сущность тоже ставит умолчание: `Part.java:109` — `private PartCondition condition = PartCondition.USED;`.
* **«Завести без состояния» требует changeset:** снять `NOT NULL` (и, вероятно, `DEFAULT`) с `part.condition`; `CHECK` с `IN (…)` NULL пропускает сам. **Changeset делает только `migrator`, по одному за раз, с откатом** (`db/CLAUDE.md`): исполнитель этой задачи changeset не пишет — запрашивает у `migrator`а и возвращает номер и текст в PR. Откат вернуть `NOT NULL` может только если пустых нет — как откатывать при пустых (проставить `USED` или отказать словами), решает `migrator`.
* **Путь заведения.** `IntakeController.addExpectedPart` (`POST /api/intake/supplies/{id}/expected-parts`, `OWNER_ONLY`) → `ExpectedPartRequest` → `IntakeService.registerExpectedPart(supplyId, rawName, donorId, quantity, price, authorId, requestId)` → `buildPart`. Состояния в запросе нет. Экран — `frontend/src/screens/ExpectedGoods.tsx`.
* **Приёмка состояние ожидаемой не трогает:** `IntakeService.acceptExpected` (~249) принимает позицию «как есть».
* **Открытый вопрос владельцу, код ответа не даёт:** нужно ли состояние при приёмке ожидаемой позиции, когда она становится настоящей. Варианты: (а) приёмка ничего не спрашивает; (б) приёмка показывает заведённое состояние и, если позиция заведена «без состояния», требует выбрать; (в) то же, но поправить можно всегда. Предложение — (б): позиция без состояния не ложится на склад без него. Исполнитель вопрос **не решает**, а выносит; это отдельная задача после ответа, и заведение она не блокирует.
* **Показ пустого состояния — сверить прогоном, а не по заявлению.** По 0314/0318 и ответу «7-а» (страница по ссылке пустое и незнакомое не печатает) пустое слово не должно печататься. Проверить на каждом месте: склад (`CatalogRow.condition`, `conditionTitle` → `null`), продавец (корзина, поиск, состав сделки, `ConditionWord`), этикетка, печатные документы сделки (`DealPrintService`, `PartService.conditionsOf`), страница по ссылке, лист обхода и сведение пересчёта, состав перевозки, отчёт по машине, «Ожидалось по этой поставке», отказы (`PartCondition.named` при `null` возвращает наименование; `PreorderService.named` ждёт `null` из строки — проверить), `sqlLabel` (CASE без ELSE даёт NULL), `StockNaming` (после 0321). «null», «undefined», висящий « · » или падение на пустом состоянии — дефект этой задачи.
* **Места, читающие `part.condition` как не-NULL (вывел, перебрать по `src/main/java`):** отбор выгрузки `p.condition = ANY (...)` (позиция без состояния не попадёт ни в один отбор по состоянию — назвать, как должен вести себя отбор «все»); `DromPriceWriter` / `DromOffer` (что уезжает в поле состояния объявления для позиции без состояния — **молча как «б/у» не отправлять**, решение назвать в PR; предложение — не выгружать до выбора состояния); колёсный прайс; отчёты, группирующие по состоянию (строка «без состояния»); `BazonImporter` и другие пути, пишущие состояние сами.

### Требования

1. Форма заведения ожидаемого: поле «Состояние» со списком из четырёх значений (`CONDITION` / `conditionTitle()` в `frontend/src/inventory/catalog.ts`, не свой словарь) и пунктом «Не указано»; «б/у» предложено без нажатия; нажатий тому, кому подходит «б/у», не больше, чем сейчас.
2. Запрос заведения несёт `condition` (код) или пустое; пустое = без состояния; незнакомое значение отбивается словами (формулировку берёт исполнитель из соседних отказов), а не пятисоткой `part_condition_ck`.
3. `part.condition` допускает NULL (changeset `migrator`а). Умолчание «б/у» для пути ожидаемого переезжает на форму, а не сидит молча в сущности; для других путей заведения (приёмка, перенос) умолчание без решения не менять.
4. Позиция без состояния проходит все места сверки без «null», без висящего разделителя, без падения.
5. Выгрузка: позиция без состояния на площадку не уходит молча как «б/у».
6. Идемпотентность заведения по `requestId` не сломана.

## Как проверить, что сделано

1. Заведение с каждым из четырёх значений, с пустым и с незнакомым: сохраняется / сохраняется пустым / отказ словами. Тест через HTTP.
2. Живой прогон: форма предлагает «б/у»; «Не указано» заводит позицию, и она не показывает слова состояния ни на складе, ни в «Ожидаемом», ни в «Ожидалось по этой поставке», ни в сделке под предзаказ, ни на странице по ссылке.
3. Перебор мест, читающих `part.condition`: ни одно не падает и не печатает `null`; список «было / стало» — в PR.
4. Откат миграции проверен на схеме с пустыми значениями и без.
5. Записи: `intake/CLAUDE.md`, `inventory/CLAUDE.md`, `db/CLAUDE.md`; таблица §12 `docs/bazon-parity.md`.
