## Что найдено

`ops/deploy-access.sh`, ветка ПРОМ:

```
who="${reviewer:-$("$GH" repo view --json owner --jq .owner.login)}"
id="$("$GH" api "users/$who" --jq .id)"
printf '{"reviewers":[{"type":"User","id":%s}],…}' "$id" | "$GH" api -X PUT … --input -
```

Если `gh api users/<кто>` ответит пустым — логин с опечаткой, учётной записи
нет, сеть ответила не тем, — то `id` пуст, и в тело уходит
`{"reviewers":[{"type":"User","id":}]}`: **синтаксически неверный JSON**.

## Почему это стоит задачи

Отказ здесь ожидается от GitHub, а не от нас, и звучать он будет про разбор
JSON — то есть человек получит невнятное сообщение вместо «пользователя
с таким логином нет». Хуже, если GitHub стерпит тело без `reviewers`:
тогда окружение `prom` заведётся **без обязательного подтверждающего**,
команда отчитается успехом, и узнают об этом в день, когда кто-то выложит
на живые данные клиента без подтверждения.

Это тот же класс, что «ответ без ожидаемого ключа — чужой ответ, а не ноль»
(`ops/CLAUDE.md`, про накат схем): пустота от внешней команды принимается
за значение.

## Что сделать

Проверять `id` до сборки тела: пусто или не число — отказ словами, с именем
логина и подсказкой про `--подтверждающий`. И **после** заведения окружения
спрашивать у GitHub, что подтверждающий действительно стоит, — сегодня это
делает только `проверить`, отдельной командой, которую можно не запустить.

## Как проверить, что сделано

**Доказательство:** подменный `gh`, отдающий пустую строку на `users/…`, —
команда обязана отказать, назвать логин и **не** послать PUT. Проверить это
пробой в `--selftest`, и убедиться, что она краснеет на снятой проверке:
без этого она повторит историю первой редакции самопроверки 0140, где пять
проб из одиннадцати не утверждали ничего.
