## Что человек сможет

Открыв карточку машины, перенесённой с Bazon до этой выкладки, увидеть в поле «Статус» её прежний статус из Bazon («В Японии», «В [город]») и выбрать то же значение в «Настройки → Статусы машин» у любой другой машины — как у машины, перенесённой уже новым кодом.

Как часто: один раз на клиента при выкладке; затронуты все перенесённые машины (у переходящего клиента ≈530 доноров).

## Почему это важно

Решение владельца 31.10.2026 (`tasks/0364-mashina-donor-polnaya-forma-pravka-posle-zavedeniya-zapchasti-mashiny.md`, раздел «Ответ владельца — 31 октября 2026», п. 2): статусы машин из Bazon переносятся в список статусов клиента; для уже перенесённых, если нужен changeset с данными, — отдельная схемная выдача `migrator`, один за раз. Нужен: новый код переноса (PR 542) пишет статус в `donor_status`/`donor.status_id` только при следующем переносе. Машины, перенесённые раньше, хранят статус Bazon в «Где стоит» (`donor.location`), а `tenant/110` выдал им `status_id` по состоянию приёмки («Куплена» и т. п.). Без данных у ≈530 машин стоит «Куплена» вместо «В Японии», и исправить это можно только повторным переносом всего склада.

## Что известно

* **Номер донора уже перенесённым этой задачей не трогается:** `tenant/108` проставляет `donor.number` из `legacy_code` (целое > 0; из двух кодов с одним числом — у меньшего `id`). Отдельный changeset на номер не нужен; исполнитель подтверждает это тестом и называет в PR.
* Статус перенесённой машины лежит в `donor.location` — **вывод** по `tasks/0364`, «Ход работы — 31 октября 2026» («так пишет перенос»); код переноса до PR 542 исполнитель этой задачи читает сам. Признак перенесённой — `donor.legacy_code IS NOT NULL`.
* `donor_status`: уникальность по `lower(btrim(name))`, `sort_order`, ссылка с машины без `ON DELETE` (`tenant/110`).

### Как сделать (для сборки)

Исполнитель `migrator`, один за раз. Номер changeset'а — первый свободный по `origin/main` на момент взятия: на 31.10.2026 `tenant/111` заявлен дважды (PR 541, 0343, и PR 543, 0386), брать после их слияния. Раньше слияния PR 542 не выкладывать: экран и перенос должны знать новое поле.

1. Для машин с `legacy_code IS NOT NULL` и непустым `btrim(location)`: найти в `donor_status` запись с тем же `lower(btrim(name))`; нет — завести в конец списка (`sort_order = max + 1`, в порядке первого появления по меньшему `donor.id`).
2. Поставить `status_id` на найденную или заведённую запись **только тем машинам, у которых `status_id` всё ещё тот, что выдал `tenant/110`** (имя совпадает с прежним перечнем по `donor.status`): выбор, сделанный человеком, не перезаписывается.
3. `donor.location` **не очищать**: данные не теряются, «Где стоит» остаётся как было (решение владельца «не менять прежнего образа без нужды», `tasks/0364`). Если исполнитель считает иначе — это вопрос владельцу в этой задаче, а не его решение.
4. Откат: описать, что теряется (заведённые значения списка и выбор); `status_id` вернуть по `donor.status`, как в `tenant/110`.
5. Повторный накат безвреден; схема без перенесённых машин (новый клиент) не падает.

## Как проверить, что сделано

1. Схема с перенесёнными машинами: `location` «В Японии» у двух, «В Москве» у одной, пусто у одной. После наката в `donor_status` две новые записи («В Японии», «В Москве»), у трёх машин `status_id` — они, у четвёртой прежний; `location` не изменился.
2. Машина, у которой человек успел сменить `status_id`, не перезаписана.
3. Регистр и пробелы («в японии ») не дают второй записи.
4. Накат на схеме без перенесённых машин ничего не меняет; откат проходит.
5. Тест падает без changeset'а: у машины, перенесённой по старому коду, статус из Bazon не выбран.
