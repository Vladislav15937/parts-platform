## Что человек сможет

Прийти на боевую ячейку разбираться и получить от git либо правду
о лежащих настройках, либо явное «git здесь не источник правды,
спрашивай так-то», — а не молчаливый ответ про восьмидневной давности
коммит. И выполнить ручной путь выкладки на этой машине, не упираясь
в тринадцать файлов, которых git не ждёт.

## Почему это важно

**На машине смешаны два способа доставки настроек.** Дерево заведено
подъёмом: `docs/cloud-bringup.md:155` — `git clone <репозиторий>
parts-platform`, и там же сказано зачем — «из репозитория берутся
`docker-compose.prod.yml` и каталог `ops/`». Потом доставку сменили:
кнопка кладёт настройки `rsync`'ом с выкладываемого коммита
(0111, `.github/workflows/deploy.yml:265-267`) и git на машине
**не трогает вовсе** (`grep -n 'git ' ops/deploy.sh` — пусто). Клон
остался и с 19 сентября не двигался.

**Замерено на ячейке 28 сентября 2026** (командами владельца; разведка
в ячейку не ходила): `git status --short --branch` → `## HEAD (no
branch)`, `git log --oneline -1` → `222571c` (19 сентября). При этом
файлы на диске — ровно `ops/` коммита `65397d0` (27 сентября): проверено
сверкой `git diff --name-only 222571c 65397d0 -- ops
docker-compose.prod.yml`, которая даёт **ровно те 19 путей**, что
владелец видел расходящимися (подробности — в `tasks/0215`).

Отсюда три следствия, и каждое уже сработало.

**1. Документ велит проверять то, что на этой машине проверить нельзя.**
`docs/deployment.md:878` — `git rev-parse HEAD # обязан совпасть
с APP_IMAGE_TAG в .env`, и `:902-906` объявляет это свойством: «пара
„код и настройки“ стала проверяемой одной командой, а не памятью
выкладывающего» (то же — `ops/CLAUDE.md:1908`). На ячейке, которую
выкладывают кнопкой, эта команда отвечает SHA восьмидневной давности
при совершенно верных настройках: равенство не может выполниться
по построению, потому что кнопка `HEAD` не двигает.

**2. Ручной путь на этой машине не выполнить.** Шаг 0 того же раздела —
`git checkout --detach <новый SHA>`. На дереве, где `rsync` переписал
тринадцать отслеживаемых файлов, git отказывает («Your local changes
to the following files would be overwritten by checkout») — то есть
резервный путь, которым выкладывают версию старше кнопки, на боевой
ячейке закрыт, и узнают об этом в ту минуту, когда он понадобился.

**3. Признак «норма или беда» по этому дереву уже дважды соврал.**
`ops/CLAUDE.md:3539-3575`: человек увидел восемь расходящихся файлов,
прочитал это как отказ и остановился — «правильно по букве инструкции
и напрасно по существу»; починка того же признака содержала тот же
дефект, потому что сверялась с `origin/main`, от которого дерево
отстаёт законно. Вывод памятки: «норму нельзя записывать утверждением,
которого не измеряли».

**Цена — время разбора в худшую минуту.** На эту машину приходят, когда
что-то сломалось. Первое, что делает пришедший, — спрашивает git, что
здесь стоит; git отвечает уверенно и неверно, и дальше версия причины
строится на этом ответе. За 28 сентября это уже произошло: двадцать
расходящихся файлов были прочитаны как «настройки обновляли мимо git
и они могли устареть», тогда как файлы были ровно с выложенного коммита.

## Как проверить, что сделано

1. **Решено и записано, чем на боевой ячейке является дерево git** —
   источником настроек (тогда его двигает выкладка, и `rsync` с ним
   согласован) или наследием подъёма, которое больше ничего не значит
   (тогда документы это говорят прямо, а `git rev-parse HEAD` перестаёт
   предъявляться как ответ о версии настроек). Один из двух, а не оба:
   два способа доставки на одну машину — это то, из-за чего задача
   и завелась.
2. **Ни один документ не содержит проверки, которая на кнопочной ячейке
   не может пройти.** Перебором по `docs/deployment.md`,
   `docs/deploy-button.md`, `docs/pilot-server.md`, `docs/cloud-bringup.md`
   и `ops/CLAUDE.md`: где написано «обязан совпасть», там сказано, при
   каком способе доставки это верно.
3. **Ручной путь выполним на машине, которую выкладывали кнопкой** —
   либо приведением дерева, либо заменой шага 0 на то, что работает
   (`git show <SHA>:<файл> > <файл>` уже применяется точечно,
   `docs/deployment.md:2255-2257`). Проверяется репетицией на стенде,
   устроенном как ячейка: `rsync` настроек с коммита A, затем ручной
   путь на коммит B.
4. **`ops/active-build.caddy` при любом приведении не переписывается.**
   Версия из репозитория объявляет активной синюю сборку
   (`reverse_proxy app-blue:8080`), а подмена inode при живом терминаторе
   означает, что следующее переключение сборок «пройдёт» и не случится
   (`ops/CLAUDE.md:1895-1906`). Если приведение всё же его трогает,
   в том же шаге стоит `up -d caddy`, и цена названа.
5. **Команда человеку — сначала читающая.** Печатает, что собирается
   сделать и с какими файлами, и только потом делает; признак отказа
   у каждого шага. Ячейку правит человек, не агент.

## Чего делать нельзя

* **Не приводить дерево `git checkout -f`, `git pull` или `git stash`
  по `ops/`.** Причина та же, что в 0215: среди расходящихся файлов
  есть живое состояние, и «привести к репозиторию» означает перевести
  трафик на сборку из умолчания. `git update-index --skip-worktree`
  тоже не спасает — проверено, git отказывает тем же сообщением
  (`ops/CLAUDE.md:1882-1886`).
* **Не решать за владельца, что делать с клоном на боевой машине.**
  Убрать его совсем — это отнять и точечную правку через `git show`,
  которой применяли 0153. Вопрос назвать, а не закрыть.
* **Не переписывать историю памяток.** Записи про отцепленный `HEAD`
  верны для ручного пути и объясняют, почему так сделано; сужать надо
  обещание, а не вырезать рассказ.
* **В боевую ячейку не ходить.**
